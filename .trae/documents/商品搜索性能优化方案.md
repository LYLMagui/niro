# 商品搜索性能优化方案

## 1. 结论与推荐路径

* **推荐方案**：采用 **后端模糊搜索 API + 前端防抖调用** 的模式。

* **原因**：全量加载商品数据（尤其是商品量级大时）会导致前端内存占用高、渲染卡顿、首次加载慢，且无法利用数据库索引。

* **预计收益**：首屏加载速度提升 90%，内存占用降低 80%，支持海量数据搜索。

## 2. 个人开发者视角（60%｜落地优先）

### 2.1 实现复杂度与最小可行（MVP）

* **废弃**：`/goods/simple-list` 全量接口（或仅保留给小数据量场景）。

* **新增/改造**：改造 `/goods/simple-list` 接口，支持 `keyword` 参数进行后端模糊搜索，并限制返回条数（如 limit 50）。

* **前端改造**：`t-select` 开启远程搜索模式 (`remote-method`)，配合 `lodash.debounce` 防抖。

### 2.2 维护性与可演进

* **可扩展点**：后续可引入 Elasticsearch 替换数据库 `LIKE` 查询，接口契约不变。

* **数据库优化**：为 `name` 和 `short_name` 字段创建 GIN 索引（pg\_trgm 扩展）以加速模糊匹配。

## 3. 产品经理视角（25%｜用户价值与体验）

* **交互流程**：用户输入关键词 -> 前端防抖 (300ms) -> 调用后端 -> 展示匹配的前 50 条选项。

* **体验提升**：避免了等待全量数据加载的 Loading 时间，输入响应更灵敏。

## 4. 架构师视角（15%｜边界与可靠性）

* **性能与安全**：

  * 必须限制单次返回数量（Limit），防止恶意拉取。

  * 必须添加防抖，防止高频接口调用压力。

  * 数据库层面建议开启 `pg_trgm` 扩展优化 `LIKE %xxx%` 查询。

## 5. 实施步骤

1. **数据库优化**：PostgreSQL 开启 `pg_trgm` 并创建索引。
2. **后端接口改造**：`getSimpleList` 增加 `keyword` 参数，实现 `LIKE` 查询 + `LIMIT`。
3. **前端组件改造**：`t-select` 改为远程搜索模式，实现防抖查询。
