# 订单记录页按 C5 任务页标准对齐设计

## 技术规格
Goal: 将 `niro-client/src/views/OrderRecord.vue` 重构为与 `niro-client/src/views/TaskList.vue` 同路数的 C5 页面风格，统一桌面端与移动端的视觉层级和交互节奏，同时保留现有订单业务能力。
Scope: 仅修改 `niro-client/src/views/OrderRecord.vue` 的页面结构、列表呈现、移动端展示、局部格式化逻辑与少量页面级样式；必要时少量补充 `niro-client/src/style.css`，但不改接口层、权限模型、后端返回结构与详情抽屉数据来源。
Risks: 当前订单页是纯表格导向结构，重组为任务页式骨架后，容易出现桌面端表格节奏不稳、移动端卡片信息过密、勾选与批量操作反馈不一致，以及详情操作在不同端口径不统一。
Compatibility: 保持查询、重置、状态 Tab、排序、勾选、批量删除、C5 同步、详情抽屉全部可用；继续使用 `orderApi` 现有接口与 `PermissionConstant` 现有权限，不新增接口字段、不修改状态枚举语义。
Verification: 手动验证桌面端与移动端布局、筛选展开/收起、Tab 切换、查询/重置、批量删除、同步 C5、详情查看、空态和分页；前端至少通过 `pnpm type-check`，有条件再执行 `pnpm build`。

## 背景与现状

当前订单记录页位于 `niro-client/src/views/OrderRecord.vue`，已经具备完整业务能力：

- 顶部状态 Tab：全部 / 成功 / 失败 / 取消
- 筛选条件：订单关键词、平台类型
- 工具栏：同步 C5 订单、批量删除、列设置
- 表格列：ID、商品信息、平台/账号、平台订单号、价格、状态、时间、操作
- C5 详情抽屉：展示订单详情与扩展信息

但它和 `niro-client/src/views/TaskList.vue` 的页面节奏不一致，主要问题有三类：

1. 结构不一致：订单页还是“筛选 + 表格”的旧式排布，任务页已经形成稳定的“筛选区 + 工具栏 + 主内容区 + 移动端卡片”的管理后台骨架。
2. 视觉层级偏散：订单页的按钮、选择反馈、空态和表格区域节奏与任务页不统一，看起来像另一套页面。
3. 移动端缺失：任务页已经有完整的移动端卡片策略，订单页仍然只面向表格，窄屏下可读性和操作性都差。

真实问题不是订单页缺功能，而是页面组织方式落后于当前 C5 页面标准。

## 方案对比

### 方案 A：只做视觉统一，不改结构

做法：

- 保留当前 DOM 结构和表格主导形式
- 只统一按钮、边距、标签、表格样式、空态样式
- 移动端继续沿用压缩表格或最小修补

优点：

- 改动最小
- 风险最低

缺点：

- 很难真正对齐 `TaskList.vue`
- 页面骨架和交互节奏还是旧的
- 移动端问题基本解决不了

### 方案 B（推荐）：按任务页骨架做中度结构对齐

做法：

- 保留现有业务能力与接口
- 重建页面为 `TaskList.vue` 同款骨架
- 增加轻量统计摘要
- 增加移动端卡片视图
- 允许重排信息分组和部分列的展示层级

优点：

- 真正实现“按 C5 页面标准统一”
- 视觉和交互都能和任务页并轨
- 不碰接口与业务边界，风险仍然可控

缺点：

- 比纯样式修补多一些模板重组工作
- 需要同时照顾桌面端和移动端展示口径

### 方案 C：在方案 B 基础上做更强的信息面板化改造

做法：

- 强化顶部摘要区
- 进一步压缩列、重排操作入口
- 把订单页做成更偏“订单中心”的独立风格

优点：

- 信息密度和扫读效率可能更高

缺点：

- 已经偏离“对齐 `TaskList.vue`”这个目标
- 容易把页面做成另一套设计
- 超出本次重构边界

## 结论

采用 **方案 B**。

理由：用户已经明确这次要按 `niro-client/src/views/TaskList.vue` 的标准对齐，并允许中度信息重组、要求桌面端与移动端一起做，同时只接受轻量统计摘要。方案 B 正好卡在这个边界内：结构统一、交互统一、移动端补齐，但不扩散到接口和业务规则。

## 详细设计

### 1. 页面骨架

`niro-client/src/views/OrderRecord.vue` 重构为与 `TaskList.vue` 一致的骨架层级：

1. 页面外层白底主容器
2. 顶部状态 Tab
3. 筛选区
4. 工具栏 + 勾选反馈区
5. 轻量统计摘要
6. 主内容区
   - 桌面端：表格
   - 移动端：订单卡片
7. 详情抽屉

设计原则：

- 顶部先给筛选，再给动作，再给结果内容
- 保持用户在任务页和订单页之间切换时的阅读路径一致
- 不为了统一而拆散现有业务能力

### 2. 筛选区设计

沿用任务页的“核心条件常驻，次要条件折叠”的模式。

#### 默认展示

- 订单关键词

关键词占据主筛选位，文案继续使用：`请输入商品名/订单号`

#### 展开后展示

- 平台类型

当前只有一个高级筛选项，因此不新增新的筛选条件，也不强行把筛选区做复杂。

#### 交互规则

- 查询按钮放在筛选动作区右侧
- 重置按钮与查询并列
- 展开/收起使用和任务页一致的轻链接形式
- 移动端初始默认收起高级筛选，桌面端默认展开

### 3. 工具栏与勾选反馈区

工具栏直接复用任务页的组织方式：左侧放操作，右侧放提示和勾选反馈。

#### 左侧操作

- 同步 C5 订单
- 批量删除
- 列设置

约束：

- 不新增新动作
- `同步 C5 订单` 保留 loading 态
- `批量删除` 仍然只处理当前页已勾选记录
- `列设置` 继续保留现有占位行为，不借这次重构顺手实现新功能

#### 右侧反馈

- 文案：`提示：批量删除仅处理当前页已勾选数据`
- 已选择 N 项
- 清空勾选

目标：

- 把勾选反馈做成和任务页一致的固定认知位置
- 避免用户在表格和按钮之间来回找当前选择状态

### 4. 轻量统计摘要

在工具栏下方增加一行轻量摘要，不新增接口，直接基于当前页 `dataList` 计算：

- 全部
- 成功
- 失败
- 取消

规则：

- 全部 = 当前页记录数
- 成功 = `status === 1`
- 失败 = `status === 2 || status === 11`
- 取消 = `status === 3`

设计边界：

- 这是页面摘要，不是假装成全局统计
- 不放金额、不放跨页统计、不暗示用户它代表全部数据集
- 视觉上保持轻量，作用是让 Tab、列表和状态认知更连贯

### 5. 桌面端表格设计

桌面端保留 `t-table`，但展示节奏向任务页靠拢。

#### 保留列

- 勾选列
- ID
- 商品信息
- 平台/账号
- 平台订单号
- 价格
- 状态
- 时间
- 操作

#### 列内展示规则

##### 商品信息

继续使用“缩略图 + 商品名 + 次信息”的形式：

- 主信息：商品名称
- 次信息：磨损

要求：

- 商品名保持为主要阅读焦点
- 次信息弱化，不与价格、状态抢视线

##### 平台/账号

继续展示平台 tag 和账号名。

要求：

- 平台 tag 保留 `BUFF` / `C5` 区分
- 账号名作为次信息展示
- 没有账号名时展示 `-`

##### 平台订单号

- 有订单号时可点击查看详情
- 无订单号时显示 `未生成`
- 保留等宽字体，但视觉权重要低于商品信息

##### 价格

- 继续显示 `¥xx.xx`
- 保持可排序

##### 状态

状态展示继续沿用现有语义，但统一视觉：

- 成功：绿色 light tag
- 失败：红色 light tag，hover 可看错误信息
- 取消：灰色 light tag
- 其他：主色 light tag，表示处理中

##### 时间

- 继续显示创建时间
- 保持可排序
- 文案格式不变

##### 操作

- `详情`：仅 C5 且有订单号时可见
- `删除`：继续带确认

约束：

- 不新增快捷操作
- 不把操作列变成复杂下拉菜单

### 6. 移动端卡片设计

参考 `TaskList.vue` 的移动端实现，为订单页增加卡片模式。

#### 卡片结构

每张卡片拆成三层：

1. 卡片头部
   - 勾选框
   - 商品缩略图
   - 商品名
   - 次级商品信息（磨损）
   - 右侧状态 tag
2. 卡片主体
   - 平台/账号
   - 平台订单号
   - 价格
   - 时间
3. 卡片操作区
   - 详情
   - 删除

#### 展示要求

- 不是把桌面表格简单压缩，而是重排为更适合窄屏阅读的块状信息
- 订单号可以换行或截断，但要保证用户能识别是否已生成
- 平台和账号信息合并呈现，减少碎片化标签
- 卡片操作按钮放底部，避免挤进信息区

#### 分页

移动端沿用 `TaskList.vue` 的简单分页形式：

- 使用 `t-pagination`
- `theme="simple"`
- 不展示页大小切换

### 7. 响应式策略

本次响应式目标不是另起一套移动设计，而是让订单页和任务页采用同样的切换规则。

规则：

- 使用与任务页一致的窗口宽度判断策略
- 桌面端展示表格
- 移动端展示卡片
- 高级筛选在移动端默认收起
- 工具栏、摘要和勾选反馈在移动端改为纵向堆叠，但信息口径不变

### 8. 状态与交互规则

#### Tab 与筛选联动

- `全部`：`queryParams.status = undefined`
- `成功`：`queryParams.status = 1`
- `失败`：`queryParams.status = 2`
- `取消`：`queryParams.status = 3`

保持现有逻辑，不改状态值映射。

#### 查询与重置

- 查询：重置到第一页，清空当前勾选，重新拉取数据
- 重置：恢复默认筛选状态，并回到 `全部`

#### 勾选与批量删除

- 勾选行为继续基于当前页数据
- 翻页后自动过滤掉当前页不存在的勾选项
- 批量删除仍然通过当前页 `selectedRecords` 计算

#### 详情抽屉

- 继续只支持查看 C5 订单详情
- 抽屉数据结构不改
- 抽屉内部布局可以只做轻量样式整理，不重做信息模型

### 9. 实现边界

本次明确不做以下事情：

- 不改 `src/api/order.ts`
- 不改 `src/types/order.ts` 的接口结构
- 不新增统计接口
- 不改 `PermissionConstant`
- 不改详情抽屉的数据字段来源
- 不新增更多筛选项
- 不顺手实现真正的列设置能力

原因很简单：这次是页面标准统一，不是订单模块功能扩展。

### 10. TDesign 组件使用约束

本页继续基于现有 TDesign 组件实现，涉及组件包括：

- `t-tabs`
- `t-button`
- `t-table`
- `t-tag`
- `t-empty`
- `t-drawer`
- `t-pagination`

约束：

- 沿用现有组件，不自行造列表和标签轮子
- 表格仍由 `t-table` 承担排序、勾选、分页联动
- 移动端卡片是页面模板重组，不替换为新的第三方组件方案

## 验证方案

### 1. 桌面端验证

- 筛选区、工具栏、摘要、表格上下节奏与 `TaskList.vue` 是否统一
- 查询、重置、展开/收起是否正常
- Tab 切换是否正确映射状态
- 订单号点击详情是否正常
- 批量删除、清空勾选、翻页后勾选过滤是否正常
- 空态与 loading 态是否正常

### 2. 移动端验证

- 是否正确切到卡片视图
- 卡片信息是否足够清楚，不出现字段挤压
- 详情、删除、勾选是否仍然顺手可用
- 摘要区和工具栏是否能正常换行堆叠
- 简单分页是否正常

### 3. 回归验证

- `同步 C5 订单` 权限与 loading 行为不变
- `删除` 权限与确认行为不变
- C5 详情抽屉数据是否正常展示
- 非 C5 订单仍然不支持详情查询

### 4. 静态验证

- 执行 `pnpm type-check`
- 如环境允许，再执行 `pnpm build`

## 规格自检

已完成以下自检并内联收敛：

- 无 `TODO`、待定项或占位描述
- 轻量摘要明确限定为“当前页数据”，避免和全局统计混淆
- 方案边界收敛在一个页面内，未扩散到接口和后端
- 桌面端与移动端的展示口径保持一致，没有互相矛盾
- 列设置能力明确保持现状，不在本次范围内
