# 2026-04-21 任务进度成功订单统计修复设计

## 目标
修复 C5 任务列表中“存在购买成功订单，但任务进度仍显示 0/N”的问题。

## 现状
- 任务列表进度展示使用 `successCount / buyCount`。
- 后端任务分页在 `BuffScanTaskServiceImpl` 中调用 `TradeOrderRecordMapperManager.countSuccessByTaskIds(...)` 聚合成功单数量。
- 当前聚合 SQL 仅统计 `trade_order_record.status = 1`。
- 订单记录页前端将 `1 / 10 / 200` 都视为成功态展示。

## 根因
任务进度统计口径与订单成功展示口径不一致。

当历史订单或同步订单在库中保留了 `10 / 200` 这类 C5 成功状态码时：
- 订单页会显示“购买成功”；
- 任务进度聚合不会计入；
- 自动完成相关统计也可能偏小。

## 方案对比
### 方案一：仅修复任务进度统计口径（采用）
将任务成功订单统计从“仅 `status = 1`”调整为“兼容统计 `1 / 10 / 200` 成功态”。

优点：
- 改动最小；
- 能直接修复当前问题；
- 不影响现有下单与同步主流程。

缺点：
- 属于对历史数据口径的兼容，不是彻底统一状态值。

### 方案二：统一所有写库入口为内部状态枚举
所有订单写库入口都只落内部状态值，另补历史数据清洗。

优点：长期一致性最好。

缺点：涉及链路更多，本次修复范围过大。

### 方案三：只改前端成功展示
取消前端对 `10 / 200` 的成功展示。

优点：改动最少。

缺点：无法解决任务进度统计错误，不采用。

## 本次实施范围
1. 调整 `TradeOrderRecordMapperManager.countSuccess(Long taskId)` 的成功态统计口径。
2. 调整 `TradeOrderRecordMapper.countSuccessByTaskIds(...)` 与对应 manager 的成功态统计口径。
3. 保持前端与其余业务流程不变。

## 不做事项
- 不修改订单列表前端展示口径。
- 不做历史订单数据迁移。
- 不全面改造 C5 订单状态归一化链路。

## 兼容性
- 对外接口字段不变；
- 仅修正 `successCount` 和基于成功数的自动完成判断；
- 对已正确使用 `status = 1` 的数据无副作用。

## 风险
如果库内存在把 `10 / 200` 用于非成功语义的脏数据，可能被一并计入成功。但按当前订单页展示口径和 C5 状态语义，这一风险可接受。
