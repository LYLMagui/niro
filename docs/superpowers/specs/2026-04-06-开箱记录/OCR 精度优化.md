# 开箱记录 OCR 精度优化设计

## 目标

在固定 1080p 模板截图场景下，收敛并稳定开箱记录 OCR 的 `price` 与 `wear` 识别链路。

本轮目标只有两个：

- `price`：只允许从左下角绿色胶囊 ROI 读取，消灭左侧列表、聊天卡片、拼接文本和整图 OCR 对价格的污染
- `wear`：继续只从底部黑色数字条 ROI 读取，尽量把结果稳定拉近截图中的完整小数值，优先争取 9 位及以上有效小数

同时保持：

- 前端接口不变
- Java `UnboxRecordOcrResultDTO` 字段结构不变
- Python `/ocr/recognize` 返回结构不变
- 不通过整图多轮 OCR 爆搜换精度

## 范围

本次设计只覆盖现有固定模板 OCR 链路内部的 `price` / `wear` 精度优化，不扩展为通用 OCR 平台。

涉及文件：

- `ocr_demo/service.py`
- `ocr_demo/parser.py`
- `ocr_demo/ocr_client.py`
- `ocr_demo/app.py`
- `niro-server/niro-web/src/main/java/com/niro/web/service/impl/UnboxRecordOcrServiceImpl.java`

不在本次范围内的内容：

- 前端协议调整
- Java 侧图像处理
- 数据库或缓存改造
- `name` / `exterior` 的大幅重写

`name` 与 `exterior` 只要求不因本次优化而回退；本轮实现重点只放在 `price` 与 `wear`。

## 设计背景

当前问题已经收敛得很明确：

### 1. price 的真实问题不是“识别次数不够”，而是“脏来源太多”

现有链路里，价格存在被以下来源污染的风险：

- 左侧聊天列表
- 聊天卡片文本
- `target_card`
- `stitched_fields`
- 整图 OCR 或宽 ROI 结果
- 其他 fallback 文本

这会把不相关金额甚至噪声数字带入竞争，出现把错误价格当成结果的情况。对固定模板截图来说，这种“多来源竞争”不是增强鲁棒性，而是在放大噪声。

### 2. wear 的真实问题不是“再加更多 OCR 组合”，而是“ROI 还不够贴、候选排序还不够狠”

磨损数字条很细，当前误差主要来自：

- ROI 还偏宽，混入多余像素和噪声
- 候选选择过于依赖“位数多就赢”这类粗规则
- 主候选和邻近候选的优先级不够清晰

结果就是会出现尾数漂移，例如本应接近 `0.055003539`，却被识别成尾数错误的值。

## 核心判断

这个问题值得做，而且正确方向已经定了：

- 这是固定 1080p 模板截图，不是通用视觉场景
- 目标是稳定命中，不是泛化到任意页面
- 所以应当把来源砍干净、把 ROI 收窄、把字段解析专用化

也就是说：

- `price` 必须改成单来源字段
- `wear` 必须继续固定黑条 ROI，但把 ROI 与候选排序进一步收紧

## 总体方案

Python 识别链路继续按字段分治，但本轮只对 `price` 与 `wear` 做收敛式改造：

- `price`：严格单来源，唯一合法来源是左下角绿色胶囊 ROI
- `wear`：继续固定底部黑色数字条 ROI，收窄主 ROI，并允许极少量邻近微偏移候选
- `name`：保持现有逻辑，不作为本轮主优化目标
- `exterior`：保持现有逻辑，不作为本轮主优化目标

总体调用链保持不变：

```text
Frontend -> Java /unbox/record/ocr -> Python /ocr/recognize -> Java -> Frontend
```

Java 继续只负责上传接收、图片二进制转发、响应结构解析和接口日志，不承担图像增强逻辑。主要优化发生在 Python OCR 服务内部。

## 字段级设计

### 1. price：改成严格单来源字段

#### 1.1 合法来源

`price` 的唯一合法来源：

- 左下角绿色胶囊 ROI

禁止参与 `price` 竞争或兜底的来源：

- 左侧聊天列表
- 聊天卡片
- `target_card`
- `stitched_fields`
- 整图 OCR
- 任意非绿色胶囊 fallback 区域

也就是说，`price` 不再做跨区域竞争。只要不来自绿色胶囊，就算识别出金额，也没有资格成为 `price` 结果。

#### 1.2 ROI 内部识别策略

绿色胶囊 ROI 内部允许 3~5 组轻量增强候选，用于对抗字符细、局部糊、轻微缺符号的问题，但这些候选都必须来自同一块绿色胶囊区域。

可选增强方向：

- gray
- 2x / 3x 放大
- contrast
- sharpen
- 轻量 binary（仅在 ROI 内部尝试，不扩散到其他区域）

这里的关键不是“多做几次 OCR”，而是“在唯一合法来源内做有限增强”。

#### 1.3 结构化金额解析

`price` 不再按“任意金额正则命中”来决定结果，而是按绿色胶囊的结构解析：

1. 优先识别 `接受报价` 这类胶囊锚点文本
2. 再在同一 ROI 内找与该锚点同一胶囊内的金额
3. 金额优先匹配 `¥4.91` 这类形式
4. 允许有限修正：
   - 缺少 `¥`
   - `¥` 与数字粘连
   - 小数点附近的轻微 OCR 脏读

但修正必须是有限且结构化的，不能退化成“看到像金额的都收”。

#### 1.4 失败策略

如果绿色胶囊 ROI 最终没有解析出合法金额：

```json
price = null
```

这里不允许再从任何其他区域兜底。宁可 `null`，也不要把脏价格抬进结果。

### 2. wear：继续固定黑条 ROI，但把候选收紧

#### 2.1 ROI 设计

`wear` 继续只看底部黑色数字条固定 ROI。

在现有基础上做两步收紧：

- 主 ROI 再收窄，更贴近数字条本体
- 允许 1~2 个邻近微偏移 ROI，处理轻微裁切偏差

这些邻近候选仍然属于同一块底部数字条区域，不属于宽范围 fallback，更不允许回退到 stitched panel 或整图文本竞争。

#### 2.2 预处理策略

主候选继续使用对细数字更友好的轻量增强，优先保边缘，不走重型二值化爆搜。

主路径优先组合：

- gray
- 3x / 4x 放大
- contrast
- sharpen

必要时允许极少量邻近候选使用轻量 binary，但只在数字条邻近 ROI 内部使用。

#### 2.3 候选选择规则

`wear` 候选排序不再由“位数多就赢”主导，而是改成更强的字段约束排序。

优先级从高到低：

1. 合法 `0.xxxxxxxxx` 形式
2. 更贴近底部数字条字符形态和间距
3. `primary` 主 ROI 结果优先
4. 小数位足够长的结果优先，目标 9~12 位
5. OCR 置信度更高的结果优先

这意味着：

- 只有位数多但明显不像数字条输出的结果，不能压过主 ROI 合法结果
- 缺失 `0.`、位数太短或尾数明显漂移的结果，只能算低质量候选

#### 2.4 合法性约束

`wear` 继续保持强约束：

- `0 < wear < 1`
- 优先接受 `0.xxxxxxxxx` 这类完整格式
- 小数位 9~12 位为高质量目标
- 位数明显不足、格式残缺或形态异常的结果视为低质量

#### 2.5 失败策略

如果主 ROI 与邻近微偏移 ROI 都没有得到合法高质量结果，则：

```json
wear = null
```

不再让 stitched panel、整图 OCR 或宽区域脏文本与黑条 ROI 争夺最终 `wear`。

### 3. name 与 exterior

本轮不重写 `name` 与 `exterior`。

要求只有两条：

- 不因本次 `price` / `wear` 收敛而回退
- 保持现有返回结构和业务兼容性

## 性能与回退策略

### 1. 主链路

正常请求下的主路径：

- `price`：绿色胶囊 ROI 内部轻量增强 + 结构化金额解析
- `wear`：底部黑条主 ROI 识别
- `name`：沿用现有逻辑
- `exterior`：沿用现有逻辑

### 2. fallback 的边界

本次仍然允许 fallback，但 fallback 必须被收在字段内部：

#### price fallback

只允许：

- 同一绿色胶囊 ROI 内的有限增强组合
- 同一绿色胶囊 ROI 内的结构化纠错

不允许：

- 切到其他 ROI
- 引入 stitched panel
- 引入整图 OCR
- 引入聊天列表或聊天卡片金额竞争

#### wear fallback

只允许：

- 1~2 个邻近微偏移 ROI
- 极少量数字条专用轻量预处理变化

不允许：

- 扩展成大范围 region/scale/preprocess 穷举
- 回退到 stitched panel 主导最终结果
- 整图 OCR 参与 `wear` 决策

### 3. 耗时控制

目标仍然是保持当前量级，不把本次优化变成性能回退：

- `price`：限定在单 ROI 内做有限组合
- `wear`：限定在主 ROI + 少量邻近 ROI 内做有限识别
- 不做整图多轮爆搜
- 不增加新的远程服务或复杂图像管线

## 模块职责调整

### `ocr_demo/service.py`

这是本次主改文件，负责：

- 收紧 `price` 与 `wear` 的 ROI 定义
- 改写 `price` 解析来源限制
- 调整 `wear` 主候选与邻近候选的调度逻辑
- 输出更清晰的字段级元信息和日志

### `ocr_demo/parser.py`

负责：

- 实现绿色胶囊金额的结构化解析
- 收紧 `wear` 候选排序规则
- 保持字段级合法性校验清晰可控

### `ocr_demo/ocr_client.py`

负责提供必要的轻量预处理能力，例如：

- gray
- contrast
- sharpen
- upscale
- 必要时有限 binary

它仍然只承担 ROI 图像预处理和单次 OCR，不演化成复杂图像处理框架。

### `ocr_demo/app.py`

不改接口协议，只补充必要日志。

### `UnboxRecordOcrServiceImpl.java`

Java 侧继续只负责：

- 图片转发
- 响应解析
- 调用日志

不把图像增强、ROI 选择或结构化 OCR 逻辑挪到 Java 层。

## 兼容性

本次优化不改变外部协议。

Python 成功响应仍然返回：

```json
{
  "name": "P2000 | 红翼",
  "price": 4.91,
  "wear": 0.055003539,
  "exterior": 0
}
```

兼容性要求：

- `UnboxRecordOcrResultDTO` 字段保持不变
- 前端调用方式保持不变
- 字段识别失败时返回 `null`，不导致整次请求失败

## 风险与控制

### 风险 1：绿色胶囊 ROI 过严，导致价格识别不到

**控制：** 允许在同一 ROI 内做 3~5 组轻量增强和有限结构纠错，但不放开来源边界。

### 风险 2：price 识别不到后返回 `null` 的比例上升

**控制：** 接受这个代价，因为当前目标是宁可缺失，也不要把脏价格抬成结果。固定模板场景下，这个取舍是合理的。

### 风险 3：wear 主 ROI 过窄切掉首尾字符

**控制：** 保留 1~2 个邻近微偏移 ROI，只修正轻微裁切问题，不扩展成宽区域 fallback。

### 风险 4：候选排序写成拍脑袋补丁

**控制：** 排序规则只围绕字段本质约束：合法格式、数字条形态、主 ROI 优先、位数充足、置信度更高。避免堆无边界特判。

### 风险 5：性能被额外识别组合拖慢

**控制：** 严格限制组合数量，只在字段内部做小规模尝试，不允许整图扩散。

## 验收标准

### 功能验收

- `price` 只来自左下角绿色胶囊 ROI
- 非绿色胶囊来源不再参与 `price` 竞争
- 绿色胶囊无法识别合法金额时，`price = null`
- `wear` 只来自底部黑条 ROI 及其极少量邻近微偏移候选
- `wear` 候选排序更稳定，尽量贴近截图中的完整小数值
- `name` 与 `exterior` 不低于当前实现

### 稳定性验收

- 单字段失败返回 `null`，不导致整次请求失败
- 非法图片、空文件、错误响应仍走既有错误路径
- Java 与前端接口保持兼容

### 性能验收

- 常规请求耗时继续保持在当前量级
- 不因新增大范围 fallback 导致明显超时

## 验证方式

1. 使用固定 1080p 模板样例图做回归测试
2. 重点核对 `price` 与 `wear`：
   - `price` 是否只取自绿色胶囊
   - `wear` 是否更接近目标值，例如 `0.055003539`
3. 检查 `name` 与 `exterior` 没有明显回退
4. 记录字段级日志、候选来源和总耗时
5. 验证空文件、非法图片和 OCR 服务异常路径

## 实施顺序

建议按以下顺序实施：

1. 收紧 `price` 来源，只保留绿色胶囊 ROI
2. 实现绿色胶囊金额的结构化解析
3. 收紧 `wear` 主 ROI 与邻近微偏移候选
4. 调整 `wear` 候选排序规则
5. 回归确认 `name`、`exterior` 与整体耗时未回退

## 结论

这次优化不是再给 OCR 加更多全局尝试，而是利用固定模板前提，把 `price` 和 `wear` 彻底收敛成字段专用路径。

一句话总结就是：

- `price` 只认绿色胶囊，并做结构化金额解析；识别不到就 `null`
- `wear` 继续固定黑条 ROI，但把 ROI 微调和候选规则收紧到更贴近真实数字条输出

这符合当前业务的真实问题，也符合“保持接口不变、修改聚焦、避免过度设计”的目标。
