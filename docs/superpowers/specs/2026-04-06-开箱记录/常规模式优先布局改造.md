# UnboxRecord 新增批次弹窗常规模式优先布局改造设计

日期：2026-04-12  
文件：`niro-client/src/views/UnboxRecord.vue`

## 1. 目标

将“新增批次 / 编辑批次”弹窗从“统计信息与结果列挤压录入区”的结构，调整为“常规 modal 优先、录入为主、结果侧置”的布局。

核心目标：

- 常规 modal 作为桌面端主形态，全屏只作为扩展态
- 表格只承担批量录入，不再承担利润结果展示
- 利润、手续费、当前行结果移到右侧辅助侧栏
- 说明文案从常驻文本改为问号悬浮提示，减少噪音
- 保持现有业务逻辑、数据结构、保存链路和移动端双形态不变

## 2. 范围

本次只调整 `UnboxRecord.vue` 中批次编辑器弹窗的信息架构和布局组织：

- 桌面端 modal 下的编辑器壳层尺寸与区块划分
- 顶部标题区、基础信息区、明细工具条、明细表格、右侧辅助栏
- 桌面端表格列展示策略
- 说明文案的展示方式
- 常规 modal 与全屏态的布局优先级

不包含：

- 新增业务字段
- 修改保存逻辑、计算逻辑、接口调用逻辑
- 调整移动端卡片编辑的业务语义
- 改造为新的弹窗组件
- 无关页面美化或全局样式重构

## 3. 现状问题

当前弹窗的主要问题不是字段不够，而是信息层级错误：

1. 表头语义混杂：录入列、结果列、强调列混在一起，扫描成本高
2. 结果列过重：`实际购入价`、`参考净利润`、`净利润` 等结果型内容占用列宽，压缩真正的录入列
3. 常驻说明抢视线：诸如“买入价 × 折扣”“优先录这里”的文案长期挂在页面上，占空间且打断录入节奏
4. 弹窗主形态偏向工作台：对常规使用场景来说过重，不符合用户最常用的非全屏录入方式

## 4. 设计原则

1. **录入优先**：打开弹窗后第一任务是录头信息和明细，不是看统计卡
2. **结果后置**：利润、手续费、当前行分析都属于辅助判断，不应占用主表格列宽
3. **常规 modal 优先**：桌面端先把普通弹窗做好，全屏只是扩展态，不单独设计另一套信息结构
4. **减噪**：能用悬浮提示解决的说明，不常驻页面
5. **零业务破坏**：不动 `draftBatch`、计算来源、保存行为和现有状态切换语义

## 5. 方案比较

### 方案 A：保留现有表格结构，只压缩样式

做法：

- 保留利润列和结果列
- 只通过调列宽、改字体、减小 padding 缓解拥挤

优点：

- 改动最小

缺点：

- 根因不变
- 表格仍然同时承担录入和结果展示
- 列宽冲突只会缓解，不会真正消失

### 方案 B：表格只录入，右侧侧栏承接结果信息（推荐）

做法：

- 表格保留输入字段和必要只读字段
- 利润、手续费、选中行结果统一放到右侧侧栏
- 批次总览也放入右侧，形成“录入主区 + 结果辅区”

优点：

- 根因处理正确
- 录入区更稳定，结果区更集中
- 最符合用户已经确认的 HTML 原型方向

缺点：

- 需要重排弹窗主体结构
- 需要处理桌面端不同宽度下的侧栏比例

### 方案 C：顶部做轻量 summary strip，取消右侧侧栏

做法：

- 表格去掉利润列
- 结果信息压缩到工具条或顶部摘要条

优点：

- 布局更简单

缺点：

- 当前选中行的明细结果没有稳定容器
- 汇总和单行结果会继续争抢顶部空间
- 不如侧栏方案清晰

## 6. 最终决策

采用 **方案 B：表格只录入，右侧侧栏承接结果信息**。

原因：

- 这是唯一真正消除表格宽度失控的方法
- 与用户已确认的静态原型一致
- 能在不改业务逻辑的前提下重建清晰的信息层级
- 最适合“常规弹窗优先”的使用方式

## 7. 具体设计

### 7.1 弹窗主形态

桌面端主形态定义为常规 modal：

- 非全屏时使用收敛后的弹窗尺寸作为默认体验
- 全屏按钮保留，但全屏只放大容器，不改变区块顺序
- 两种模式共享同一套内容结构：头部 → 基础信息 → 明细表格 → 右侧侧栏

这意味着全屏不是另一套页面，只是当前 modal 的放大版本。

### 7.2 顶部结构

顶部保留轻量标题栏：

- 左侧：标题、批次标签、当前明细数
- 右侧：全屏/缩小、取消、保存批次、关闭

约束：

- 顶部仍然是主要操作区
- 不在顶部堆放说明文案和大块统计
- 标题区只承担身份识别和主操作，不承担结果展示

### 7.3 基础信息区

基础信息区保留现有字段，但压缩表达方式：

- 第一层主字段：批次名称、开箱日期、箱子类型、默认折扣
- 第二层补充字段：备注等
- 区块默认保持紧凑，展开只是补充录入，不改变主体结构

约束：

- 不调整字段业务含义
- 不把“总利润”“待录数量”等统计重新塞回基础信息区

### 7.4 主体结构

桌面端主体使用双栏：

- 左侧主区：基础信息 + 明细工具条 + 明细表格
- 右侧辅区：批次总览 + 当前选中明细 + 字段说明

优先级：

- 左侧是主舞台，承担输入
- 右侧是辅助舞台，承担结果判断

侧栏目标宽度按已确认原型控制在约 `280px` 左右，保证它是辅助区而不是第二主区。

### 7.5 表格列策略

桌面端表格只保留录入相关字段：

- `#`
- `阶段`
- `饰品名称`
- `游戏买入价`
- `折扣`
- `实际购入价`
- `平台参考卖价`
- `平台卖出价`
- `备注`
- `操作`

处理原则：

- `实际购入价` 保留，但只作为紧凑的只读结果列
- 不再在表格中展示 `参考净利润`、`净利润` 这种结果型重列
- 不再在单元格内使用高存在感的结果卡片式布局
- 表格回归为录入工作表

### 7.6 右侧侧栏内容

右侧侧栏拆成三个区块：

1. **批次总览**
   - 当前净利润
   - 总成本
   - 总手续费
   - 待录卖出价条数
   - 已结算进度
   - 参考净利润

2. **当前选中明细**
   - 游戏买入价
   - 折扣
   - 实际购入价
   - 平台参考卖价
   - 平台卖出价
   - 手续费
   - 净利润

3. **字段说明**
   - 保留低频说明作为兜底帮助区
   - 不再与主录入区争抢空间

### 7.7 说明文案策略

说明文案改成“悬浮触发 + 侧栏兜底”：

- 表头或字段标签旁增加问号图标
- Hover 时展示 tooltip
- 页面中不再长期保留大段说明性副文案
- 只有少量关键说明保留在右侧“字段说明”块中

适用对象：

- `实际购入价`
- `平台参考卖价`
- `平台卖出价`
- `默认折扣`

### 7.8 全屏兼容策略

全屏态下：

- 沿用同一套结构
- 只扩大容器可用空间
- 可适当放宽主区与侧栏比例，但不改变结果侧置的基本原则

禁止做法：

- 全屏态恢复利润列进表格
- 全屏态再做一套与常规 modal 完全不同的布局逻辑

## 8. 兼容性要求

以下内容必须保持不变：

- `draftBatch` 数据结构
- `draftSummary`、`draftSummaryCards`、各类 metrics 的计算来源
- `saveDraftBatch` 行为
- `handleAddRow`、`handleBulkAdd`、`applyDefaultsToEmptyRows`、`mockQueryC5Price` 行为
- `purchaseState` 切换语义
- 桌面端表格 / 移动端卡片双形态入口
- 现有全屏开关语义

允许调整的是：

- 区块位置
- 列展示内容
- 样式强弱
- 文案展示方式
- 桌面端录入与结果的空间分配

## 9. 风险与控制

### 风险 1：侧栏过宽，反向挤压表格

控制：

- 侧栏固定在辅助宽度，不做与主区对半分
- 优先保证表格最小可读宽度

### 风险 2：结果从表格移出后，用户短期不适应

控制：

- 保留“当前选中明细”区，确保点中一行就能看到对应结果
- 在表格中保留 `实际购入价` 这个关键只读值，减少跳跃感

### 风险 3：说明文案隐藏后，用户找不到规则

控制：

- 关键字段一律保留问号 tooltip
- 右侧保留简短字段说明块作为兜底

### 风险 4：全屏/缩小两态出现分叉维护

控制：

- 两态共享一套 DOM 结构和信息顺序
- 只调容器尺寸和局部比例，不分叉逻辑

## 10. 验证标准

改造完成后，满足以下结果即视为达标：

1. 常规 modal 下，表头和录入列不再因利润列被挤压
2. 用户打开弹窗后，视线先落在头信息和明细录入，而不是统计卡
3. 结果信息能在右侧连续查看，不需要在表格横向扫多个结果列
4. 说明文案明显减噪，但关键规则仍可通过 tooltip 快速查看
5. 全屏态只是空间扩展，不是另一套结构
6. 不破坏现有保存、计算、状态切换和移动端展示逻辑

## 11. 实现边界

本次实现应优先落在以下区域：

- 编辑器桌面端外层容器结构
- 桌面端 `draftTableColumns` 的列精简
- 表格 slot 中结果型内容的迁移
- 右侧 summary / 当前选中明细区域的重组
- tooltip 化说明文案

不应在本轮顺手做：

- 业务计算重写
- 移动端卡片大改
- 新增复杂筛选、排序、聚合分析能力
- 对其他页面复制这套布局

## 12. 当前结论

这次不是“美化一下弹窗”，而是把弹窗恢复成正确的数据职责分工：

- 表格负责录入
- 侧栏负责结果
- tooltip 负责说明
- modal 负责日常主场景
- fullscreen 只是扩展态
