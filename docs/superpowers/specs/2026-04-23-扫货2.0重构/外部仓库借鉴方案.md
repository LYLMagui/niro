# 扫货 2.0 外部仓库借鉴方案

日期：2026-04-24  
范围：基于 `docs/external-repos/` 下外部仓库的扫货相关实现，补充扫货 2.0 的可借鉴设计  
当前状态：分析已完成，可作为实现阶段的参考文档

## 1. 目标

这份文档不改动《扫货 2.0 重构设计》里已经确认的边界，只回答一个问题：

外部仓库在“启动停止、防超买、实时进度、执行流水线”这四件事上，哪些做法值得借鉴，哪些不值得借鉴。

本次分析样本：

- `docs/external-repos/csgo-market-sniper`
- `docs/external-repos/SCMBot`
- `docs/external-repos/node-csgo-web-tradebot`

## 2. 样本结论总览

### 2.1 `csgo-market-sniper`

优点：

- 扫描链路很直，结构是“拉候选 -> 条件过滤 -> 下单”。
- 配置模型简单，适合作为单任务单商品执行模型的参考。
- 如果候选结果天然按价格升序排列，那么一旦价格超过阈值就可以提前结束当前批次扫描。

缺点：

- 启停能力几乎等于没有，启动靠脚本运行，停止靠杀进程。
- 防超买只有余额与单价判断，没有名额预占、幂等键、已购去重。
- 进度只在终端打印，无法支撑服务端任务运行态展示。

结论：

- 适合借鉴“直线执行流水线”。
- 不适合借鉴“任务控制”和“防超买”。

### 2.2 `SCMBot`

优点：

- 运行模型比脚本型仓库成熟，扫描任务挂在可取消 worker 上。
- 停止不是直接杀进程，而是发取消信号，让线程在等待点和循环点收尾退出。
- 有统一的状态消息回推机制，适合借鉴运行态更新方式。
- 有被限流后的暂停/恢复思路，可以转成账号维度冷却机制。

缺点：

- 仍然缺少强幂等设计，重复买入和预算判断并不牢靠。
- 状态与 UI 绑定较重，桌面应用结构不适合直接照搬到服务端。
- 多线程共享状态较多，容易把实现带回复杂分支。

结论：

- 适合借鉴“可取消执行单元”“统一状态总线”“账号冷却”。
- 不适合借鉴“状态与界面耦合”“弱幂等并发模型”。

### 2.3 `node-csgo-web-tradebot`

优点：

- 服务端事件推送模型清晰，适合借鉴实时状态更新方式。
- 前端先禁用按钮，后端再做二次校验，适合借鉴启停按钮的交互幂等。
- 事件流天然适合把“任务汇总”和“最近运行态”拆开处理。

缺点：

- 这不是扫货仓库，核心域是交易站，不是市场扫货。
- 没有任务调度与持续扫描模型。
- 防重复提交只做到轻量级，没有真正的任务级幂等与调度保护。

结论：

- 适合借鉴“实时事件推送模型”。
- 不适合借鉴“扫货执行逻辑”。

## 3. 对扫货 2.0 的借鉴结论

## 3.1 启动 / 停止

最值得借鉴的是 `SCMBot` 的思路：任务必须是可取消的执行单元，而不是一个只能靠进程级杀死的死循环。

对扫货 2.0 的落地建议：

1. 调度层只负责挑选任务并占用账号并发槽位，不直接处理扫描细节。
2. 执行层为每个运行实例持有独立的 `stopRequested` 标记。
3. 所有循环点、等待点、重试点、限流冷却点都必须检查 `stopRequested`。
4. 手动停用任务时，不要求立刻中断线程，而是进入“请求停止 -> 当前小轮次收尾 -> 实例结束”的路径。
5. 任务的长期状态仍保持既有设计；如果不想扩充数据库状态枚举，就不要新增长期 `STOPPING`，只在内存执行态里保留停止请求标记。

应该借鉴的点：

- 可取消执行单元
- 停止信号可穿透等待点
- 账号维度独立冷却与恢复

不应该借鉴的点：

- 用线程和界面事件直接耦合任务状态
- 用进程退出代替任务停止

## 3.2 防超买

这部分不应该直接借鉴外部仓库；外部仓库暴露出来的最大共同问题，就是把“余额够不够”和“单价是否符合”误当成了防超买。

扫货 2.0 应坚持当前已确认方案，并做以下强化：

1. `BUY_COUNT` 模式继续使用“购买名额预占”。
2. 可购买余量统一按 `target_buy_count - success_buy_count - reserved_buy_count` 计算，不允许直接按目标数量减成功数。
3. 命中后先尝试预占名额，预占成功后才能创建下单尝试。
4. 每个下单尝试必须绑定稳定唯一键，推荐继续使用 `account_id + listing_id`。
5. 回调只能更新既有尝试记录，不能创建第二条尝试记录。
6. 下单失败、超时回收、确认跳过时必须回补预占名额；下单成功时将预占名额转为成功数。
7. 账号维度应增加“在途下单数”约束，避免余额尚未回写时同账号短时间并发命中过多。
8. 同一批扫描结果要先做内存短期去重，再做数据库唯一约束兜底。

应该借鉴的不是它们的方案，而是它们的问题：

- 不能只看余额
- 不能只看单价阈值
- 不能在下单成功后才回头统计名额
- 不能没有 listing 级唯一约束

## 3.3 实时更新进度

最值得借鉴的是 `node-csgo-web-tradebot` 的事件推送模型：服务端主动推送状态变化，前端订阅运行态，而不是所有信息都靠页面轮询拼装。

对扫货 2.0 的落地建议：

1. 任务列表继续以任务表的汇总字段为准，保证页面首屏稳定。
2. 运行中的实时状态通过事件流推送，不把实时进度硬塞进任务定义接口。
3. 事件流至少覆盖以下几类事件：
   - 任务状态变化
   - 运行实例启动/结束
   - 命中计数更新
   - 下单尝试结果更新
   - 最近错误更新
   - 停止原因确认
4. 首版即使不做复杂事件体系，也应至少支持“任务状态 + 关键计数 + 最近错误 + 最近一次命中/下单”的实时推送。
5. 前端启停按钮要做一次前端禁用，后端仍按状态机做二次校验，避免重复点击造成重复请求。

推荐展示口径：

- 任务汇总：`task_status`、`success_buy_count`、`reserved_buy_count`、`hit_count`、`last_error_message`
- 最近运行：`run_status`、`started_at`、`finished_at`、`buy_attempt_count`、`buy_success_count`、`stop_reason`
- 运行中增量：最近命中、最近下单尝试、最近错误、最近心跳

## 3.4 执行流水线

最值得借鉴的是 `csgo-market-sniper` 那种直线型执行链路。扫货 2.0 不应该把调度、命中判断、下单、回调、状态汇总揉在一个大方法里，而应该维持单向流水线。

推荐执行顺序：

1. 调度器为账号分配并发槽位
2. 选出待运行任务并创建运行实例
3. 拉取一批候选 listing
4. 做内存短期去重
5. 做价格与磨损过滤
6. 判断停止条件是否已满足
7. 预占购买名额
8. 记录命中明细
9. 创建下单尝试记录
10. 发起下单
11. 根据结果更新尝试记录与任务汇总
12. 判断是否继续下一轮扫描或结束实例

其中可以吸收的优化点：

- 如果外部平台返回结果已经按价格升序排列，则超过 `maxPrice` 后可以提前结束当前批次扫描，避免无效遍历。
- 命中判断与下单发起必须拆开，前者是纯筛选，后者是有副作用动作。
- 所有“是否继续执行”的判断都应落在统一出口，而不是散落在多层分支里。

## 4. 建议直接纳入扫货 2.0 的实现原则

建议实现阶段直接采纳以下原则：

1. 启停控制采用“任务级可取消执行单元”，不允许脚本式死循环。
2. 防超买继续以“名额预占 + listing 唯一约束 + 回调只更新既有记录”为核心。
3. 实时进度采用“任务汇总读表，运行态事件推送”的双通道模型。
4. 执行逻辑采用“调度 -> 过滤 -> 预占 -> 尝试 -> 收尾”的直线流水线。
5. 账号维度增加冷却时间与在途下单限制，避免限流和短时间并发打爆。
6. 前端启停按钮只做交互幂等，真正的状态正确性仍由后端保证。

## 5. 不建议借鉴的做法

1. 用进程退出或脚本中断代替任务停止。
2. 只靠余额判断来防超买。
3. 没有 listing 级唯一键就直接发起下单。
4. 把运行状态完全绑在 UI 控件或终端输出上。
5. 把调度、扫描、命中、下单、回调、汇总全部堆进一个服务或一个大循环。

## 6. 结论

对扫货 2.0 最合理的吸收方式不是复刻某个外部仓库，而是组合各自最有价值的部分：

- 启停控制借鉴 `SCMBot`
- 实时进度借鉴 `node-csgo-web-tradebot`
- 执行流水线借鉴 `csgo-market-sniper`
- 防超买坚持扫货 2.0 既定方案，并在账号在途约束和回收路径上进一步补强

实现阶段应避免“外部仓库里有什么就抄什么”，而应只吸收那些能降低复杂度、提高可控性、且不破坏扫货 2.0 已确认边界的设计。
