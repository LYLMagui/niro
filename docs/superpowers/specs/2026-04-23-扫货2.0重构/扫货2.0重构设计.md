# 扫货 2.0 重构设计

日期：2026-04-23  
最近更新：2026-05-09  
范围：C5 扫货任务域 2.0 的表结构、接口、前后端实现、调度、运行状态、命中记录、下单幂等与待优化项  
当前状态：核心功能已落地到可运行首版；表结构、后端 CRUD、命中/下单明细、SSE 运行态推送和前端页面订阅刷新已存在；账号归属校验、attempt 级 `out_trade_no`、预占归属、可取消停用、在途金额扣减、保守启动恢复、前端 C5 账号选择器、账号级在途下单数限制、账号短冷却，以及长期 INIT attempt 的超时核验和终态补偿已补齐。2026-05-09 确认运行模型切换为单实例持续运行：任务启用后直接 `RUNNING` 并由本进程循环扫描，run 实例表、`READY` 循环调度、`nextScanAt` 与跨实例 lease 退出核心链路。

## 1. 目标

本次重构在保留旧扫货代码的前提下，建立一套新的 C5 扫货 2.0 任务域。目标不是继续在旧 `BuffScanTask` 链路上叠补丁，而是把任务定义、运行实例、命中明细、下单尝试和调度执行拆开，降低旧模型中“定义、运行态、平台差异、调度状态混在一起”的复杂度。

2.0 的核心目标：

1. 任务定义与运行实例解耦。
2. 命中记录与下单尝试拆表，避免副作用动作和筛选结果混在一起。
3. C5 首版只围绕价格与磨损判断命中。
4. BUY_COUNT 模式必须具备购买名额预占，避免并发命中导致超买。
5. 下单尝试使用数据库唯一约束兜底，避免同账号同平台 listing 重复下单。
6. 旧扫货源码保留，但不作为 2.0 的任务运行入口。

## 3. 已确认边界

1. 首版只做 C5，不做 BUFF 或多平台统一运行。
2. 2.0 只重建任务域，复用用户、C5 账号、CS2 商品、订单主数据与底层 C5 SDK。
3. 数据库会清空初始化，不需要兼容旧 1.0 运行态数据。
4. 每个任务只针对一个商品，每个任务固定绑定一个账号。
5. 一个账号可绑定多个任务，账号并发上限由账号运行态配置控制，默认值为 5。
6. 同账号同商品允许存在多个任务和多个 `READY` 任务，但同一时刻最多 1 个任务进入 `RUNNING`。
7. 首版只保留单轮占槽持续扫描，不保留旧版定时、运行时长、休眠周期模式。
8. 停止条件支持按购买数量停止，或按余额停止。
9. 余额停止支持两种口径：余额低于 `maxPrice`，或余额低于 `reserveBalance`。
10. 命中条件只支持价格与磨损，不支持 phase / pattern / sticker。
11. 扫描结果只记录命中明细与下单尝试明细，不保存全量扫描快照。
12. 异常采用连续错误计数；当前实现连续异常达到 3 次后进入 ERROR。
13. 人工介入只支持任务级启停，不开放运行实例级操作。
14. 前端列表展示任务汇总和最近一次运行信息，并通过 SSE 订阅运行态事件后自动刷新。
15. 任务创建默认为 `DRAFT`，手动启用后进入 `READY`。
16. C5 扫货 2.0 不再读取用户全局 C5 AppKey 与 Steam 交易链接；每个 C5 扫货账号单独保存 `c5AppKey` 与 `steamTradeUrl`，账号检测和下单请求均以绑定账号配置为准。

## 6. 接口设计

2.0 接口全部走独立 v2 前缀：

`/api/c5/sniping/v2/tasks`

当前后端 Controller 已落地以下接口：

1. `POST /api/c5/sniping/v2/tasks`  
   创建任务，默认 `DRAFT`。

2. `PUT /api/c5/sniping/v2/tasks/{id}`  
   编辑任务；`RUNNING` 状态禁止修改。

3. `GET /api/c5/sniping/v2/tasks/{id}`  
   查询任务详情。

4. `GET /api/c5/sniping/v2/tasks`  
   分页查询任务列表，返回任务汇总和最近一次运行信息。

5. `POST /api/c5/sniping/v2/tasks/{id}/enable`  
   启用任务：`DRAFT / STOPPED / ERROR -> READY`。

6. `POST /api/c5/sniping/v2/tasks/{id}/disable`  
   停用任务：`READY` 直接进入 `STOPPED`；`RUNNING` 写入 `stopRequested`，由执行安全点收尾为 `STOPPED`。

7. `DELETE /api/c5/sniping/v2/tasks/{id}`  
   软删除任务；`RUNNING` 状态禁止删除。

8. `GET /api/c5/sniping/v2/tasks/{id}/hits`  
   查询命中明细。

9. `GET /api/c5/sniping/v2/tasks/{id}/buy-attempts`  
   查询下单尝试明细。

权限与登录：

- Controller 标注 `@SaCheckLogin`。
- 当前所有接口复用 `PermissionConstants.TASK_SCAN_LIST`。

## 7. 状态机与调度流程

### 7.0 最新运行模型：单实例持续运行

2026-05-09 确认当前部署为单实例，运行模型从“READY 单轮占槽 + run 实例”切换为“任务即运行主体”。任务启用后直接进入 `RUNNING`，本进程内循环按 `scanIntervalMs` 执行扫描；不再创建 `c5_sniping_task_run_v2` 运行实例，不再写入或展示 `nextScanAt`，不再使用 `lease_owner` / `lease_until` 做跨实例抢占。C5 网络异常、接口异常、维护或限流不再让任务自动进入 `ERROR`，只记录最近错误并继续重试。任务只在买够数量、余额保护触发、用户停用或删除时结束。

本次迁移会清理历史异常 `ERROR` run，移除任务表中的 `latest_run_id`、`next_scan_at`、`lease_owner`、`lease_until`，移除命中与下单尝试表中的 `run_id`，并删除历史 run 表。历史 `READY` 任务迁移为 `STOPPED`，避免上线后自动扫旧任务。


### 7.1 任务状态机

当前状态机：

`DRAFT -> READY -> RUNNING -> STOPPED / COMPLETED / ERROR`

状态含义：

- `DRAFT`：草稿，不参与调度。
- `READY`：已启用，等待调度器启动。
- `RUNNING`：已创建运行实例，正在执行当前单轮扫描。
- `STOPPED`：手动停用或启动恢复时收尾。
- `COMPLETED`：达到停止条件后自然结束。
- `ERROR`：连续异常超过阈值或启动失败。

当前实现采用“单轮执行占槽模型”：任务到期后短暂从 `READY` 进入 `RUNNING`，完成一轮扫描后如果未达到停止条件，则回到 `READY` 并写入 `nextScanAt`。该模型能避免同账号多任务长期占用账号槽位。

### 7.2 运行实例状态机

运行实例状态机：

`RUNNING -> STOPPED / COMPLETED / ERROR`

当前每次任务从 READY 被调度并成功进入 RUNNING 时，会创建一条运行实例。每个运行实例对应一次单轮扫描，单轮结束后由调度服务按执行结果收尾。

### 7.3 当前调度规则

当前 `C5SnipingTaskV2SchedulerServiceImpl` 的实际规则：

1. 服务启动后执行恢复逻辑。
2. 每 1000ms 扫描一次到期 READY 任务。
3. 只选择 `next_scan_at <= now()` 且 lease 为空或已过期的 READY 任务。
4. 按账号分组后先检查账号是否处于冷却期。
5. 统计当前账号 `RUNNING` 任务数，并读取账号运行态中的 `concurrencyLimit`，默认值为 5。
6. 有空槽时按优先级和下次扫描时间选择任务启动。
7. 本机通过 `localRunningTaskIds` 避免同一任务重复异步启动。
8. 异步启动时先抢占数据库 lease，再二次检查账号冷却。
9. 创建 run 后把任务 `READY -> RUNNING`，并校验 lease owner 与 lease 未过期。
10. 执行一轮 `executeOneCycle`。
11. 若达到停止条件或异常阈值，任务进入 `COMPLETED` / `ERROR` / `STOPPED`。
12. 若未停止且无停用请求，run 以 `SINGLE_CYCLE_FINISHED` 收尾，任务回到 `READY` 并按 `scanIntervalMs` 写入 `nextScanAt`。
13. 启动完成或异常后按 owner 清理 lease。

当前局限：

- 账号并发上限已有后端运行态配置，但暂未提供前端配置入口。
- 同优先级轮询仍依赖 `nextScanAt` 和更新时间，没有独立 `last_scheduled_at`。

### 7.4 当前启动恢复

服务启动时：

1. 查询 `READY / RUNNING` 的未删除任务。
2. 对 `RUNNING` 任务先处理未释放预占的 attempt。
3. 如果 attempt 关联的本地订单已有 C5 `orderId`，尝试通过 C5 订单详情刷新远端状态。
4. SUCCESS attempt 确认购买成功并释放预占；失败或取消 attempt 释放预占；仍处于 INIT 且未达到恢复阈值的 attempt 保守保留预占。
5. 如果任务已有 `stopRequested=true`，收尾 running run 后任务恢复为 `STOPPED`。
6. 否则收尾 running run 后任务恢复为 `READY`。
7. 若没有未结算 attempt，清理残留 `reserved_buy_count`。
8. `READY` 任务保持等待调度。

周期补偿策略：

1. 定时扫描已过期 INIT attempt，兼容历史 `init_expire_at` 为空且创建时间已超过兜底阈值的数据。
2. 有本地 C5 `orderId` 时先核验远端订单详情；远端成功或失败会把 attempt 收口到终态。
3. 无 `orderId`、远端仍非终态或核验失败时，先累计 `recovery_attempt_count` 并保留预占。
4. 达到最大恢复核验次数后，将 attempt 标记为 `INIT_TIMEOUT` 失败，并释放账号在途数和 BUY_COUNT 预占。
5. 定时扫描已终态但 `slot_reserved=true` 且 `slot_released=false` 的 attempt，事务化补偿释放或确认预占。

当前恢复策略剩余局限：

- C5 远端核验依赖本地订单已有 `orderId`。
- 暂不能直接按 `outTradeNo` 查询远端订单。
- INIT TTL 与最大恢复核验次数当前为代码常量。

## 8. 当前执行流水线

当前 `C5SnipingTaskV2ExecutionServiceImpl.executeOneCycle` 单轮执行流程：

1. 重新读取任务，确认任务状态未变化。
2. 如果是 `BALANCE_GUARD`，先查询 C5 余额，扣减同账号未释放 attempt 的在途金额后判断是否停止。
3. 查询启用状态的 CS2 商品，要求 `marketHashName` 非空。
4. 获取用户 C5 API Client。
5. 查询 C5 在售 listing：
   - 无磨损商品使用 `searchProductList`。
   - 有磨损商品使用 `productSearch`，并带 `wearMin` / `wearMax`。
   - 当前只查询第 1 页，每页 20 条。
6. 过滤：
   - `productId` 非空。
   - 价格不超过 `maxPrice`。
   - 磨损满足任务区间。
7. 按价格升序排序。
8. 使用本机内存 `accountId:productId` 做 60 秒短期去重。
9. 写入命中明细。
10. 尝试下单：
    - BUY_COUNT 模式先预占购买名额。
    - 在账号级 Redisson watchdog 锁内检查当前 INIT 在途下单数是否小于 `maxInFlightAttempts`。
    - 创建 `TradeOrderRecord`，状态为处理中。
    - 创建下单尝试记录，写入 `outTradeNo`、预占归属、在途金额和 `initExpireAt`。
    - 使用 `C5BatchBuyRequest` 发起单商品批量购买。
    - 根据 C5 返回的 `outTradeNo` 匹配成功或失败项。
    - 成功时更新订单、attempt、任务成功数和运行实例成功数，并通过 attempt 事务化结算预占。
    - C5 空响应、远端失败或下单接口异常时更新订单和 attempt，事务化释放预占，并写入账号短冷却。
    - 本地 attempt 初始化异常只收口 attempt 和释放预占，不写账号冷却。
11. 每个 listing 尝试后检查是否达到 BUY_COUNT 完成条件。
12. 本轮结束后更新任务命中数和运行实例命中数。
13. 连续异常达到 3 次后任务进入 ERROR。

## 9. 停止条件

### 9.1 BUY_COUNT

当 `success_buy_count >= target_buy_count` 时，任务进入 `COMPLETED`，run 进入 `COMPLETED`，停止原因为 `BUY_COUNT_REACHED`。

当前防超买实现：

1. 下单前调用 `reserveBuySlot`。
2. 只有 `success_buy_count + reserved_buy_count < target_buy_count` 时，才允许 `reserved_buy_count + 1`。
3. 如果 attempt 初始化失败、下单失败或异常，则释放预占。
4. 如果下单成功，则 `reserved_buy_count - 1` 且 `success_buy_count + 1`。
5. attempt 通过 `slot_reserved` / `slot_released` 记录是否持有预占以及是否已结算。
6. 释放或确认前先标记 attempt 已释放，避免重复释放或重复确认。

当前不足：

- INIT 超时 TTL 和最大恢复核验次数当前为代码常量，尚未产品化配置。

### 9.2 BALANCE_GUARD

当前每轮开始前查询 C5 余额，并扣减同账号未释放 attempt 的在途金额：

- `MAX_PRICE`：可用余额低于 `maxPrice` 时完成。
- `RESERVE_BALANCE`：可用余额低于 `reserveBalance` 时完成。

当前不足：

- 多任务并发下仍可能受 C5 余额延迟影响。
- 成功下单后不会立即再次查余额，而是在下一轮开始时判断。

## 10. 幂等与数据安全

### 10.1 短期内存去重

当前实现使用本机内存 `ConcurrentHashMap`：

- key：`accountId + ':' + productId`
- TTL：60 秒

用途：挡住同一实例短时间内的重复命中。

局限：

- 仅本机有效。
- 服务重启后丢失。
- 多实例部署下不共享。

### 10.2 数据库硬幂等

当前数据库唯一约束：

- `(account_id, listing_id)` 唯一。
- `idempotency_key` 唯一。

当前 `listing_id` 在 C5 首版中对应 `productId`。

幂等创建 attempt 时，如果触发唯一约束，则当前命中标记为 `SKIPPED_DUPLICATE`，如已预占名额则释放预占。

### 10.3 订单主数据复用

当前每次下单前创建 `TradeOrderRecord`，并使用其 `outTradeNo` 调用 C5 批量购买接口。

当前关联方式：

- `TradeOrderRecord.outTradeNo` 用于匹配 C5 成功/失败响应。
- `C5SnipingBuyAttemptV2.outTradeNo` 保存同一个外部流水号，支持 attempt 级定位。
- `C5SnipingBuyAttemptV2.orderRecordId` 关联订单记录。

后续优化方向：

- C5 订单同步或回调应优先按 `out_trade_no` 定位 attempt，再更新订单主数据。
- 如果 C5 后续提供按 `outTradeNo` 查询订单详情能力，应接入到启动恢复和订单同步链路。

## 12. 主要风险与缺陷

### 12.1 跨实例调度 lease 已补齐首版

当前单轮占槽调度已通过数据库 `lease_owner` / `lease_until` 避免多实例重复启动同一 READY 任务；实例内仍使用 `localRunningTaskIds` 防止重复异步启动。后续可继续补调度观测指标和独立轮询游标。

### 12.2 长期 INIT attempt 已补齐超时核验

attempt 已保存预占归属字段、`out_trade_no`、`init_expire_at` 和 `recovery_attempt_count`。调度器会周期核验过期 INIT attempt，达到最大恢复次数后以 `INIT_TIMEOUT` 收口，并补偿释放账号在途数和 BUY_COUNT 预占。

当前局限是 TTL 与最大恢复核验次数仍为代码常量，暂未产品化配置。

### 12.3 远端恢复能力受 C5 查询能力限制

当前恢复只能在本地订单已有 C5 `orderId` 时调用订单详情核验。若请求已发出但本地没有拿到 `orderId`，暂不能直接按 `outTradeNo` 查远端状态。

### 12.4 账号级限流已补齐后端保护

当前账号并发上限、最大 INIT 在途下单数和 C5 失败短冷却已经通过账号运行态表与后端执行链路落地；余额保护也会扣减 INIT attempt 在途金额。

当前局限是账号运行态暂未提供前端配置入口，冷却时长仍为代码常量。

### 12.5 实时观测已补齐首版

当前已采用 SSE 提供用户维度运行态事件订阅，后端在任务启停、调度启动、单轮结束、任务终态、命中记录和 attempt 状态变化后发布事件；前端收到事件后以 debounce 方式刷新任务列表，并在当前明细抽屉匹配时刷新命中或下单尝试明细。

## 13. 后续优化清单

### P0：建议优先补齐

1. 如果 C5 SDK 后续提供能力，接入按 `outTradeNo` 查询远端订单详情。
2. 启用任务前校验用户 Steam Trade URL 和 C5 API Client 可用性。
3. 为账号运行态提供配置入口和运维展示。

### P1：影响稳定性和公平性

1. INIT 超时 TTL、最大恢复核验次数和账号冷却时长配置化。
2. 增加 `last_scheduled_at` 或独立调度游标，保证同优先级轮询真实有效。
3. 补充调度 lease、账号冷却、在途下单数和 INIT 补偿的运行指标。

### P2：体验与观测优化

1. 更完整的运行指标：平均扫描耗时、最近命中、最近下单结果。
2. 多平台抽象；当前不要在 C5 专用实现上过早泛化。

## 14. 验证建议

实现和后续优化至少覆盖以下验证：

1. 表约束：
   - 同账号同商品运行态唯一。
   - 同任务只允许一个 RUNNING run。
   - 同账号同 productId 唯一下单尝试。

2. 状态机：
   - 创建后为 DRAFT。
   - 启用后为 READY。
   - 调度后为 RUNNING。
   - 停用后为 STOPPED。
   - BUY_COUNT 达标后为 COMPLETED。
   - 连续异常达到阈值后为 ERROR。

3. 防超买：
   - `success_buy_count + reserved_buy_count` 不得超过 `target_buy_count`。
   - 下单失败释放预占。
   - 下单成功转成功数。
   - 重复 listing 被数据库唯一约束拦截。
   - 账号 INIT 在途下单数不得超过账号运行态 `maxInFlightAttempts`。
   - 已终态但未结算的预占 attempt 可被周期补偿正确释放或确认。

4. C5 协议：
   - 查询在售列表参数正确。
   - `productId` 能作为当前 C5 listing 标识。
   - 批量购买请求 `outTradeNo` 能正确匹配成功/失败响应。

5. 恢复：
   - 服务重启后 RUNNING 任务按 `stopRequested` 恢复为 STOPPED 或 READY。
   - running run 被收尾。
   - 已终态 attempt 的预占按 `slot_reserved` / `slot_released` 结算。
   - 无未结算 attempt 时清理残留预占数。
   - 有本地 C5 `orderId` 时尝试远端订单详情核验。
   - 过期 INIT attempt 在未达到恢复阈值前保留预占，达到阈值后以 `INIT_TIMEOUT` 失败收口。
   - 无 `orderId` 的 INIT attempt 也会累计恢复核验次数，不会首次扫描就释放预占。

6. 调度与账号保护：
   - READY 任务必须先获取未过期 lease 才能启动。
   - 获取 lease 后、创建 run 前会二次检查账号冷却。
   - 账号冷却期间不会启动新任务。
   - C5 空响应、远端失败或下单接口异常会写入账号短冷却。

## 16. 当前结论

扫货 2.0 当前实现已经完成从“纯设计”到“可运行首版”的关键跨越：表结构、接口、前端页面、单轮占槽调度、C5 查询、命中落库、下单尝试、订单记录、BUY_COUNT 预占、账号归属校验、attempt 级预占归属、`out_trade_no` 直连、可取消停用、在途金额扣减、保守启动恢复、SSE 运行态推送、账号运行态、账号在途下单数限制、账号短冷却、跨实例调度 lease，以及长期 INIT attempt 超时核验都已存在。

但它仍不是最终最优模型。当前剩余问题主要集中在 C5 远端按 `outTradeNo` 查询能力、账号运行态配置入口、INIT/冷却常量配置化和更完整的调度观测。
