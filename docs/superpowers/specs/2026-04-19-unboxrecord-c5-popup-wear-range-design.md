# 开箱记录 C5 在售挂单弹窗磨损区间化设计

## 目标

将开箱记录页中“C5 在售挂单”弹窗从“单个磨损值就近匹配”改为“按磨损区间筛选 + 价格升序浏览 + 滚动翻页”的交互。

本次设计要解决的核心问题：

- 当前查询参数仍是单个 `wear`，语义已经不适合真实使用场景
- 当前前端存在二次按磨损重排，破坏了低价优先浏览体验
- 当前列表有固定条数上限，不支持像平台列表一样继续下翻
- 用户需要在弹窗内显式选择当前外观可用的细分磨损区间
- 用户需要在受外观约束的前提下手动输入自定义区间

最终目标是让用户在弹窗中看到一份更接近 BUFF 风格的挂单列表：

- 没有当前磨损时，默认不筛磨损，首行就是当前低价
- 有当前磨损时，默认命中对应细分区间
- 所有区间查询结果都按价格升序展示
- 列表可滚动到底部继续翻页
- 用户点击某条挂单后，只回填平台卖出价并关闭弹窗

## 范围

本次设计覆盖以下前后端链路：

### 前端

- `niro-client/src/views/UnboxRecord.vue`
- `niro-client/src/api/unbox.ts`
- `niro-client/src/types/unbox.ts`

### 后端

- `niro-server/niro-web/src/main/java/com/niro/web/controller/UnboxRecordController.java`
- `niro-server/niro-web/src/main/java/com/niro/web/service/UnboxRecordService.java`
- `niro-server/niro-web/src/main/java/com/niro/web/service/impl/UnboxRecordServiceImpl.java`
- `niro-server/niro-web/src/main/java/com/niro/web/dto/param/UnboxRecordC5ListingQueryParam.java`
- `niro-server/niro-web/src/main/java/com/niro/web/dto/UnboxRecordC5ListingVO.java`
- 新增或调整分页响应 DTO

本次不覆盖：

- OCR 识别链路本身
- C5 平台 SDK 行为修改
- 其他页面对 C5 商品列表的复用封装
- 悠悠有品等其他平台的磨损区间策略接入

## 已确认前提

本方案建立在以下前提上：

- 弹窗入口仍在开箱记录编辑场景内
- 查询对象仍然是当前行对应的武器名称与外观
- 弹窗顶部新增区间选择能力，不改成独立页面
- 用户明确要求“不限制行数”，因此列表改为滚动分页，不再保留固定前 N 条逻辑
- 用户明确要求“没有当前磨损值时，不传磨损区间，只按价格升序，像 BUFF 的列表那样打开就是当前低价”
- 用户明确要求区间选项必须随当前行 `exterior` 动态变化
- 用户明确要求支持手动输入自定义区间，且该区间必须受当前外观总边界约束

## 核心判断

这个需求值得做，而且正确做法不是继续在现有 `wearDiff` 排序上打补丁，而是把查询语义直接改成：

- 前端显式选择磨损区间
- 后端按区间过滤
- 结果统一按价格升序返回
- 前端只负责展示与翻页，不再自行重排

这样数据结构和交互含义是一致的，后续不会继续堆特殊情况。

## 总体方案

弹窗内新增一个按外观动态生成的磨损区间下拉框，选项固定由三部分组成：

1. `不筛磨损（按价格）`
2. 当前外观对应的预设细分区间
3. `自定义区间`

用户行为规则如下：

- 当前行有磨损值时，默认选中其所在的预设区间
- 当前行没有磨损值时，默认选中 `不筛磨损（按价格）`
- 弹窗控制区始终提供一个统一的 `查询` 按钮
- 切换下拉选项本身不立即发请求，只有点击 `查询` 后才应用当前选择
- 选中预设区间后，点击 `查询` 提交该区间的 `wearMin / wearMax`
- 选中自定义区间后，显示最小值和最大值输入框，用户点击 `查询` 后才发请求
- 列表统一按价格升序展示
- 列表滚动到底部后按相同条件继续请求下一页并追加

## BUFF 细分区间基线

本次预设区间以已核实的 BUFF 页面分段作为基线，按外观划分如下：

### 崭新出厂（Factory New）

- `0.00 - 0.01`
- `0.01 - 0.02`
- `0.02 - 0.03`
- `0.03 - 0.04`
- `0.04 - 0.07`

### 略有磨损（Minimal Wear）

- `0.07 - 0.08`
- `0.08 - 0.09`
- `0.09 - 0.10`
- `0.10 - 0.11`
- `0.11 - 0.15`

### 久经沙场（Field-Tested）

- `0.15 - 0.18`
- `0.18 - 0.21`
- `0.21 - 0.24`
- `0.24 - 0.27`
- `0.27 - 0.38`

### 破损不堪（Well-Worn）

- `0.38 - 0.39`
- `0.39 - 0.40`
- `0.40 - 0.41`
- `0.41 - 0.42`
- `0.42 - 0.45`

### 战痕累累（Battle-Scarred）

- `0.45 - 0.50`
- `0.50 - 0.63`
- `0.63 - 0.70`

说明：

- 本次只写入已确认的 BUFF 细分区间，不引入未核实的悠悠有品规则
- 当前外观的总边界仍按标准外观范围计算，战痕总范围是 `0.45 - 1.00`
- 当 BUFF 本身不再提供更细预设时，由 `自定义区间` 负责覆盖剩余合法范围

## 外观总边界

自定义区间和自动命中逻辑都依赖当前外观的总边界：

- 崭新出厂：`0.00 - 0.07`
- 略有磨损：`0.07 - 0.15`
- 久经沙场：`0.15 - 0.38`
- 破损不堪：`0.38 - 0.45`
- 战痕累累：`0.45 - 1.00`

如果当前行没有 `exterior`，则本次设计不开放区间筛选能力，只保留 `不筛磨损（按价格）`。

## 接口设计

### 请求参数

现有单点磨损查询改为区间 + 分页语义，建议请求结构如下：

```ts
{
  weaponName: string
  exterior?: number | null
  wearMin?: number | null
  wearMax?: number | null
  pageNum: number
  pageSize: number
}
```

规则：

- 选择 `不筛磨损（按价格）` 时，`wearMin = null`，`wearMax = null`
- 选择预设区间时，提交该区间的 `wearMin / wearMax`
- 选择自定义区间时，提交用户输入并校验通过后的 `wearMin / wearMax`
- `pageNum` 从 `1` 开始
- `pageSize` 固定为前端定义常量，不由用户直接输入

### 响应结构

接口不再返回裸 `List`，改为弹窗专用分页对象：

```ts
{
  records: UnboxRecordC5Listing[]
  pageNum: number
  pageSize: number
  hasMore: boolean
}
```

`hasMore` 足以支撑弹窗翻页，不额外返回 `total`。

### 列表项字段

列表项继续保留当前弹窗展示需要的基础字段：

```ts
{
  productId: string
  price: number
  sellerUid: string
  sellerName: string
  wear: number | null
  delivery: number | null
  imageUrl: string
  marketHashName: string
  itemName: string
}
```

本次设计中，`wearDiff` 不再参与主流程，也不再作为响应字段保留。因为新交互已经从“按目标磨损就近排序”切换为“按指定区间筛选后按价格排序”。

## 后端行为规则

### 查询逻辑

后端统一按以下语义处理：

- `wearMin / wearMax` 都为空：
  - 使用 `searchProductList`
  - 不加磨损区间过滤
  - 直接按价格升序返回
- `wearMin / wearMax` 都有值：
  - 使用 `productSearch`
  - 将区间值映射到 SDK 已支持的 `wearMin / wearMax`
  - 只返回该区间内数据
  - 仍按价格升序返回

本次设计不保留“有 `wear` 时按 `wearDiff` 再按价格”的混合排序。

### 排序职责

排序职责只保留在后端：

- 统一价格升序
- 前端禁止二次重排

这意味着当前后端实现中的 `wearDiff` 相关比较器应退出主流程，避免与新区间查询冲突。

## 前端状态模型

每一行维护各自独立的 C5 弹窗状态，避免切换行时串数据。

建议状态结构如下：

```ts
{
  visible: boolean
  loading: boolean
  loadingMore: boolean
  initialized: boolean

  selectedRangeKey: string
  customWearMin: number | null
  customWearMax: number | null

  appliedWearMin: number | null
  appliedWearMax: number | null

  pageNum: number
  pageSize: number
  hasMore: boolean

  listings: UnboxRecordC5Listing[]
}
```

其中分为两类状态：

### 编辑态

- `selectedRangeKey`
- `customWearMin`
- `customWearMax`

### 已应用查询态

- `appliedWearMin`
- `appliedWearMax`

这样用户修改输入框或切换选项时，不会立刻把当前列表清掉，只有点击查询后才重载数据。

## 下拉选项结构

下拉项使用结构化数据而不是纯字符串：

```ts
type C5WearRangeOption =
  | {
      key: "all"
      label: "不筛磨损（按价格）"
      mode: "all"
    }
  | {
      key: string
      label: string
      mode: "preset"
      wearMin: number
      wearMax: number
    }
  | {
      key: "custom"
      label: "自定义区间"
      mode: "custom"
      exteriorMin: number
      exteriorMax: number
    }
```

每一行的选项由 `exterior` 动态生成：

```ts
getWearRangeOptionsByExterior(exterior)
```

返回结果固定包含：

1. `不筛磨损（按价格）`
2. 当前外观的预设细分区间
3. `自定义区间`

如果 `exterior` 为空，则只返回 `不筛磨损（按价格）`。

## 初始化规则

首次打开某一行弹窗时：

- 若当前行有磨损值：
  - 先根据 `exterior` 找到可用预设区间
  - 再根据当前磨损值命中对应区间
  - 默认选中该预设区间，并以该区间发起首次请求
- 若当前行没有磨损值：
  - 默认选中 `不筛磨损（按价格）`
  - 不传 `wearMin / wearMax`
  - 首屏第一条应是当前最低价

如果当前行有磨损值，但没有命中任何预设区间，同时仍位于当前外观总边界内，则默认切到 `自定义区间`。

这时不自动填入一个伪造的自定义区间，而是在界面上显示提示文案，例如：

- `当前磨损 0.3812 不在预设区间内，请手动设置`

## 自定义区间交互

当下拉框选中 `自定义区间` 时：

- 在下拉框下方显示两个输入框：
  - 最小磨损
  - 最大磨损
- 同时显示一个 `查询` 按钮
- 不采用输入即请求模式

只有用户点击 `查询` 后，才会：

- 校验输入
- 写入 `appliedWearMin / appliedWearMax`
- 重置分页并重新拉取第一页

## 自定义区间校验

校验顺序固定如下：

1. 最小值、最大值都不能为空
2. 两者都必须是合法数字
3. 数值必须落在 `0 ~ 1` 之间
4. 数值必须落在当前外观总边界内
5. `min < max`
6. 提交前统一收敛到 4 位小数

建议错误提示直接使用明确文案：

- `最小磨损不能为空`
- `最大磨损不能为空`
- `自定义区间必须落在当前外观范围内（0.07 - 0.15）`
- `最小磨损必须小于最大磨损`

## 区间边界规则

为避免相邻区间重叠，所有预设区间和自定义区间统一采用：

- `wear >= min`
- `wear < max`

即左闭右开。

例如：

- `0.04 - 0.07`
- `0.07 - 0.08`

则 `0.0700` 归入第二个区间。

只有外观总边界兜底时允许最后一个总区间包含上边界 `1.00`，但该特例只在总边界判断中处理，不向各个预设区间扩散。

## 分页与无限滚动

### 翻页规则

列表容器滚动到底部时：

- 若 `loadingMore = true`，忽略本次触发
- 若 `hasMore = false`，停止请求
- 否则：
  - `pageNum += 1`
  - 带当前 `appliedWearMin / appliedWearMax` 请求下一页
  - 将结果追加到 `listings`

### 必须重置分页的场景

以下任一动作发生时，都必须：

- `pageNum = 1`
- `hasMore = true`
- `listings = []`
- `initialized = true`

触发场景包括：

1. 首次打开弹窗
2. 点击刷新
3. 从 `不筛磨损（按价格）` 切到预设区间并点击查询
4. 从预设区间切到自定义区间并点击查询
5. 修改自定义区间后再次点击查询
6. 当前行的 `weaponName / exterior / wear` 被 OCR 或人工编辑后再次打开弹窗

## 列表展示

### 布局

列表采用单列流式布局，不做多列瀑布流。原因是 popup 宽度有限，多列会破坏信息密度和可读性。

每条挂单展示以下信息：

- 价格：主视觉信息
- 磨损：次信息，无值时显示 `--`
- 卖家：优先 `sellerName`，缺失时回退 `sellerUid`
- 发货方式：短文案或轻量标签

### 顶部摘要

在弹窗标题下方持续显示当前查询条件摘要：

- `当前区间：不筛磨损（按价格）`
- `当前区间：0.07 - 0.08`
- `当前区间：自定义 0.3810 - 0.4000`

如果当前行本身有磨损值，可补充弱提示：

- `当前磨损：0.3864`
- `当前外观：崭新出厂`

## Loading / 空态 / 错误态

### 首屏 loading

首次打开弹窗且该行尚未初始化时：

- 弹窗立即打开
- 标题、下拉框、按钮先渲染
- 列表区显示 loading skeleton 或 spinner
- 不等待接口完成后再打开弹窗

### 翻页 loading

加载下一页时：

- 保留当前已加载列表
- 在底部显示轻量 `加载中` 提示
- 不覆盖旧内容
- 已有列表仍允许点击

### 空态

区分两种文案：

- 不筛磨损时为空：`暂无在售挂单`
- 指定区间时为空：`当前磨损区间暂无在售挂单`

空态下不自动回退到全部磨损重新查询。

### 错误态

区分两种错误场景：

1. 首屏失败且没有任何数据：
   - 显示整块错误态
   - 文案：`查询失败，请稍后重试`
   - 提供 `重试` 按钮
2. 翻页失败但已有历史数据：
   - 保留已加载列表
   - 底部显示 `加载更多失败`
   - 提供 `点击重试`

### 列表结束态

当 `hasMore = false` 且 `listings` 不为空时，底部显示：

- `已加载全部挂单`

## 选择挂单后的行为

点击某条挂单后，只执行一件事：

- 将该挂单价格回填到当前行 `actualSellPrice`

本次交互不顺带修改：

- 当前行磨损
- 当前行备注
- 当前行处理状态
- 其他衍生字段

如果当前行已存在 `actualSellPrice`，则新选择直接覆盖旧值。

### 成功反馈

回填成功后立即：

1. 关闭当前弹窗
2. 给出成功提示，例如：
   - `已回填平台卖出价 ¥123.45`

## 弹窗关闭与缓存策略

### 手动关闭

如果用户只是手动关闭弹窗，没有改变查询条件，也没有点击挂单：

- 保留当前行已加载列表
- 保留当前已选区间
- 下次再次打开时直接展示现有结果

### 不保留滚动位置

本次设计明确不保留滚动位置。因为 popup 本身较小，保滚动位置收益低于实现复杂度。

### 缓存失效条件

以下基础字段任一变化时，该行 C5 查询缓存立即视为失效：

- `weaponName`
- `exterior`
- `wear`

下次打开弹窗时必须重新初始化并重新拉取第一页。

## 顺序一致性

前端必须完全信任后端返回顺序：

- 不再按磨损值倒序重排
- 不再按 `wearDiff` 排序
- 不把 `wear = null` 的项手动挪到底部
- 追加新页时直接按返回顺序接到尾部

否则“按价格升序浏览当前低价挂单”这个核心目标会被前端自己破坏。

## 兼容性影响

### 前端

- `queryC5Listings` 的请求参数从单个 `wear` 改为 `wearMin / wearMax / pageNum / pageSize`
- 返回值从 `UnboxRecordC5Listing[]` 改为分页对象
- 当前行 C5 popup 状态需从“单次列表请求”扩展为“条件 + 分页 + 缓存”模型

### 后端

- `UnboxRecordC5ListingQueryParam` 需要改结构
- Controller 返回类型需要从 `List<...>` 改为分页 DTO
- Service 层需要移除以 `wearDiff` 为核心的排序路径

本变更属于当前功能链路内的前后端同时调整，不要求对旧弹窗接口做并行兼容。

## 验收标准

### 功能验收

- 有当前磨损时，弹窗首次打开默认命中对应预设区间
- 没有当前磨损时，弹窗首次打开默认不筛磨损且首行显示当前低价
- 选择预设区间后，请求参数正确传出 `wearMin / wearMax`
- 选择自定义区间并校验通过后，按输入区间查询
- 列表滚动到底部可以继续翻页并追加内容
- 点击某条挂单后，仅回填 `actualSellPrice` 并关闭弹窗

### 交互验收

- 查询条件摘要、当前磨损提示、空态、错误态、结束态都能正确显示
- 手动关闭后再次打开，若基础字段未变，能够保留已有查询结果与选中区间
- 基础字段变化后，旧缓存会失效并重新初始化

### 一致性验收

- 后端返回顺序与前端展示顺序保持一致
- 不再出现前端按磨损倒序把低价项挤走的问题
- 区间边界采用左闭右开后，不出现相邻区间重复命中

## 结论

这次改动的关键不是给现有“按磨损接近度排序”的流程多加几个 if，而是把数据结构和交互语义一起改正：

- 查询按区间，不按单点
- 列表看价格，不看前端二次重排
- 没有磨损就直接看低价
- 有磨损就默认落到当前外观对应的细分区间
- 不够用的地方用受外观约束的自定义区间补齐

这是最直接、最稳定、也最不容易继续长歪的方案。
