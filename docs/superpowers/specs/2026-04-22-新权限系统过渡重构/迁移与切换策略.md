# 迁移与切换策略

## 目标
本文件用于明确新权限系统从并行试点进入干净切换阶段的迁移策略。目标是让新权限系统成为唯一运行时权限真源，并移除旧权限系统的前端运行时、后端菜单权限链路与旧权限表。

## 当前切换口径
### 新系统运行时真源
干净切换完成后，前端菜单导航与按钮权限只以新权限系统为准：
- 菜单导航来源：`/api/v2/permission/navigation`
- 按钮权限来源：`/api/v2/permission/buttons`
- 菜单与页面资源来源：`resource_published`
- 角色资源授权来源：`role_resource_published`
- 超级管理员角色锁定口径：`sys_role.role_key = 'admin'`

### 旧系统删除边界
本阶段删除旧权限运行时链路：
- 删除 `/api/user/menus` 正常运行时消费链路
- 删除旧 RBAC 菜单维护入口和旧权限页面
- 删除旧菜单权限相关后端接口与不再被引用的链路代码
- 通过新增 Flyway migration 直接删除 `sys_role_menu` 与 `sys_menu`

用户、角色、用户角色关系继续复用既有表，`sys_user`、`sys_role`、`sys_user_role` 不属于本次删除范围。

## 分阶段实施策略
### Phase 0：文档状态切换
- 将本主题状态从“并行试点”调整为“干净切换已确认”。
- 明确旧权限系统不保留运行时兜底。
- 明确新权限系统最终承接菜单导航、按钮权限与角色资源授权。
- 明确旧权限表删除范围仅包含 `sys_role_menu` 与 `sys_menu`。

### Phase 1：模型增强
目标是让新权限系统能表达旧侧栏的目录、页面菜单和按钮结构。

本阶段确认复用 `MENU` 表达目录型节点，不新增 `GROUP` 类型：
- 目录型 `MENU`：允许无 `pageKey`，只承载导航分组。
- 页面型 `MENU`：绑定 `pageKey`，作为页面入口。
- `PAGE`：仍作为页面资源与按钮归属的稳定页面根。
- `BUTTON`：必须能沿父级链路归属到有效 `PAGE`，中间可以经过目录型或页面型 `MENU`。

需要调整：
- 发布校验允许目录型 `MENU` 无 `pageKey`。
- 导航构建允许目录型 `MENU` 作为 `ParentView` 容器。
- 角色预览仍以有效 `PAGE` 作为可达页面候选。
- 按钮归属沿父级向上解析到 `PAGE`。

### Phase 2：全量页面注册
补齐前端 `pageRegistry`，至少覆盖旧 `componentMap` 中仍在运行的后台页面：
- `Dashboard`
- `TaskList`
- `TaskConfig`
- `C5SnipingTaskV2`
- `OrderRecord`
- `GoodsList`
- `StickerList`
- `InventoryBoard`
- `UnboxRecord`
- `ProfitStats`
- `Settings`
- `InviteCodeManageNew`
- `LogsNew`
- `PermissionManageNew`

旧 `PermissionManage.vue` 不再作为最终新权限入口，最终由 `PermissionManageNew.vue` 承接。

### Phase 3：数据基线确认
通过新增 Flyway migration 写入新资源与授权，不修改历史 migration。

数据基线要求：
- 手工写入新资源树，避免旧 `sys_menu` 历史字段语义污染新模型。
- 同步写入 `resource_draft` 与 `resource_published`。
- 将仍需保留的角色授权映射到 `role_resource_draft` 与 `role_resource_published`。
- admin 角色补全所有新资源授权。
- 删除旧表前确认新权限表已经覆盖全部运行时目录、页面和按钮。
- 新增或补偿按钮资源时，同步写入 `resource_draft`、`resource_published`、`role_resource_draft` 与 `role_resource_published`，并确保 `role_key = 'admin'` 拥有全部资源。

### Phase 4：前端运行时干净切换
- 侧栏只消费新权限导航。
- 登录后不再依赖 `/api/user/menus` 装配运行时菜单。
- 清理旧动态路由缓存，保留新权限缓存版本比对机制。
- 首页跳转、目标路由判断和动态路由挂载只基于新权限路由。
- 删除旧权限页面入口与旧 RBAC 菜单维护入口。

### Phase 5：后端旧链路删除
- 删除旧菜单运行时接口。
- 删除旧 RBAC 菜单维护相关接口。
- 删除旧菜单权限 Service、MapperManager、Mapper、DTO 中不再被引用的代码。
- 保留用户、角色、用户角色关系相关能力。

### Phase 6：删除旧权限表
新增 Flyway migration 删除旧权限表，不修改历史 migration：
- 先删除 `sys_role_menu`
- 再删除 `sys_menu`

migration 必须说明破坏性影响与回滚思路；执行后旧菜单权限数据不再可直接恢复。

### Phase 7：按钮权限全量迁移与超管锁定
逐页迁移按钮权限：
- 从旧 `usePermission`、旧 `permission` 指令或旧用户权限码切换到 `useNewPermission`。
- 按页面补齐 `BUTTON` 资源和 `permissionCode`。
- 修改类、危险类和敏感类按钮必须使用新按钮权限资源；查询、重置、详情等查看类动作可复用页面查看权限。
- 业务状态禁用继续保留，不因超级管理员拥有权限而放开不可执行状态。
- `role_key = 'admin'` 的授权树全选且禁用，后端拒绝保存该角色授权修改。
- 发布流程自动补齐 admin 角色全量授权。
- 发布后验证不同角色的按钮显隐。
- 全量迁移完成后删除不再被引用的旧按钮权限工具。

## 回滚与修复策略
### 切换前回退
在删除旧表的 migration 执行前，如发现新导航不可用，可以通过代码回退到上一版本并继续使用旧链路。

### 删除旧表后的恢复
删除 `sys_role_menu` 与 `sys_menu` 后，不再支持通过前端切换恢复旧权限系统。若确需恢复旧表，只能通过新增 Flyway migration 重建表结构，并从备份或补偿脚本恢复数据。

### 新权限数据修复
新资源数据错误不回滚历史 migration：
- 优先通过 `PermissionManageNew` 修复草稿并重新发布。
- 必要时新增补偿 migration 修复 `resource_draft`、`role_resource_draft`、`resource_published` 与 `role_resource_published`。

## 验收标准
### 后端
- `/api/v2/permission/navigation` 能返回包含目录型 `MENU` 的导航树。
- 发布校验允许目录型 `MENU`，但仍能阻止孤儿节点、循环父级、按钮无页面归属等错误配置。
- `/api/v2/permission/buttons` 只返回当前登录用户已发布按钮权限码。
- 角色预览能展示可见导航、可达页面和按钮权限。

### 前端
- 目录型 `MENU` 能渲染为导航分组。
- 页面型 `MENU` 与 `PAGE` 能正确装配路由。
- 未注册 `pageKey` 的页面入口会被跳过并输出前端告警。
- 登录后不再请求 `/api/user/menus`。
- 侧栏不再合并旧菜单与新菜单，只展示新权限导航。
- `InviteCodeManageNew`、`LogsNew` 与其他后台页面统一从新权限导航进入。

### 数据
- `resource_published` 覆盖所有运行时页面。
- `role_resource_published` 至少覆盖 admin 全量授权。
- `role_resource_draft` 同步覆盖 admin 全量授权，权限页展示时 admin 始终全选。
- `sys_role_menu` 与 `sys_menu` 已通过新增 Flyway migration 删除。
- `sys_user`、`sys_role`、`sys_user_role` 保持可用。

## 风险与约束
### 风险一：目录型 `MENU` 放宽后出现无页面空目录
缓解方式：前端构建路由时跳过无有效子路由的目录；发布校验继续保证至少存在启用页面候选。

### 风险二：授权映射不完整
缓解方式：先保障 admin 全授权，再按角色预览核对普通角色。

### 风险三：旧按钮权限未完全迁移
缓解方式：按钮权限按页面逐步迁移；页面迁移完成前不得删除仍被引用的旧按钮权限工具。

### 风险四：admin 授权被误改
缓解方式：前端权限页禁用 `role_key = 'admin'` 的授权勾选，后端保存接口拒绝修改 admin 授权，发布流程自动补齐 admin 全量授权。

### 风险五：删除旧表后无法快速恢复旧权限数据
缓解方式：删除旧表前先确认新权限数据基线；如需恢复，只能通过新增 migration 重建旧表并从备份或补偿脚本恢复数据。

## 结论
全量替换采用干净切换方式推进：先让新权限系统具备完整表达能力，再通过页面注册、数据基线确认、前端运行时切换、后端旧链路删除、旧权限表删除和按钮权限迁移完成替换。切换完成后，旧权限系统不再作为运行时来源或回退兜底。
