# 新权限系统过渡重构设计

## 背景
当前仓库的权限链路已经具备基础 RBAC 能力，但路由、菜单、按钮权限在模型和页面上耦合较重。前端动态路由主要依赖后端下发菜单树，权限管理页也将角色、菜单、授权、批量分配堆叠在同一工作区中，适合局部维护，不适合承接新的路由系统重构。

本次目标已经从并行试点调整为干净切换：新权限系统承接新的路由装配方式、资源模型和权限管理页面，并成为唯一运行时权限真源。旧权限系统的运行时链路、页面入口和旧菜单权限表将被移除。

## 目标
本次设计用于落地一套替代旧权限系统的新权限系统，覆盖以下能力：
- 新路由系统的前后端职责重新划分
- 新权限资源模型的定义
- 新权限管理页工作台设计
- 保存并发布的权限生效机制
- 按角色的导航与按钮可见性预览
- 前端运行时干净切换到新权限导航与新按钮权限
- 全量业务按钮迁移到新 `BUTTON` 权限资源
- 超级管理员角色全权限锁定与后端兜底
- 旧菜单权限接口、旧权限页面和旧权限表删除

## 非目标
本次不包含以下内容：
- 不删除用户、角色和用户角色关系表
- 不在本期做版本回滚能力
- 不引入复杂审批流
- 不在权限页中开放核心路由定义的任意编辑能力
- 不在本期移除现有 `userId = 1` 的管理兜底

## 命名与边界规则
### 命名区分
新权限系统延续试点阶段已落地的命名规则：
- 新页面命名统一加 `new`
- 新接口统一使用 `v2`

该命名规则用于延续既有代码和接口边界；干净切换完成后，旧权限页面和旧菜单链路不再作为运行时入口。

### 数据边界
干净切换阶段的数据边界收敛为：
- 继续复用既有用户、角色与用户角色关系
- 新系统独立维护菜单、按钮、授权关系、草稿态与发布态
- 删除旧菜单权限关系：`sys_role_menu` 与 `sys_menu`

这意味着新系统不会再直接沿用旧系统的资源结构，也不会和旧系统共享菜单/授权关系表，但仍复用现有用户与角色主体，避免身份体系重复维护。

### 一期数据模型口径
一期不采用多版本发布批次模型，而采用极简双表发布模型：
- `resource_draft`
- `role_resource_draft`
- `resource_published`
- `role_resource_published`

编辑动作只改草稿态，运行时只消费已发布态。管理员点击发布时，使用事务将草稿整包覆盖到已发布态。

一期明确不做：
- 发布批次
- 历史版本对比
- 回滚能力
- 审批流

## 新路由系统总体模式
### 模式选择
新路由系统采用混合模式：
- 前端维护页面注册表，负责页面能力和组件映射
- 后端维护已发布的新菜单配置、新按钮资源与授权关系
- 前端根据页面注册表 + 已发布配置装配最终导航与访问能力

### 为什么不用纯后端动态路由
纯后端动态路由会让 `path / component / 路由定义` 与权限配置继续纠缠，导致权限页承担过多职责，也让前端路由演进受后端数据结构限制。

### 为什么不用纯前端静态路由
纯前端静态路由无法满足后台按角色配置菜单结构、显隐、排序、按钮权限和预览发布的需求，也不利于后续权限治理。

### 最终职责分工
#### 前端负责
- 页面注册表
- 核心路由键、页面路径、组件绑定、页面实现
- 根据已发布资源配置进行路由与导航装配
- `new` 页面组与试点页面接入
- 进入 `new` 链路时比对 `config_version` 或 `published_at`，版本变化时只清理新系统缓存并重拉
- 新页面按钮权限消费链路

#### 后端负责
- 新菜单配置
- 新按钮资源定义
- 角色到资源的授权关系
- 草稿/发布态
- 发布后的版本标识
- 角色视角预览所需数据

## 新资源模型
### 总体结构
新资源模型采用“路由/菜单绑定 + 按钮独立”。

#### 路由页面
路由页面是前端注册表中的页面能力单元，负责：
- 唯一 `pageKey`
- 页面路径
- 页面组件绑定
- 页面级基础标识

前端页面注册表是页面能力真源。后端只保存 `pageKey` 引用，不保存 `path`、`component`、`routeName` 等路由定义。

路由页面是页面能力的真源，但不在权限页中直接开放核心定义编辑。

#### 菜单节点
菜单是导航展示层，用于描述“页面如何出现在侧栏和导航中”。菜单负责：
- 标题
- 图标
- 排序
- 显隐
- 层级关系
- 绑定哪个路由页面

菜单依附路由页面存在，但不是路由本身。

#### 按钮权限
按钮是独立资源，用于表示页面内可操作能力。按钮负责：
- 按钮名称
- 权限码
- 所属页面
- 分组或说明

按钮底层独立建模，但交互上按页面聚合展示，同时支持全局搜索。

全量迁移阶段，后台业务页面内的修改类、危险类和敏感类按钮必须建立 `BUTTON` 资源。查询、重置、详情等查看类动作可复用页面查看权限；删除、启停、同步、发布、外部查询、OCR、角色分配等动作优先使用独立权限码。

### 资源关系
- 一个路由页面可以绑定一个或多个菜单节点
- 一个菜单节点对应一个页面入口展示方式
- 一个页面下可以定义多个按钮资源
- 角色授权分为：页面/菜单可见权限 与 页面内按钮可操作权限

## 新权限管理页设计
### 页面定位
新权限管理页是新权限系统的主工作台，不再采用旧权限页那种“大 Tab 拼盘”模式，而是围绕资源治理展开。

页面命名为 `PermissionManageNew`，并在干净切换后成为唯一权限管理入口。

### 页面骨架
页面采用资源工作台结构，分为五个区域：
1. 顶部操作栏
2. 左侧资源树
3. 中间资源配置区
4. 右侧角色授权区
5. 辅助抽屉

### 顶部操作栏
顶部操作栏承担全局控制，包含：
- 资源搜索
- 资源类型筛选（路由/菜单/按钮）
- 草稿状态展示
- 预览入口
- 发布入口

顶部操作栏要持续展示是否存在未发布变更，避免配置与生效状态混淆。

### 左侧资源树
左侧资源树是页面主轴，按层级展示：
- 第一层：页面/路由
- 第二层：菜单节点
- 第三层：按钮资源

资源树需要支持：
- 搜索定位
- 展开/折叠
- 类型与状态标识
- 当前选中高亮

### 中间资源配置区
中间区域用于展示和编辑当前资源详情。

#### 页面资源选中时
只展示：
- 来源路由信息
- 当前绑定菜单情况
- 当前绑定按钮概览
- 预览入口

不允许直接改：
- `component`
- 核心路由键

#### 菜单资源选中时
允许编辑：
- 标题
- 图标
- 排序
- 显隐
- 层级关系

不允许直接改：
- 核心路由定义
- 页面组件映射

#### 按钮资源选中时
允许编辑：
- 按钮名称
- 权限码
- 分组
- 说明

### 右侧角色授权区
右侧区域用于对当前资源做角色授权。

授权分为两类：
- 页面/菜单授权：控制是否可见
- 按钮授权：控制是否可操作

角色区需要支持：
- 展示全部角色
- 只看已授权角色
- 当前资源授权差异提示

#### 菜单权限 Tab
菜单权限 Tab 按“页面 + 菜单树”展示角色可见资源：
- PAGE 资源作为模块根节点，展示页面标题、pageKey 和当前勾选状态。
- MENU 资源作为页面下的树形节点，支持逐项勾选。
- BUTTON 资源不在菜单权限 Tab 展示，继续由操作权限 Tab 承接。
- 勾选状态直接写入当前角色的资源授权草稿，保存按钮仍统一调用现有角色资源保存接口。
- 不新增接口，不改变发布机制，不做菜单与按钮的隐式联动。

#### 超级管理员锁定
`role_key = 'admin'` 的超级管理员角色在授权区始终按全权限展示：
- 菜单权限与操作权限均显示全选。
- 所有授权勾选框禁用，不能勾选或取消勾选。
- 保存该角色授权的入口禁用或提示不可修改。
- 删除、停用、修改 admin 角色编码等既有限制继续保留。

该锁定规则只处理角色授权，不覆盖业务状态禁用。运行中任务不可编辑或删除、已绑定任务账号不可删除等状态型限制仍然对超级管理员生效。

### 辅助抽屉
抽屉承担非主流程能力，避免页面再次退化为大杂烩。

一期抽屉包括：
- 用户分配角色抽屉
- 角色预览抽屉
- 发布前校验结果抽屉

## 页面风格基线
新权限页需要延续当前后台的页面风格，而不是引入新的中台皮肤。

### 风格原则
- 浅色后台
- 白底卡片
- TDesign 原生控件为主
- 蓝灰色低饱和强调
- 紧凑表单与轻量分割

### 视觉层级
- 顶部操作栏最轻
- 左侧资源树是结构主轴
- 中间详情区是视觉重心
- 右侧角色区作为持续可见的辅助区

### 组件延续
建议继续使用：
- `t-tree`
- `t-form`
- `t-table`
- `t-button`
- `t-tag`
- `t-alert`
- `t-drawer`

### 避免的风格方向
- 不做深色工作台
- 不做玻璃、渐变、重运营后台皮肤
- 不为了“新系统”刻意脱离现有页面气质

## 权限变更生效机制
### 生效模式
新权限系统采用“保存并发布”的双阶段机制，不采用即时生效。

### 草稿态
资源配置和授权改动首先进入草稿态，未发布前不会影响线上导航与权限结果。

### 发布态
点击发布后，系统统一对草稿进行合法性校验，通过后以事务方式整包覆盖已发布态。

### 发布主体
一期只有管理员可以执行发布。

### 超级管理员授权补齐
发布流程必须自动补齐 `role_key = 'admin'` 角色对全部发布态资源的授权。草稿态也要保持 admin 角色全量授权，使权限页读取草稿时和发布态一致。角色授权保存接口收到 admin 角色授权修改请求时直接拒绝，避免只靠前端禁用造成误保存。

### 缓存失效
发布成功后，后端更新 `config_version` 或 `published_at`。前端进入 `new` 链路时先比对版本，不一致则清理新系统缓存并重新拉取已发布配置。

### 发布前校验
一期至少需要校验：
- 菜单是否绑定有效页面
- 按钮权限码是否重复
- 按钮是否挂在有效页面下
- 是否存在孤儿菜单或孤儿按钮
- 发布后是否会导致某些角色无首页可进

## 角色预览
### 预览目标
预览能力是新权限系统一期的必备功能，用于验证新路由与新权限模型是否正确。

### 预览内容
按角色预览时至少展示：
- 最终可见导航树
- 页面内可见按钮
- 当前角色首页与可进入页面

### 预览入口
预览通过抽屉或侧边面板打开，不跳出主工作台。

## 用户分配角色
用户分配角色不作为新权限页主结构的一部分，而是通过辅助抽屉进入。

这样做的原因是：
- 主页面聚焦资源与角色授权
- 避免再次把用户管理、资源治理和授权配置混在一起
- 仍然保留必要的角色分配能力

## 新权限系统干净接入方式
### 旧系统移除
旧权限系统不再作为运行时来源。旧权限页、旧 RBAC 菜单维护入口、旧 `/api/user/menus` 消费链路和旧菜单权限表从系统中移除。

### 新系统入口
新系统通过 `PermissionManageNew` 承接权限管理，后台侧栏只展示新权限导航。

### 接口边界
新权限系统的后端接口统一采用 `v2`。运行时菜单导航走 `/api/v2/permission/navigation`，按钮权限走 `/api/v2/permission/buttons`。

### 路由装配边界
前端使用 `pageRegistry` 作为页面能力真源，使用新权限已发布导航装配运行时路由，不再消费 `/api/user/menus`。

### 前端装配规则
前端运行时装配规则为：
- `page registry`：前端真源，维护 `pageKey -> path / routeName / component / 页面级 meta`
- `new permission store`：负责新导航、新按钮权限、新缓存与版本比对
- `new route builder`：把后端已发布配置与前端页面注册表装配成运行时路由

新链路必须满足：
- 登录后不请求 `/api/user/menus`
- 侧栏只展示新权限导航
- 首页跳转和目标路由判断只基于新权限路由
- 新系统未知 `pageKey` 只跳过对应节点并记录 warning，不拖垮整棵菜单树
- 新系统按钮权限不复用旧权限消费口径，改为独立 `useNewPermission` 或等价 store 能力

## 分阶段迁移策略
### 总原则
新权限系统在试点闭环基础上进入全量干净切换，不再保留旧权限运行时兜底。

### 已完成试点范围
已完成试点：
- 新权限管理页自身
- `InviteCodeManageNew`
- `LogsNew`

### 全量切换范围
全量切换覆盖所有仍在运行的后台页面，页面能力统一进入 `pageRegistry`，菜单与授权统一进入新权限发布态。

### 切换入口
后台侧栏只展示新权限导航，`PermissionManageNew` 是唯一权限管理入口，旧权限页面入口移除。

### 后续迁移顺序
先完成菜单导航运行时切换，再迁移页面按钮权限；按钮权限完成前，仍被引用的旧按钮权限工具暂不删除。按钮迁移按 `按钮权限与超级管理员锁定.md` 执行，并通过新增 Flyway 补偿 migration 同步写入草稿态、发布态和 admin 全量授权。

本次实现范围已按当前代码推进到主链路闭环，当前状态如下：

3. [x] 新路由装配逻辑已落地，前端已新增 `pageRegistry`、`new permission store`、`new route builder`，并按已发布导航装配 `new` 菜单组。
4. [x] `PermissionManageNew` 页面工作台已落地，覆盖资源树、资源配置、角色授权、用户分配抽屉、角色预览、发布校验与发布入口。
5. [x] 保存并发布机制已落地，后端发布时以事务将草稿资源与授权整包覆盖到发布态，并返回 `configVersion` / `publishedAt`。
6. [x] 角色预览与发布前校验已落地，校验包含资源类型、父子关系、页面/菜单/pageKey 关系、按钮权限码重复和角色可进入页面等关键约束。
7. [x] `InviteCodeManageNew` 与 `LogsNew` 的试点接入已落地，新入口走新权限链路。
8. [x] 侧栏新增 `new` 菜单组入口已落地。
9. [x] 全量后台页面注册表与新权限资源种子已进入当前实现，待验证数据完整性。

### 当前差异与剩余事项
- 前端运行时仍存在旧 `/api/user/menus` 主链路与旧动态路由缓存，需要切换为只消费新权限导航。
- 侧栏仍存在旧菜单与新菜单合并逻辑，需要改为只展示新权限导航。
- 旧权限页面、旧 RBAC 菜单维护入口、旧菜单权限后端链路需要移除。
- 需要新增 Flyway migration 删除 `sys_role_menu` 与 `sys_menu`。
- 按钮资源与页面按钮权限需要全量核对并迁移到新按钮权限接口。
- 超级管理员角色需要按 `role_key = 'admin'` 在前端授权区锁定，并由后端拒绝授权保存与发布时自动补齐全量授权。
- 后端只保存 `pageKey` 引用，发布校验无法直接校验该 `pageKey` 是否真实存在于前端页面注册表；当前仍由前端装配时跳过未知 `pageKey` 并输出 warning。

## 结论
本次权限系统重构采用干净切换方式推进：
- 旧权限运行时链路移除
- 旧权限页面与旧 RBAC 菜单维护入口移除
- 旧权限表 `sys_role_menu` 与 `sys_menu` 通过新增 Flyway migration 删除
- 新系统独立接口、独立资源结构
- 身份主体继续复用用户、角色与用户角色关系
- 资源与授权关系转入新结构
- 全量业务按钮进入新按钮权限资源
- 超级管理员角色保持全资源授权且不可被手动取消
- 前端以页面注册表为真源，后端以已发布配置为权限真源
- `PermissionManageNew` 成为唯一权限管理入口

切换完成后，菜单导航与按钮权限统一由新权限系统提供，旧权限系统不再作为运行时来源或回退兜底。
