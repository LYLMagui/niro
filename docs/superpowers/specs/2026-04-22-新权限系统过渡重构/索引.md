# 新权限系统过渡重构索引

## 主题
在已落地的新权限系统基础上，推进旧权限系统干净切换：让 `resource_published` 与 `role_resource_published` 成为唯一运行时权限真源，并移除旧 `/api/user/menus` 与旧 `sys_menu/sys_role_menu` 运行时链路。

## 当前状态
干净切换方案已确认，Phase 0 文档更新与 Phase 1 目录型 `MENU` 模型增强已完成代码落地。后端 `v2` 接口、新路由装配、`PermissionManageNew` 工作台、保存并发布、角色预览、发布校验、`InviteCodeManageNew` 与 `LogsNew` 试点入口已形成闭环；目录型 `MENU` 已具备承接旧侧栏目录/菜单/按钮结构的基础表达能力。当前新增确认全量按钮权限迁移与超级管理员锁定方案：后台业务按钮进入新权限系统，`role_key = 'admin'` 角色默认拥有全部资源且授权勾选不可修改。旧权限运行时链路不保留兜底，旧权限表 `sys_role_menu` 与 `sys_menu` 通过新增 Flyway migration 直接删除。

## 当前有效结论
- 干净切换目标已确认：新权限系统成为唯一运行时权限真源，旧权限系统不再作为运行时来源或回退兜底。
- 替换采用分阶段实施：先确认新权限数据基线，再切换前端运行时、删除旧后端链路、删除旧权限表，并完成按钮权限全量迁移。
- 旧 `/api/user/menus`、旧 RBAC 菜单维护接口、旧权限页面与旧菜单运行时链路需要从正常系统中移除。
- 旧权限表删除范围为 `sys_role_menu` 与 `sys_menu`；`sys_user`、`sys_role`、`sys_user_role` 不删除，继续作为用户、角色与用户角色关系真源。
- 新权限系统独立存在，前端相关页面、组命名统一加 `new`，接口统一使用 `v2`。
- 替换阶段复用旧系统的用户、角色；新建菜单、按钮、授权关系与发布态。
- 新路由系统采用混合模式：前端维护页面注册表，后端维护新菜单配置与新权限资源，前端按已发布配置装配最终导航。
- 页面注册表是新路由系统真源；后端仅保存 `pageKey`，不保存 `path`、`component`、`routeName` 等路由定义，权限工作台中的页面资源仅只读展示。
- 新资源模型采用“路由/菜单绑定 + 按钮独立”：页面路由定义不在权限页内直接编辑，菜单负责导航展示配置，按钮权限独立建模但按页面聚合展示。
- 新系统数据模型采用极简双表发布模型：`resource_draft`、`role_resource_draft`、`resource_published`、`role_resource_published`。
- 发布机制采用单一全局草稿 + 单一已发布态；只有管理员可发布，发布时整包覆盖已发布态，不做发布批次、历史版本、回滚与审批流。
- `v2` 接口采用细 REST 风格，最小闭环包含资源查询、资源编辑、角色授权、发布前校验、执行发布、导航查询、当前登录用户已发布按钮权限查询。
- 新系统采用轻量版本比对自动失效：发布后更新 `config_version` 或 `published_at`，前端比对版本，不一致则清缓存并重拉。
- 新权限管理页采用资源工作台结构：左侧资源树、中间资源配置、右侧角色授权，并通过抽屉承接用户分配和权限预览。
- 角色授权区的菜单权限 Tab 采用“页面 + 菜单树”口径：PAGE 作为模块根节点，MENU 作为可勾选子节点，BUTTON 资源不在该 Tab 展示；授权仍复用现有角色资源草稿与保存发布机制。
- 全量替换阶段允许目录型 `MENU`：`MENU` 可以作为无 `pageKey` 的导航目录，也可以作为绑定 `pageKey` 的页面入口；`BUTTON` 仍必须能归属到有效页面链路。
- `PermissionManageNew` 是唯一权限管理入口，旧 `PermissionManage.vue` 与旧 RBAC 菜单维护入口移除。
- 权限变更采用“保存并发布”机制，不走即时生效；发布前需要做资源合法性校验，并支持按角色预览。
- 全量按钮权限迁移采用“按钮资源补种子 + 前端新权限消费 + 后端发布补齐”的方式推进，修改类、危险类和敏感类业务按钮必须进入新 `BUTTON` 资源。
- 超级管理员角色统一按 `sys_role.role_key = 'admin'` 锁定；该角色在权限页始终全选且禁用，后端拒绝保存其授权修改，发布时自动补齐全部资源授权。
