# solo-pm-workflow 合并技能设计

日期：2026-04-20  
范围：项目级 Claude Code skill 设计与落地规范

## 1. 目标

为独立开发者提供一个统一入口的 Claude Code skill，在用户表达不同类型需求时，能够按意图动态路由到两类工作流之一：

1. 产品需求 / PRD / 竞品分析工作流
2. HTML 原型 / 页面雏形生成工作流

该 skill 的核心不是把两个大 skill 直接拼接在一个主文件里，而是建立一个轻量的主路由层：

- 主 `SKILL.md` 只负责识别用户意图、决定进入哪条子流程、在必要时建议完整闭环
- 两条子流程分别沉淀到 `references/` 目录中，作为可维护的引用文档
- 所有引用统一使用相对路径，避免硬编码绝对路径

## 3. 当前事实与问题

### 3.1 当前项目内没有对应的合并 skill

当前项目 `.claude/skills/` 下已有若干技能，但不存在一个针对“独立开发者产品推进闭环”的统一 skill。现有 skill 更多是单点能力：

- `frontend-design`
- `brainstorming`
- `find-skills`
- `skill-optimizer`
- `backend-development-standard`
- `frontend-page-development`

缺少一个面向“先想清楚，再决定是做产品分析还是直接做原型”的中间层技能。

### 3.2 两个外部 skill 的价值重心不同

待整合的两类能力，本质上并不重复：

- 产品需求 / 竞品分析类：擅长从模糊想法出发，整理用户、痛点、需求边界、竞品差异和机会点。
- HTML 原型生成类：擅长将需求快速转成可展示的高保真 HTML 页面原型。

问题不在于“二选一”，而在于缺少一个清晰的入口，让系统知道什么时候该先做产品分析，什么时候该直接做原型，什么时候该建议两者串联。

### 3.3 如果主文件写得太重，会变成新的维护负担

如果把两套完整流程都直接塞进主 `SKILL.md`，会带来三个问题：

1. 主文件过长，触发条件和执行流程混杂。
2. 后续调整某一条子流程时，必须反复修改主文件。
3. 很难做到“只按用户意图路由，不把所有流程都灌进上下文”。

因此主文件必须足够薄，只承担路由职责。

## 5. 路由规则设计

### 5.1 路由目标一：产品策略工作流

当用户表达以下类型需求时，主 skill 路由到 `product-strategy.md`：

- 帮我梳理产品想法
- 帮我写 PRD
- 帮我做需求拆解
- 帮我分析目标用户 / 用户痛点
- 帮我做竞品分析
- 帮我判断做什么功能更合理
- 我是独立开发者，不会做产品设计，帮我先想清楚

该工作流的核心输出应偏向：

- 问题定义
- 用户与场景
- 需求边界
- 功能优先级
- 竞品洞察
- 下一步建议

### 5.2 路由目标二：HTML 原型工作流

当用户表达以下类型需求时，主 skill 路由到 `html-prototype.md`：

- 帮我生成一个 HTML 原型
- 做一个页面雏形
- 做一个可展示的 landing page
- 根据需求生成网页原型
- 给我几个可视化方案
- 做一个高保真页面 demo

该工作流的核心输出应偏向：

- 页面规划
- 风格选择
- 生成策略
- 输出文件组织
- 原型质量检查

### 5.3 复合需求的编排规则

当用户的表达同时包含“需求不清楚”和“想快速看到页面”两类信号时，主 skill 不应立即跳到原型生成，而应采用串联编排：

1. 先走产品策略工作流
2. 产出最小可执行需求框架
3. 再把该框架作为输入交给 HTML 原型工作流

典型例子：

- 我想做一个 SaaS，但不知道功能怎么定，帮我顺便出个页面原型
- 我有个创业想法，你先帮我梳理需求，再做一个 demo 页面

默认规则：

- **需求清楚** → 可以直接进入原型工作流
- **需求模糊** → 先进入产品策略工作流
- **用户明确要完整闭环** → 先产品策略，再原型

## 6. 主 SKILL.md 的内容要求

主 `SKILL.md` 需要符合标准化结构，至少包含：

1. Frontmatter
2. `# Skill Title`
3. `## When to use this skill`
4. `## Instructions`
5. `## Examples`
6. `## Best practices`
7. `## References`

其中：

### 6.1 Frontmatter 要求

建议字段：

```yaml
---
name: solo-pm-workflow
description: 面向独立开发者的产品推进工作流，根据用户意图在产品策略分析与 HTML 原型生成之间动态路由，必要时串联两者形成从想法到原型的闭环。
---
```

不额外堆叠无用元数据，保持简洁。

### 6.2 Instructions 要求

`Instructions` 中应明确三段逻辑：

1. 先判断用户目标是“想清楚”还是“做出来”
2. 再判断需求是否已经足够清晰
3. 最后决定：
   - 路由到产品策略
   - 路由到 HTML 原型
   - 或者先产品策略再原型

并要求主 skill 在路由时引用相对路径，而不是复制子流程全文。

## 7. references 子文档设计

### 7.1 `product-strategy.md`

该文档用于承接产品需求与竞品分析能力，内容要点：

- 适用场景
- 需求梳理流程

该文档用于承接 HTML 原型生成能力，内容要点：

- 适用场景
- 页面规划
- 风格选择
- 输出目录选择
- 生成策略
- 自检标准
- 如何承接来自产品策略文档的输入

该文档不负责重新做完整产品分析，而是接住已经明确的需求输入。

## 8. 相对路径引用规范

主文件中的引用必须使用相对路径。标准写法如下：

```markdown
- 产品策略工作流：`./references/product-strategy.md`
- HTML 原型工作流：`./references/html-prototype.md`
```

禁止：

- 使用绝对文件系统路径
- 使用仓库外路径
- 在主文件中粘贴整份 reference 内容替代引用

## 9. 推荐交互策略

### 9.1 默认交互原则

主 skill 的语气应该像一个“有产品判断力的路由器”，而不是一个直接执行所有事情的巨型模板。

它应该先做最小判断：

- 用户现在缺的是方向，还是缺的是展示？
- 用户要的是分析，还是要一个可看的结果？
- 用户的需求是否足够具体到可以直接出原型？

### 9.2 决策优先级

优先级按以下顺序执行：

1. 用户明确意图
2. 需求清晰度
3. 是否需要闭环建议

也就是说：

- 如果用户明确说“直接给我页面原型”，不要强行先做长篇产品分析。
- 如果用户明显还没想清楚产品是什么，不要直接做精致原型去掩盖需求空洞。
