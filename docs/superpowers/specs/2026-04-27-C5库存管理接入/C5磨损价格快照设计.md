# C5 磨损价格快照设计

## 背景与问题

库存上架抽屉和开箱记录 C5 在售挂单弹窗都需要查询 C5 在售商品价格参考。当前带磨损区间的查询通过 C5 `/merchant/market/v2/products/search` 实时请求，接口 QPS 为 1 秒 1 次。

实时查询会带来以下问题：

- 多人同时打开库存上架抽屉或开箱记录弹窗时，容易触发 C5 限流。
- 前端翻页、刷新、重复打开会放大请求量。
- 同一个 `marketHashName + 磨损区间` 的价格参考在不同用户和不同入口之间无法复用。
- 价格参考属于辅助定价数据，不需要阻塞用户操作等待 C5 实时返回。

因此需要把 C5 在售参考查询从“前端触发实时查询”改为“本地价格快照 + 后台定时刷新”。

## 目标

- 库存上架抽屉和开箱记录 C5 在售挂单弹窗统一读取本地价格快照。
- 前端入口不再直接触发 C5 实时查询。
- 后台刷新队列按快照 key 刷新 C5 在售参考价格。
- 相同商品、相同归一化磨损区间的快照全局共享，不按用户或账号重复刷新。
- C5 市场查询调用统一经过 Redis 令牌桶限流，保证全系统 1 QPS。
- 前端价格参考区域统一展示上次更新时间、刷新状态和“约 5 分钟刷新”提示。

## 范围

### 本期范围

- 库存上架抽屉的同磨损在售参考。
- 开箱记录 C5 在售挂单弹窗。
- 新增 C5 市场价格快照表。
- 新增或改造后端快照查询、申请刷新、后台刷新任务。
- 后端刷新使用系统级 C5 市场查询 AppKey，不默认消耗用户 C5 扫货账号 AppKey。
- 前端两个入口改为读本地快照，并展示统一刷新状态提示。

### 非目标

- 不做价格趋势图。
- 不做刷新历史表。
- 不做按用户隔离的价格缓存。
- 不做实时 C5 查询兜底。
- 不做复杂商品热度模型。
- 不改造库存刷新历史批次能力。

## 当前现状

当前库存上架同磨损参考后端入口为：

```text
GET /api/c5/inventory/market-references
```

现有逻辑：

- 有 `wearMin` / `wearMax` 时，调用 C5 `/merchant/market/v2/products/search`。
- 无 `wearMin` / `wearMax` 时，调用 C5 `/merchant/market/v2/products/list`。
- 后端只请求当前页，并将 C5 返回结果转换为前端参考挂单 DTO。
- 当前不落库。

C5 SDK 当前已有封装：

```java
C5MarketClient.productSearch(C5ProductSearchRequest req)
```

对应 C5：

```text
POST /merchant/market/v2/products/search
```

普通在售列表封装为：

```java
C5MarketClient.searchProductList(C5ProductListRequest req)
```

对应 C5：

```text
POST /merchant/market/v2/products/list
```

## 核心决策

### 1. 快照全局共享

价格快照是 C5 公开市场行情缓存，不包含用户私有库存、账号密钥或交易数据。

快照不按 `user_id` 或 `account_id` 隔离。不同用户、不同入口查询相同商品和相同磨损区间时，共用同一条快照。

前端接口仍然需要登录与权限校验，但返回数据来自全局快照池。

### 2. 快照 key

快照唯一维度为：

```text
app_id + market_hash_name + range_type + wear_min + wear_max
```

首期固定：

```text
app_id = 730
page_num = 1
page_size = 50
```

保留 `page_num` / `page_size` 字段作为刷新配置，但不进入唯一键。

`WEAR` 类型在入库前必须由后端归一化磨损区间，再使用归一化后的 `wear_min` / `wear_max` 生成快照 key。前端可以传当前磨损或原始区间，但不能直接决定最终快照 key。

归一化规则首期采用固定磨损档位：

| 档位 | `wear_min` | `wear_max` | 说明 |
|---|---:|---:|---|
| 崭新出厂 | `0.00000000` | `0.07000000` | Factory New |
| 略有磨损 | `0.07000000` | `0.15000000` | Minimal Wear |
| 久经沙场 | `0.15000000` | `0.38000000` | Field-Tested |
| 破损不堪 | `0.38000000` | `0.45000000` | Well-Worn |
| 战痕累累 | `0.45000000` | `1.00000000` | Battle-Scarred |

归一化行为：

- `range_type = ALL` 时，固定归一化为 `wear_min = 0.00000000`、`wear_max = 1.00000000`。
- `range_type = WEAR` 且传入当前磨损 `wear` 时，后端按 `wear` 所在档位归一化。
- `range_type = WEAR` 且传入 `wearMin` / `wearMax` 时，后端按区间中点所在档位归一化。
- 区间边界采用左闭右开，最后一档右边界包含 `1.00000000`。
- 数据库存储的 `wear_min` / `wear_max` 始终为归一化后的档位边界。

### 3. 磨损区间语义

新增 `range_type` 区分区间含义：

```text
ALL   不筛磨损，按价格查看
WEAR  指定磨损区间
```

`ALL` 类型：

- 表内统一存 `wear_min = 0`、`wear_max = 1`。
- 前端展示为“不筛磨损（按价格）”。
- 后台刷新时走 C5 `/merchant/market/v2/products/list`，不传 `wearMin` / `wearMax`。

`WEAR` 类型：

- 表内保存归一化后的 `wear_min` / `wear_max`。
- 后台刷新时走 C5 `/merchant/market/v2/products/search`，传归一化后的 `wearMin` / `wearMax`。
- 返回记录按价格升序保存，前端可在本地基于当前磨损计算“磨损最接近”展示。

### 4. 每次刷新抓取数量与排序口径

每个快照 key 每次只请求 1 页：

```text
pageNum = 1
pageSize = 50
```

本地 `listings_json` 最多保存 50 条挂单。

快照内记录按价格升序、磨损升序保存。该口径优先保证“低价参考”的稳定性，同时覆盖开箱记录弹窗的“磨损最接近”诉求：

- 库存上架抽屉默认展示价格最低的前 10 条，可展开查看最多 50 条。
- 开箱记录 C5 在售挂单弹窗接收当前磨损后，前端从最多 50 条快照记录中按 `abs(record.wear - currentWear)` 升序选出最接近的 5 条展示；无当前磨损时按价格升序展示。

该方案不为 `target_wear` 单独建快照 key，避免同一商品按每个具体磨损生成大量快照。代价是“最接近”只在当前归一化档位的前 50 条低价样本内计算，首期接受该近似。

### 5. 刷新周期

首期统一刷新周期：

```text
目标刷新间隔：5 分钟
```

`refresh_interval_seconds` 表示目标刷新间隔，不承诺严格准点刷新。实际刷新时间受队列积压、C5 限流、系统 AppKey 可用性和失败退避影响。

用户打开入口时只更新 `last_request_time`。只有快照不存在或已过期时，才将 `next_refresh_time` 提前到 `now()`。

用户手动刷新时设置 `next_refresh_time = now()` 并临时提高 `refresh_priority`。手动刷新成功或失败后，`refresh_priority` 重置为 `0`，避免一次手动刷新导致长期优先。

### 6. 前端不保留实时查询

库存上架抽屉和开箱记录 C5 在售挂单弹窗都不再直接请求 C5。

用户打开入口或点击刷新时，只会申请本地快照刷新：

- 快照不存在：创建快照，进入刷新队列。
- 快照已过期：提前 `next_refresh_time`。
- 用户手动刷新：提前 `next_refresh_time`，临时提高优先级，并受刷新冷却保护。

所有 C5 请求由后台刷新 worker 统一执行。

## 数据模型

### 表名

```text
c5_market_price_snapshot
```

表语义：

```text
C5市场价格最新快照表
```

一行代表一个 C5 在售参考查询维度的最新快照。

### 字段设计

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `bigint` | 主键 ID |
| `app_id` | `integer` | Steam 应用 ID，CS2 固定 730 |
| `market_hash_name` | `varchar(255)` | Steam 市场 Hash 名称 |
| `range_type` | `varchar(32)` | 区间类型，`ALL` 不筛磨损，`WEAR` 指定磨损区间 |

| `wear_max` | `numeric(12,8)` | 查询最大磨损，`ALL` 固定 1 |

| `page_size` | `integer` | C5 查询页大小，首期固定 50 |

### 状态枚举

```text
PENDING     等待刷新
REFRESHING  刷新中
SUCCESS     最近刷新成功
FAILED      最近刷新失败
DISABLED    已停用
```

### `listings_json` 精简字段

每条挂单只保存前端展示和辅助定价需要的字段：

```json
{
  "productId": "C5在售商品ID",
  "price": 123.45,
  "wear": 0.12345678,
  "delivery": 2,
  "acceptBargain": false,
  "sellerUid": "卖家UID",
  "imageUrl": "图片地址",
  "assetId": "资产ID"
}
```

首期不保存完整 C5 原始响应，不保存完整 `assetInfo`。

## 后端接口设计

### 快照查询接口

两个前端入口统一使用本地快照查询能力。

建议接口语义：

```text
GET /api/c5/market-price-snapshots/reference
```

请求参数：

| 参数 | 说明 |
|---|---|
| `marketHashName` | Steam 市场 Hash 名称 |
| `rangeType` | `ALL` 或 `WEAR` |
| `wearMin` | 最小磨损，`WEAR` 必传 |
| `wearMax` | 最大磨损，`WEAR` 必传 |
| `displayMode` | 展示模式，`PRICE_LOWEST` 价格优先或 `WEAR_NEAREST` 磨损接近优先 |
| `currentWear` | 当前磨损，`displayMode = WEAR_NEAREST` 时用于前端排序 |
| `limit` | 前端展示数量，默认 10，最大 50 |

返回字段：

| 字段 | 说明 |
|---|---|
| `records` | 挂单参考列表 |
| `lowestPrice` | 最低价 |
| `avgPrice` | 当前快照样本算术平均价 |
| `sampleCount` | 样本数量 |
| `snapshotStatus` | 快照状态 |
| `lastSuccessTime` | 最近成功刷新时间 |
| `refreshIntervalSeconds` | 刷新间隔 |
| `stale` | 是否已超过刷新周期 |
| `normalizedWearMin` | 后端归一化后的快照最小磨损 |
| `normalizedWearMax` | 后端归一化后的快照最大磨损 |
| `displayMode` | 实际展示模式 |
| `message` | 前端提示文案 |

查询行为：

- 入参先由后端归一化为最终快照 key。
- 快照不存在：创建 `PENDING` 快照，`next_refresh_time = now()`，返回空列表与排队状态。
- 快照存在且未过期：返回现有快照。
- 快照存在且已过期：返回旧快照，并提前 `next_refresh_time = now()`。
- 普通查询只更新 `last_request_time`，不提高 `refresh_priority`。
- 不直接调用 C5。

### 手动申请刷新接口

建议接口语义：

```text
POST /api/c5/market-price-snapshots/refresh-request
```

行为：

- 入参先由后端归一化为最终快照 key。
- 创建或更新快照。
- 更新 `last_request_time = now()`。
- 同一快照 60 秒内重复手动刷新只更新时间，不重复提高优先级。
- 设置 `refresh_priority = 100`。
- 设置 `next_refresh_time = now()`。
- 不直接调用 C5。

## 后台刷新队列设计

### 整体模型

采用“XXL-JOB 扫描 + Redis 队列 + 单 worker 消费”的方案：

```text
XXL-JOB 每 1 分钟扫描到期快照
  -> 抢占并标记 REFRESHING
  -> 投递 snapshotId 到 Redis 队列
  -> worker 按 Redis 令牌桶 1 QPS 消费
  -> 调用 C5 并写回快照结果
```

XXL-JOB 只负责轻量扫描和入队，不在 job 线程里等待令牌或直接调用 C5。这样可以吃满 1 QPS，同时避免 job 执行接近 1 分钟后与下一轮重叠。

Redis 队列 key：

```text
c5:market-price:snapshot-refresh:queue
```

worker 并发：

```text
首期固定 1 个逻辑 worker
```

如果未来需要多实例部署，多个 worker 可以同时启动，但必须共用 Redis 令牌桶，并在消费前重新校验快照状态，避免重复刷新。

### 扫描频率

XXL-JOB 每 1 分钟触发一次价格快照扫描任务。

扫描条件：

```text
refresh_enabled = true
next_refresh_time <= now()
status in ('PENDING', 'SUCCESS', 'FAILED')
```

### 每轮扫描数量

每轮最多扫描并入队 60 条快照。

排序规则：

```text
refresh_priority desc
last_request_time desc
next_refresh_time asc
id asc
```

如果积压超过 60 条，剩余记录等待下一轮扫描。

### 抢占与去重

不在数据库里写复杂业务逻辑，不使用存储过程。抢占逻辑放在 Service 中完成：

1. 查询候选 snapshot id。
2. 对每个 id 执行条件更新：只有当 `status <> 'REFRESHING'` 且 `next_refresh_time <= now()` 时，才更新为 `REFRESHING`。
3. 更新成功的记录才投递到 Redis 队列。
4. worker 消费时再次读取记录，只有 `status = REFRESHING` 才执行 C5 请求。

条件更新示例语义：

```text
update c5_market_price_snapshot
set status = 'REFRESHING', refresh_start_time = now(), update_time = now()
where id = ?
  and refresh_enabled = true
  and next_refresh_time <= now()
  and status <> 'REFRESHING'
```

该方案把业务判断放在 Java Service，数据库只承担原子条件更新，不承担排序、退避、状态流转等业务过程。

### REFRESHING 超时恢复

扫描任务每轮开始时先恢复卡住的刷新记录：

```text
status = 'REFRESHING'
refresh_start_time < now() - 5 分钟
```

恢复规则：

```text
status = FAILED
fail_count = fail_count + 1
last_error_message = '刷新任务超时'
last_fetch_time = now()
next_refresh_time = now() + min(5 * fail_count, 30) 分钟
refresh_priority = 0
```

超时恢复在 Service 中按普通更新执行，不使用数据库存储过程。


### 刷新成功规则

刷新成功后：

```text
status = SUCCESS
fail_count = 0
last_error_message = ''
last_fetch_time = now()
last_success_time = now()
next_refresh_time = now() + refresh_interval_seconds
fetch_count = fetch_count + 1
refresh_priority = 0
lowest_price / avg_price / sample_count / has_more / listings_json 更新为最新结果
last_fetch_account_id = 本次使用的系统账号 ID
```

### 刷新失败规则

刷新失败后：

```text
status = FAILED
fail_count = fail_count + 1
last_error_message = 错误摘要
last_fetch_time = now()
fetch_count = fetch_count + 1
refresh_priority = 0
next_refresh_time = now() + min(5 * fail_count, 30) 分钟
last_fetch_account_id = 本次使用的系统账号 ID
```

连续失败退避：

```text
第 1 次失败：5 分钟后重试
第 2 次失败：10 分钟后重试
第 3 次失败：15 分钟后重试
最多退避到 30 分钟
```

## 系统 AppKey 与限流设计

### 系统 AppKey 池

后台刷新只使用系统级 C5 市场查询 AppKey，不默认使用用户配置的 C5 扫货账号 AppKey。

保守规则：

- 快照数据全局共享，不绑定用户账号。
- 系统 AppKey 由服务端配置或平台维护账号提供。
- 普通用户的 C5 扫货账号 AppKey 不进入全局快照刷新池。
- 如未来需要复用用户账号，必须增加显式授权字段，例如 `allow_market_snapshot_pool`，且默认关闭。
- 选择策略采用轮询。
- 轮询游标放 Redis，不落库。
- 每次刷新记录 `last_fetch_account_id`；首期没有系统账号表时记录 `0`。
- 日志中不得输出 AppKey 明文。

Redis 游标 key：

```text
c5:market-price:system-appkey-pool:cursor
```

### Redis 令牌桶限流

C5 市场查询统一采用 Redis 令牌桶限流。

`/merchant/market/v2/products/search` 限流规则：

```text
桶容量：1
补充速率：1 token / 秒
每次请求消耗：1 token
```

建议 Redis key：

```text
c5:market-price:products-search:rate-limit
```

`/merchant/market/v2/products/list` 也通过后台队列执行，首期可共用同一个 C5 市场查询令牌桶，避免绕过统一市场查询预算。

获取不到令牌时：

- worker 不调用 C5。
- 将当前快照恢复为可重试状态，`status = PENDING`，`next_refresh_time = now() + 10 秒`。
- 不增加 `fail_count`，因为这不是 C5 查询失败。

Redis 不可用时：

- 扫描任务本轮停止，不投递新刷新任务。
- worker 本轮停止，不绕过限流直连 C5。
- 不批量改写快照为 `FAILED`，避免系统组件故障污染业务失败状态。

## 前端交互设计

### 库存上架抽屉

打开抽屉时：

- 根据当前商品和磨损区间查询本地快照。
- 不直接请求 C5。
- 默认展示前 10 条参考挂单。
- 支持展开查看最多 50 条。
- 底部展示后端返回的刷新状态提示，包含上次成功刷新时间。

用户点击刷新：

- 调用申请刷新接口。
- 不等待 C5 实时返回。
- 展示排队刷新状态。

### 开箱记录 C5 在售挂单弹窗

打开弹窗时：

- 有当前磨损或用户选择磨损区间时，查询 `WEAR` 快照，并传 `displayMode = WEAR_NEAREST`。
- 用户选择“不筛磨损（按价格）”时，查询 `ALL` 快照，并传 `displayMode = PRICE_LOWEST`。
- 不直接请求 C5。
- 默认展示磨损最接近的 5 条参考挂单。
- 支持切换为价格优先展示，最多 50 条。
- 底部展示后端返回的刷新状态提示，包含上次成功刷新时间。

### 降级展示

没有快照：

```text
暂无价格参考，已加入刷新队列
```

有快照但过期：

```text
继续展示旧快照，并显示：价格约每 5 分钟刷新，上次更新 HH:mm，正在排队刷新
```

刷新中：

```text
继续展示旧快照，并显示正在刷新价格参考
```

刷新失败且有旧快照：

```text
继续展示旧快照，并显示最近刷新失败，可稍后重试
```

刷新失败且没有成功快照：

```text
暂无价格参考，最近刷新失败
```

## 验收标准

- 库存上架抽屉打开时不直接调用 C5。
- 开箱记录 C5 在售挂单弹窗打开时不直接调用 C5。
- 同一个 `app_id + market_hash_name + range_type + 归一化 wear_min + 归一化 wear_max` 只生成一条快照。
- 后台任务每 1 分钟扫描到期快照，每轮最多入队 60 条。
- Redis 刷新队列由单 worker 消费，C5 市场查询实际调用受全局 1 QPS 令牌桶限制。
- 每条快照刷新使用 `pageNum=1`、`pageSize=50`。
- `WEAR` 类型刷新走 `/merchant/market/v2/products/search`。
- `ALL` 类型刷新走 `/merchant/market/v2/products/list`。
- C5 市场查询调用经过 Redis 令牌桶限流。
- AppKey 使用系统级 C5 市场查询 AppKey 池轮询选择。
- 快照刷新成功后更新 `listings_json`、最低价、平均价、样本数和下次刷新时间。
- 快照刷新失败后按失败次数退避，最多 30 分钟。
- 前端默认展示前 10 条，可展开查看最多 50 条；开箱记录弹窗有当前磨损时默认展示磨损最接近 5 条。
- 前端底部展示后端返回的刷新状态提示，包含上次成功刷新时间。

## 兼容性与风险

### 兼容性

- 不删除现有 C5 SDK 封装。
- 不改变库存上架提交流程。
- 不改变开箱记录主列表数据结构。
- 新快照表为追加式变更。
- 前端入口从实时查询切换为快照查询后，应保留原有展示字段语义。

### 风险

- 快照不是实时价格，前端必须展示刷新周期提示。
- 如果待刷新快照过多，部分冷门商品会延迟刷新。
- 如果系统级 AppKey 池为空，所有快照会保持等待或进入失败退避状态。
- Redis 不可用时，令牌桶、刷新队列和轮询游标不可用，后台刷新应停止，不应绕过限流直连 C5，也不应批量污染快照失败状态。
