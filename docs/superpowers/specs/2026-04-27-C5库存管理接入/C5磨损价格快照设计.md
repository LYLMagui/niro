# C5 磨损价格快照设计

## 背景与问题

库存上架抽屉和开箱记录 C5 在售挂单弹窗都需要查询 C5 在售商品价格参考。当前带磨损区间的查询通过 C5 `/merchant/market/v2/products/search` 实时请求，接口 QPS 为 1 秒 1 次。

实时查询会带来以下问题：

- 多人同时打开库存上架抽屉或开箱记录弹窗时，容易触发 C5 限流。
- 前端翻页、刷新、重复打开会放大请求量。
- 同一个 `marketHashName + 磨损区间` 的价格参考在不同用户和不同入口之间无法复用。
- 价格参考属于辅助定价数据，不需要阻塞用户操作等待 C5 实时返回。

因此需要把 C5 在售参考查询从“前端触发实时查询”改为“本地价格快照 + 后台定时刷新”。

## 目标

- 库存上架抽屉和开箱记录 C5 在售挂单弹窗统一读取本地价格快照。
- 前端入口不再直接触发 C5 实时查询。
- 后台定时任务按快照 key 刷新 C5 在售参考价格。
- 相同商品、相同磨损区间的快照全局共享，不按用户或账号重复刷新。
- C5 `/merchant/market/v2/products/search` 调用统一经过 Redis 令牌桶限流，保证全系统 1 QPS。
- 价格参考底部统一提示“价格每 5 分钟刷新”。

## 范围

### 本期范围

- 库存上架抽屉的同磨损在售参考。
- 开箱记录 C5 在售挂单弹窗。
- 新增 C5 市场价格快照表。
- 新增或改造后端快照查询、申请刷新、后台刷新任务。
- AppKey 池采用可用 C5 扫货账号 AppKey 轮询。
- 前端两个入口改为读本地快照，并展示统一刷新提示。

### 非目标

- 不做价格趋势图。
- 不做刷新历史表。
- 不做按用户隔离的价格缓存。
- 不做实时 C5 查询兜底。
- 不做复杂商品热度模型。
- 不改造库存刷新历史批次能力。

## 当前现状

当前库存上架同磨损参考后端入口为：

```text
GET /api/c5/inventory/market-references
```

现有逻辑：

- 有 `wearMin` / `wearMax` 时，调用 C5 `/merchant/market/v2/products/search`。
- 无 `wearMin` / `wearMax` 时，调用 C5 `/merchant/market/v2/products/list`。
- 后端只请求当前页，并将 C5 返回结果转换为前端参考挂单 DTO。
- 当前不落库。

C5 SDK 当前已有封装：

```java
C5MarketClient.productSearch(C5ProductSearchRequest req)
```

对应 C5：

```text
POST /merchant/market/v2/products/search
```

普通在售列表封装为：

```java
C5MarketClient.searchProductList(C5ProductListRequest req)
```

对应 C5：

```text
POST /merchant/market/v2/products/list
```

## 核心决策

### 1. 快照全局共享

价格快照是 C5 公开市场行情缓存，不包含用户私有库存、账号密钥或交易数据。

快照不按 `user_id` 或 `account_id` 隔离。不同用户、不同入口查询相同商品和相同磨损区间时，共用同一条快照。

前端接口仍然需要登录与权限校验，但返回数据来自全局快照池。

### 2. 快照 key

快照唯一维度为：

```text
app_id + market_hash_name + range_type + wear_min + wear_max
```

首期固定：

```text
app_id = 730
page_num = 1
page_size = 50
```

保留 `page_num` / `page_size` 字段作为刷新配置，但不进入唯一键。

### 3. 磨损区间语义

新增 `range_type` 区分区间含义：

```text
ALL   不筛磨损，按价格查看
WEAR  指定磨损区间
```

`ALL` 类型：

- 表内统一存 `wear_min = 0`、`wear_max = 1`。
- 前端展示为“不筛磨损（按价格）”。
- 后台刷新时走 C5 `/merchant/market/v2/products/list`，不传 `wearMin` / `wearMax`。

`WEAR` 类型：

- 表内保存明确的 `wear_min` / `wear_max`。
- 后台刷新时走 C5 `/merchant/market/v2/products/search`，传 `wearMin` / `wearMax`。

### 4. 每次刷新抓取数量

每个快照 key 每次只请求 1 页：

```text
pageNum = 1
pageSize = 50
```

本地 `listings_json` 最多保存 50 条挂单。

前端默认展示前 10 条，可展开查看最多 50 条。

### 5. 刷新周期

首期统一刷新周期：

```text
5 分钟
```

不做复杂热度模型。用户近期打开或手动刷新会更新 `last_request_time` 并提高处理优先级。

### 6. 前端不保留实时查询

库存上架抽屉和开箱记录 C5 在售挂单弹窗都不再直接请求 C5。

用户打开入口或点击刷新时，只会申请本地快照刷新：

- 快照不存在：创建快照，进入刷新队列。
- 快照已过期：提前 `next_refresh_time`。
- 用户手动刷新：提前 `next_refresh_time` 并提高优先级。

所有 C5 请求由后台任务统一执行。

## 数据模型

### 表名

```text
c5_market_price_snapshot
```

表语义：

```text
C5市场价格最新快照表
```

一行代表一个 C5 在售参考查询维度的最新快照。

### 字段设计

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `bigint` | 主键 ID |
| `app_id` | `integer` | Steam 应用 ID，CS2 固定 730 |
| `market_hash_name` | `varchar(255)` | Steam 市场 Hash 名称 |
| `range_type` | `varchar(32)` | 区间类型，`ALL` 不筛磨损，`WEAR` 指定磨损区间 |
| `wear_min` | `numeric(12,8)` | 查询最小磨损，`ALL` 固定 0 |
| `wear_max` | `numeric(12,8)` | 查询最大磨损，`ALL` 固定 1 |
| `page_num` | `integer` | C5 查询页码，首期固定 1 |
| `page_size` | `integer` | C5 查询页大小，首期固定 50 |
| `lowest_price` | `numeric(12,2)` | 当前快照最低价 |
| `avg_price` | `numeric(12,2)` | 当前快照平均价 |
| `sample_count` | `integer` | 当前快照样本数量 |

| `next_refresh_time` | `timestamp` | 下次应刷新时间 |
| `last_fetch_time` | `timestamp` | 最近一次尝试刷新时间 |
| `last_success_time` | `timestamp` | 最近一次成功刷新时间 |
| `last_request_time` | `timestamp` | 最近一次被前端或业务关注的时间 |

| `create_time` | `timestamp` | 创建时间 |
| `update_time` | `timestamp` | 更新时间 |

### 状态枚举

```text
PENDING     等待刷新
REFRESHING  刷新中
SUCCESS     最近刷新成功
FAILED      最近刷新失败
DISABLED    已停用
```

### `listings_json` 精简字段

每条挂单只保存前端展示和辅助定价需要的字段：

```json
{
  "productId": "C5在售商品ID",

  "wear": 0.12345678,

  "acceptBargain": false,
  "sellerUid": "卖家UID",
  "imageUrl": "图片地址",
  "assetId": "资产ID"
}
```

首期不保存完整 C5 原始响应，不保存完整 `assetInfo`。

## 后端接口设计

### 快照查询接口

两个前端入口统一使用本地快照查询能力。

建议接口语义：

```text
GET /api/c5/market-price-snapshots/reference
```

请求参数：

| 参数 | 说明 |
|---|---|
| `marketHashName` | Steam 市场 Hash 名称 |
| `rangeType` | `ALL` 或 `WEAR` |
| `wearMin` | 最小磨损，`WEAR` 必传 |
| `wearMax` | 最大磨损，`WEAR` 必传 |
| `limit` | 前端展示数量，默认 10，最大 50 |

返回字段：

| 字段 | 说明 |
|---|---|
| `records` | 挂单参考列表 |
| `lowestPrice` | 最低价 |
| `avgPrice` | 平均价 |
| `sampleCount` | 样本数量 |
| `snapshotStatus` | 快照状态 |
| `lastSuccessTime` | 最近成功刷新时间 |
| `refreshIntervalSeconds` | 刷新间隔 |
| `stale` | 是否已超过刷新周期 |
| `message` | 前端提示文案 |

查询行为：

- 快照不存在：创建 `PENDING` 快照，`next_refresh_time = now()`，返回空列表与排队状态。
- 快照存在且未过期：返回现有快照。
- 快照存在且已过期：返回旧快照，并提前 `next_refresh_time = now()`。
- 不直接调用 C5。

### 手动申请刷新接口

建议接口语义：

```text
POST /api/c5/market-price-snapshots/refresh-request
```

行为：

- 创建或更新快照。
- 更新 `last_request_time = now()`。
- 提高 `refresh_priority`。
- 设置 `next_refresh_time = now()`。
- 不直接调用 C5。

## 定时刷新任务设计

### 调度频率

XXL-JOB 每 1 分钟触发一次价格快照刷新任务。

任务内部只处理：

```text
refresh_enabled = true
next_refresh_time <= now()
status <> 'REFRESHING'
```

### 每轮处理数量

每轮最多处理 50 条快照。

排序规则：

```text
refresh_priority desc
last_request_time desc
next_refresh_time asc
id asc
```

如果积压超过 50 条，剩余记录等待下一轮任务。

### 刷新成功规则

刷新成功后：

```text
status = SUCCESS
fail_count = 0
last_error_message = ''
last_fetch_time = now()
last_success_time = now()
next_refresh_time = now() + refresh_interval_seconds
fetch_count = fetch_count + 1
lowest_price / avg_price / sample_count / has_more / listings_json 更新为最新结果
last_fetch_account_id = 本次使用的账号 ID
```

### 刷新失败规则

刷新失败后：

```text
status = FAILED
fail_count = fail_count + 1
last_error_message = 错误摘要
last_fetch_time = now()
fetch_count = fetch_count + 1
next_refresh_time = now() + min(5 * fail_count, 30) 分钟
last_fetch_account_id = 本次使用的账号 ID
```

连续失败退避：

```text
第 1 次失败：5 分钟后重试
第 2 次失败：10 分钟后重试
第 3 次失败：15 分钟后重试
最多退避到 30 分钟
```

## AppKey 池与限流设计

### AppKey 池

后台刷新从可用 C5 扫货账号 AppKey 池中选择调用凭证。

规则：

- 快照数据全局共享，不绑定账号。
- AppKey 池来源为启用且 C5 AppKey 非空的 C5 扫货账号。
- 选择策略采用轮询。
- 轮询游标放 Redis，不落库。
- 每次刷新记录 `last_fetch_account_id`。
- 日志中不得输出 AppKey 明文。

Redis 游标 key：

```text
c5:market-price:appkey-pool:cursor
```

### Redis 令牌桶限流

C5 市场查询统一采用 Redis 令牌桶限流。

`/merchant/market/v2/products/search` 限流规则：

```text
桶容量：1
补充速率：1 token / 秒
每次请求消耗：1 token
```

建议 Redis key：

```text
c5:market-price:products-search:rate-limit
```

`/merchant/market/v2/products/list` 也通过后台队列执行，首期可共用同一个 C5 市场查询令牌桶，避免绕过统一市场查询预算。

获取不到令牌时：

- 本轮不直接调用 C5。
- 快照保持待刷新状态。
- 等待下一轮 XXL-JOB 调度。

## 前端交互设计

### 库存上架抽屉

打开抽屉时：

- 根据当前商品和磨损区间查询本地快照。
- 不直接请求 C5。
- 默认展示前 10 条参考挂单。
- 支持展开查看最多 50 条。
- 底部展示：`价格每 5 分钟刷新`。

用户点击刷新：

- 调用申请刷新接口。
- 不等待 C5 实时返回。
- 展示排队刷新状态。

### 开箱记录 C5 在售挂单弹窗

打开弹窗时：

- 有当前磨损或用户选择磨损区间时，查询 `WEAR` 快照。
- 用户选择“不筛磨损（按价格）”时，查询 `ALL` 快照。
- 不直接请求 C5。
- 默认展示前 10 条参考挂单。
- 支持展开查看最多 50 条。
- 底部展示：`价格每 5 分钟刷新`。

### 降级展示

没有快照：

```text
暂无价格参考，已加入刷新队列
```

有快照但过期：

```text
继续展示旧快照，并显示价格每 5 分钟刷新
```

刷新中：

```text
继续展示旧快照，并显示正在刷新价格参考
```

刷新失败且有旧快照：

```text
继续展示旧快照，并显示最近刷新失败，可稍后重试
```

刷新失败且没有成功快照：

```text
暂无价格参考，最近刷新失败
```

## 验收标准

- 库存上架抽屉打开时不直接调用 C5。
- 开箱记录 C5 在售挂单弹窗打开时不直接调用 C5。
- 同一个 `app_id + market_hash_name + range_type + wear_min + wear_max` 只生成一条快照。
- 后台任务每 1 分钟扫描到期快照，每轮最多处理 50 条。
- 每条快照刷新使用 `pageNum=1`、`pageSize=50`。
- `WEAR` 类型刷新走 `/merchant/market/v2/products/search`。
- `ALL` 类型刷新走 `/merchant/market/v2/products/list`。
- C5 市场查询调用经过 Redis 令牌桶限流。
- AppKey 使用可用 C5 扫货账号轮询选择。
- 快照刷新成功后更新 `listings_json`、最低价、平均价、样本数和下次刷新时间。
- 快照刷新失败后按失败次数退避，最多 30 分钟。
- 前端默认展示前 10 条，可展开查看最多 50 条。
- 前端底部展示“价格每 5 分钟刷新”。

## 兼容性与风险

### 兼容性

- 不删除现有 C5 SDK 封装。
- 不改变库存上架提交流程。
- 不改变开箱记录主列表数据结构。
- 新快照表为追加式变更。
- 前端入口从实时查询切换为快照查询后，应保留原有展示字段语义。

### 风险

- 快照不是实时价格，前端必须展示刷新周期提示。
- 如果待刷新快照过多，部分冷门商品会延迟刷新。
- 如果可用 AppKey 池为空，所有快照会进入失败或等待状态。
- Redis 不可用时，令牌桶和轮询游标不可用，后台刷新应停止或失败，不应绕过限流直连 C5。
