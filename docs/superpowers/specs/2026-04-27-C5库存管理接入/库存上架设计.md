# C5 库存上架设计

## 1. 背景

库存管理页已新增点击库存卡片打开上架抽屉的前端交互。当前抽屉可以展示单个定价、批量定价、全局价格同步和 C5 同磨损参考区域，但批量子项与市场参考价格仍为前端 mock 数据，提交上架也只弹出提示，没有真实接口。

当前库存列表接口按聚合口径返回卡片：`account_id + market_hash_name/name + exterior_name + if_tradable` 聚合后返回代表性库存记录，并通过 `quantity` 表示同组库存数量。由于 C5 上架必须使用每个真实库存资产的 `token` 和 `styleToken`，批量上架不能直接使用聚合卡片 DTO，必须先查询聚合背后的真实库存明细。

## 2. 目标

本次设计覆盖库存上架真实接口接入：

1. 点击聚合库存卡片后，前端能查询该卡片背后的真实库存明细。
2. 用户能在抽屉内对单个或多个库存资产设置上架价格。
3. 后端根据本地库存 ID 查询 `token` 和 `styleToken`，调用 C5 库存饰品上架接口。
4. 单个上架和批量上架复用同一个后端提交接口。
5. 上架完成后返回成功数量、失败数量、成功资产和失败信息，前端刷新库存列表。

## 3. 非目标

上架主链路不把以下内容并入提交接口：

- 不新增自动定价策略、自动上架任务或定时上架。
- 不在前端直接提交 C5 `token` / `styleToken`。
- 不在本设计中拆分贴纸、宝石、样式等子表。

同磨损参考价格和上架手续费作为上架抽屉的辅助查询能力，通过独立后端接口接入，不影响 `POST /api/c5/inventory/listings` 的提交契约。

## 4. 外部接口契约

### 4.1 C5 库存饰品上架

```text
POST /merchant/sale/v2/create
```

Query：

- `app-key`：C5 AppKey，使用账号级 `c5AppKey`。

Body：

```json
{
  "dataList": [
    {
      "price": 43.2,
      "description": "",
      "acceptBargain": 0,
      "token": "库存列表返回的 token",
      "styleToken": "库存列表返回的 styleToken"
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `price` | number | 是 | 饰品上架价格 |
| `description` | string | 否 | 上架描述，默认空字符串 |
| `acceptBargain` | integer | 是 | 是否允许还价：`0` 否，`1` 是 |
| `token` | string | 是 | C5 库存列表返回的库存资产标识 |
| `styleToken` | string | 是 | C5 库存列表返回的款式标识 |

单个上架与批量上架使用同一 C5 接口：`dataList` 只有 1 条时为单个上架，多条时为批量上架。

响应：

```json
{
  "success": true,
  "data": {
    "shopOn": true,
    "succeed": 1,
    "failed": 0,
    "failedList": [],
    "successList": [
      {
        "assetId": "39559751235",
        "productId": "1340423455735046144"
      }
    ],
    "highPriceItemIdList": [],
    "priceCheckResult": null
  },
  "errorCode": 0,
  "errorMsg": null,
  "errorData": null,
  "errorCodeStr": null
}
```

`data` 字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `shopOn` | boolean | 店铺是否开启 |
| `succeed` | integer | 成功数量 |
| `failed` | integer | 失败数量 |
| `successList` | array | 成功上架列表 |
| `successList[].assetId` | string | 饰品唯一 ID |
| `successList[].productId` | string | 上架后的在售 ID |
| `failedList` | array | 失败列表 |
| `highPriceItemIdList` | array | 定价过高饰品列表 |
| `priceCheckResult` | null / object | 价格检查结果，当前文档示例为 `null` |

### 4.2 C5 在售列表查询

```text
POST /merchant/market/v2/products/list
POST /merchant/market/v2/products/search
```

用途：按 `marketHashName` 查询 C5 在售挂单，用作上架抽屉“同平台磨损参考”。无磨损区间时使用 `/products/list`；有 `wearMin/wearMax` 时使用 `/products/search` 将磨损区间直接传给 C5。两条接口都按当前页单次请求执行，不在一次后端请求内扫描多页。

Body：

```json
{
  "appId": 730,
  "marketHashName": "AK-47 | Redline (Field-Tested)",
  "wearMin": 0.07,
  "wearMax": 0.15,
  "pageNum": 1,
  "pageSize": 10
}
```

返回使用项目现有 SDK `C5ProductListResponse`，前端只展示 `productId`、`price`、`delivery`、`acceptBargain`、`sellerUid`、`assetInfo.wear`、`img` 等字段。

### 4.3 C5 上架手续费计算

```text
POST /merchant/sale/v1/calculate
```

用途：按上架价格、库存 `token` 和 `styleToken` 查询 C5 官方手续费结果，用于替换前端固定比例预估。

Body：

```json
{
  "dataList": [
    {
      "price": 115,
      "styleToken": "库存列表返回的 styleToken",
      "token": "库存列表返回的 token"
    }
  ]
}
```

返回 `data` 为数组，单项包含 `assetId`、`itemId`、`fee`、`freeFeePrice`。本地接口不让前端直接提交 `token/styleToken`，而是由前端传本地库存明细 ID，后端查本地库存快照后组装 C5 请求。

## 5. 后端接口设计

### 5.1 聚合库存明细接口

```text
GET /api/c5/inventory/items
```

用途：打开上架抽屉时，按聚合卡片口径查询真实库存资产明细，供批量定价和提交上架使用。

Query：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `accountId` | number | 是 | C5 扫货账号 ID |
| `marketHashName` | string | 否 | 聚合卡片英文名称 |
| `name` | string | 否 | 聚合卡片中文名称，`marketHashName` 为空时兜底 |
| `exteriorName` | string | 否 | 外观名称，与当前聚合口径一致 |
| `ifTradable` | boolean | 否 | 是否可交易，与当前聚合口径一致 |
| `page` | number | 否 | 页码，默认 1 |
| `pageSize` | number | 否 | 每页数量，默认 200 |

返回：

```json
{
  "records": [
    {
      "id": 10001,
      "accountId": 1,
      "accountName": "C5 主账号",
      "assetId": "39559751235",
      "price": 11.34,
      "wear": 0.09774267925,
      "ifTradable": true,
      "tradableTime": null,
      "name": "封装的毁灭之手终端机",
      "marketHashName": "Sealed Graffiti | ...",
      "imageUrl": "https://..."
    }
  ],
  "total": 125,
  "current": 1,
  "size": 200
}
```

规则：

1. 只返回当前用户自己的库存。
2. 只返回 `inventory_status = IN_STOCK` 且 C5 `status = 0` 的正常库存记录。
3. 查询条件必须与聚合卡片可上架口径一致，避免抽屉明细和卡片数量不一致。
4. 返回 DTO 不包含 `token` 和 `styleToken`，这两个字段只在后端提交上架时读取。

### 5.2 库存上架提交接口

```text
POST /api/c5/inventory/listings
```

用途：提交单个或批量库存资产上架。

入参：

```json
{
  "accountId": 1,
  "description": "",
  "acceptBargain": 0,
  "items": [
    {
      "inventoryItemId": 10001,
      "price": 11.34
    },
    {
      "inventoryItemId": 10002,
      "price": 11.75
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `accountId` | number | 是 | C5 扫货账号 ID |
| `description` | string | 否 | 上架描述，默认空字符串 |
| `acceptBargain` | integer | 是 | 是否允许还价：`0` 否，`1` 是 |
| `items` | array | 是 | 待上架库存资产列表 |
| `items[].inventoryItemId` | number | 是 | 本地库存快照 ID |
| `items[].price` | number | 是 | 上架价格 |

返回：

```json
{
  "accountId": 1,
  "shopOn": true,
  "succeed": 2,
  "failed": 0,
  "successList": [
    {
      "assetId": "39559751235",
      "productId": "1340423455735046144"
    }
  ],
  "failedList": [],
  "highPriceItemIdList": [],
  "priceCheckResult": null
}
```

规则：

1. 前端只提交 `inventoryItemId` 和价格，不提交 C5 `token` / `styleToken`。
2. 后端校验账号属于当前用户，且每条库存记录属于该账号和当前用户。
3. 后端只允许 `inventory_status = IN_STOCK` 且 C5 `status = 0` 的正常库存参与上架。
4. 后端从本地库存快照读取 `token`、`styleToken`，组装 C5 `dataList`。
5. `price` 必须大于 0，保留两位小数。
6. `items` 不能为空，批量数量上限按 C5 实际限制或后端安全阈值控制；如 C5 文档未明确，先按后端 `100` 条上限设计。
7. C5 返回业务失败时保留原始失败信息，并转换为前端可展示结果。

### 5.3 同平台磨损参考接口

```text
GET /api/c5/inventory/market-references
```

用途：上架抽屉内按当前库存名称和磨损区间查询 C5 在售挂单，替换前端 mock 参考价。

Query：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `accountId` | number | 是 | C5 扫货账号 ID，用于读取账号级 `c5AppKey` |
| `marketHashName` | string | 是 | 当前库存英文名称 |
| `wear` | number | 否 | 当前库存磨损 |
| `wearMin` | number | 否 | 手动指定最小磨损 |
| `wearMax` | number | 否 | 手动指定最大磨损 |
| `pageNum` | number | 否 | 页码，默认 1 |
| `pageSize` | number | 否 | 每页数量，默认 10 |

规则：

1. 后端校验账号属于当前用户。
2. 有 `wearMin/wearMax` 时优先使用手动区间；否则根据 `wear ± 0.01` 自动生成同磨损参考区间，并限制在 `0 ~ 1`。
3. 有磨损区间时调 C5 `/merchant/market/v2/products/search` 并传递 `wearMin/wearMax/pageNum/pageSize`；无磨损区间时调 `/merchant/market/v2/products/list`。
4. 后端每次只请求 C5 当前页一次，避免单次请求内扫描多页触发 C5 429；前端翻页时保持当前磨损区间，仅变更 `pageNum`。
5. 后端按当前页返回的 `assetInfo.wear` 在本地过滤磨损区间作为兜底，不保存到本地库。
6. 前端只展示上一页/下一页；当 C5 当前页返回 `hasMore=false` 时隐藏下一页按钮。
7. 参考列表先按价格升序排序，同价下再按磨损升序排序。

### 5.4 上架手续费计算接口

```text
POST /api/c5/inventory/listing-fee
```

用途：上架抽屉内按当前输入上架价调用 C5 官方手续费计算接口，替换前端固定比例预估。

入参：

```json
{
  "accountId": 1,
  "inventoryItemId": 10001,
  "price": 43.2
}
```

返回：

```json
{
  "accountId": 1,
  "inventoryItemId": 10001,
  "assetId": "40568576749",
  "itemId": "553468090",
  "price": 43.2,
  "fee": 0.86,
  "freeFeePrice": 100,
  "sellerPrice": 42.34,
  "rawData": {}
}
```

规则：

1. 后端校验账号属于当前用户。
2. 后端校验库存明细属于当前用户与账号，且 `inventory_status = IN_STOCK`、C5 `status = 0`。
3. `price` 必须大于 0，保留两位小数。
4. 后端从本地库存快照读取 `token`、`styleToken`，组装 C5 `dataList`。
5. SDK 调用 C5 `/merchant/sale/v1/calculate`。
6. 后端提取官方返回的 `assetId`、`itemId`、`fee`、`freeFeePrice`，同时保留单项原始 `rawData` 便于字段差异排查。

批量堆叠上架使用同一个 C5 `/merchant/sale/v1/calculate` 的 `dataList[]` 能力，后端新增 `POST /api/c5/inventory/listing-fees`，入参为 `accountId` 和 `items[].inventoryItemId/price`，返回 `C5InventoryListingFeeDTO[]`。单条接口保留并复用批量计算逻辑，保证既有单个定价区域不破坏。

## 6. 后端分层设计

按项目现有分层：

```text
Controller -> Service -> MapperManager -> Mapper -> Entity
```

建议新增或扩展：

- SDK：在 `C5InventoryClient` 或与销售相关 client 中新增 `createListing` 封装，对应 `/merchant/sale/v2/create`。
- Param：
  - `C5InventoryItemListParam`
  - `C5InventoryListingCreateParam`
  - `C5InventoryListingCreateItemParam`
- DTO：
  - `C5InventoryAssetDTO`
  - `C5InventoryListingResultDTO`
  - `C5InventoryListingSuccessDTO`
- Service：`C5InventoryService` 增加明细查询与上架提交方法。
- MapperManager：封装按聚合条件查询明细、按 ID 列表查询库存记录的数据库访问。
- Mapper：只保留 SQL 映射，不承载业务判断。

后端流程：

1. Controller 收参并交给 Service。
2. Service 校验用户、账号归属、价格和明细列表。
3. Service 通过 MapperManager 查询库存记录。
4. Service 校验库存记录均属于当前用户与账号。
5. Service 读取账号 `c5AppKey`，组装 C5 `dataList`。
6. SDK 调用 C5 `/merchant/sale/v2/create`。
7. Service 将 C5 响应转换为本地 DTO 返回。
8. 前端收到成功结果后刷新库存列表与统计。

## 7. 本地状态设计

当前 `c5_inventory_item.inventory_status` 只有：

- `IN_STOCK`
- `REMOVED`

上架成功后需要识别“已提交上架/在售”状态，否则库存页刷新前仍可能显示可上架。推荐两种后续落地方式：

1. 最小方案：新增 `LISTING` 或 `ON_SALE` 库存状态，上架成功的 `assetId` 更新为该状态。
2. 可追溯方案：新增库存上架记录表，保存本地库存 ID、C5 `productId`、上架价格、上架结果和失败原因。

本设计推荐先采用最小方案；如果后续需要审计、重试或对账，再新增上架记录表。

## 8. 前端对接设计

页面：`niro-client/src/views/InventoryManagement.vue`

当前新增抽屉保留，但需要替换以下 mock 逻辑：

1. `handleOpenSellDrawer`：打开抽屉后，如果 `quantity > 1`，调用聚合库存明细接口填充表格。
2. `generateMockSubItems`：删除或替换为真实明细加载。
3. `handleConfirmSingleSell`：调用上架提交接口，`items` 只传当前行。
4. `handleConfirmSell`：收集已选明细及价格，调用同一个上架提交接口。
5. `refreshMockMarketData`：本次不接真实接口，保留为后续市场参考接入点，文案不要承诺“实时挂单”。
6. 上架成功后关闭抽屉，刷新库存列表和统计。
7. 批量堆叠抽屉明细加载完成后调用批量手续费接口，表格展示每行手续费与到手价。
8. 批量表格内单行价格变更后 debounce 重算该行手续费；同步全局价后批量重算所选行。

## 9. 错误处理

- 未选择任何明细：前端提示“请至少选择一件饰品”。
- 价格为空、非数字或小于等于 0：前端阻止提交，后端再次校验。
- 账号不存在或不属于当前用户：后端拒绝。
- 库存记录不存在、已移除或不属于当前账号：后端拒绝。
- 库存缺少 `token` 或 `styleToken`：后端拒绝该项上架。
- C5 返回店铺未开启：前端展示 `shopOn=false` 的结果提示。
- C5 返回部分失败：接口仍返回结果 DTO，前端展示成功/失败数量和失败列表。
- C5 HTTP 或 SDK 异常：沿用项目全局异常处理。

## 10. 验证方式

后端：

- 使用指定 JDK 编译 `niro-web`。
- 验证聚合明细接口只返回当前用户、当前账号、`IN_STOCK` 数据。
- 验证单个上架请求能组装 1 条 C5 `dataList`。
- 验证批量上架请求能组装多条 C5 `dataList`。
- 验证价格、空列表、跨账号库存、缺少 `token/styleToken` 的拒绝逻辑。
- 验证 C5 部分失败时返回成功与失败明细。

前端：

- 用户手动验证点击卡片打开抽屉。
- 用户手动验证聚合卡片明细加载、勾选、全局价同步、单行上架、批量上架。
- 用户手动验证上架成功后库存列表刷新。
- 按项目约定，前端 dev/build/type-check/test 由用户手动处理。

## 11. 已确认结论

- [x] 单个上架和批量上架共用 C5 `/merchant/sale/v2/create`。
- [x] 前端不直接提交 C5 `token` / `styleToken`。
- [x] 聚合卡片需要先查询真实库存明细，再执行批量上架。
- [x] C5 同磨损参考价格不纳入本次上架接口设计。
- [x] 上架设计作为当前 C5 库存管理主题的新增子文档沉淀。
