# 开箱记录页：分页列表、全量汇总与编辑详情拆分设计

## 背景
当前开箱记录页把列表、顶部汇总卡片和编辑器明细都建立在同一份 `unboxApi.list()` 全量数据之上。

现状的问题是：
1. 列表接口一次返回全部记录及全部 `items` 明细，页面首屏负载偏重。
2. 表格分页只是前端本地分页，不是真正的服务端分页。
3. 编辑按钮直接读取本地缓存的整条记录，无法体现“列表只返回记录级数据、编辑时再拉明细”的接口职责拆分。

后端已经补出更合适的接口方向：
- `GET /unbox/record/page`：分页列表，只返回记录级数据和列表展示所需汇总字段。
- `GET /unbox/record/{id}`：单条记录详情，包含明细，用于编辑。

用户进一步确认：
- 列表必须切成真正的服务端分页。
- 顶部 4 张汇总卡片仍然要表示“当前筛选结果的全量汇总”，不能退化为“当前页汇总”。
- 页面交互和样式保持不变，改动聚焦，不做无关重构。

因此需要在现有后端基础上再补一个独立汇总接口，并让前端分别消费分页、汇总和详情三类数据。

## 目标
1. 表格改为真正的服务端分页。
2. 列表请求不再返回 `items` 明细。
3. 点击编辑时，再按记录 ID 请求详情接口拉取明细。
4. 顶部 4 张卡片继续显示当前筛选条件下的全量汇总值。
5. 保持现有页面布局、交互习惯、表格列和编辑器样式不变。

## 范围
### 本次包含
- 后端新增开箱记录汇总接口。
- 前端 API 与类型定义按分页/汇总/详情拆分。
- `UnboxRecord.vue` 改造数据流，使表格、卡片、编辑器分别使用各自数据源。
- 分页切换、筛选切换、编辑加载链路调整。

### 本次不包含
- 不改页面视觉样式。
- 不改编辑器字段和交互细节。
- 不改 OCR 录入链路。
- 不改已有保存、新增、删除接口的语义。
- 不新增缓存、预取、并发取消等超出当前需求的优化机制。

## 现状
### 前端
`niro-client/src/views/UnboxRecord.vue` 目前使用一份 `batches` 数据：
- 列表表格从 `batches` 派生 `batchSummaryRows`
- 顶部 4 张卡片从 `filteredBatchSummaryRows` 聚合计算
- 点击编辑时 `openEditEditor` 直接从 `batches` 中找到目标批次并拷贝到 `draftBatch`

这意味着：
- 列表数据必须带明细，否则现有编辑逻辑无法工作。
- 顶部卡片只能依赖前端拿到的全量列表来计算。
- 前端分页只是 `slice` 当前数组，不是真分页。

### 后端
当前已具备：
- `GET /unbox/record/page`：记录级分页接口
- `GET /unbox/record/{id}`：详情接口，返回完整记录和明细

仍缺少：
- `GET /unbox/record/summary`：基于当前筛选条件的全量汇总接口

## 方案比较
### 方案 A：分页接口 + 独立汇总接口 + 详情接口（推荐）
- `/page` 只负责表格分页 records
- `/summary` 只负责顶部卡片汇总
- `/{id}` 只负责编辑详情

优点：
- 职责边界清楚
- 与当前后端 `Page<T>` 风格一致
- 不需要在分页 records 中混入无关明细
- 前端状态拆分后更稳定

缺点：
- 需要补一个后端接口

### 方案 B：把 summary 塞进 `/page` 响应
优点：
- 前端只发一条请求

缺点：
- 会污染标准分页返回模型
- 后续复用差
- 让分页接口承担两种职责

### 方案 C：前端用大 pageSize 再自己算汇总
优点：
- 看上去后端少改一点

缺点：
- 本质上还是拉全量数据到前端
- 与本次优化目标相反
- 数据量变大时问题仍在

**结论：采用方案 A。**

## 设计

### 1. 后端接口设计
#### 1.1 分页接口
保留现有：
- `GET /unbox/record/page`

语义：
- 根据 `page`、`pageSize`、`startDate`、`endDate` 返回当前页记录。
- records 中不带 `items` 明细。
- records 中保留列表渲染所需字段：日期、数量、成本、手续费、利润、利润率、状态等。

#### 1.2 详情接口
保留现有：
- `GET /unbox/record/{id}`

语义：
- 返回单条完整记录及其 `items` 明细。
- 编辑器仅在用户点击编辑时调用。

#### 1.3 汇总接口
新增：
- `GET /unbox/record/summary`

请求参数：
- `startDate`
- `endDate`

返回值语义：
- 返回当前筛选范围下的全量汇总，而不是当前页汇总。
- 字段与顶部 4 张卡片一一对应：
  - `totalBatches`
  - `totalPurchaseCost`
  - `totalFee`
  - `totalActualNetProfit`

该接口不返回列表 records，不承担分页职责。

### 2. 前端 API 与类型拆分
#### 2.1 `src/api/unbox.ts`
新增：
- `page(params)` → `/unbox/record/page`
- `summary(params)` → `/unbox/record/summary`

保留：
- `getDetail(id)`
- `create(data)`
- `update(id, data)`
- `delete(id)`
- `ocrImage(file)`

旧的 `list()` 不再作为页面主链路使用。是否保留取决于代码是否还有其他地方引用；若无引用，可直接删除。

#### 2.2 `src/types/unbox.ts`
新增：
- `UnboxRecordPageDTO`
- `UnboxRecordSummaryDTO`
- 如前端请求封装未已有通用分页类型，则补一个本页专用分页响应类型；若已有通用 `PageResult` 风格类型，优先复用现有模式。

保留：
- `UnboxRecordDTO`：仅用于详情和编辑器
- `UnboxRecordItemDTO`
- `UnboxRecordSaveParam`
- `UnboxRecordOcrResult`

### 3. 页面状态重构
`niro-client/src/views/UnboxRecord.vue` 中，原来单一的 `batches` 需要拆成三类状态：

#### 3.1 列表状态
- 当前页 records
- 当前页分页信息：`current`、`pageSize`、`total`
- 列表 loading

这部分只服务表格，不参与编辑器数据来源。

#### 3.2 汇总状态
- `totalBatches`
- `totalPurchaseCost`
- `totalFee`
- `totalActualNetProfit`
- 汇总 loading（可与列表共用，也可独立）

这部分只服务顶部卡片，不再从当前页数据反推。

#### 3.3 编辑状态
- `draftBatch`
- `editingBatchId`
- 编辑弹窗显隐
- 明细 OCR 状态
- 保存 loading
- 详情 loading（打开编辑时使用）

这部分只由 `getDetail(id)` 填充，避免列表 records 再承载明细。

### 4. 前端数据流
#### 4.1 页面初始化
页面初始化时：
1. 读取当前筛选条件
2. 请求 `/unbox/record/summary`
3. 请求 `/unbox/record/page`

卡片和表格并行加载，互不依赖。

#### 4.2 筛选变化
当日期范围或周期变化时：
1. 重置页码到第一页
2. 重新请求 summary
3. 重新请求 page

这样可以保持：
- 卡片口径始终对应当前筛选条件
- 表格始终展示筛选后的第一页

#### 4.3 分页变化
当分页组件切页或改 pageSize 时：
1. 只请求 page
2. 不重新请求 summary

因为 summary 口径只依赖筛选条件，不依赖当前页。

#### 4.4 点击编辑
当点击“编辑”时：
1. 先校验目标记录 ID 存在
2. 调用 `unboxApi.getDetail(id)`
3. 用详情结果填充 `draftBatch`
4. 再打开编辑器或在打开后展示加载结果

要求：
- 不再从当前表格行本地拼装编辑数据。
- 编辑器所需明细全部来自详情接口。

#### 4.5 保存成功后
新增/更新成功后：
1. 关闭编辑器
2. 重新请求当前页 page
3. 重新请求当前筛选条件的 summary

删除成功后：
1. 重新请求当前页 page
2. 重新请求当前筛选条件的 summary
3. 若当前页被删空，页码回退到有效页

### 5. 页面展示保持不变
本次改造不改变以下内容：
- 顶部 4 张卡片的布局和样式
- 表格列结构与操作按钮位置
- 编辑弹窗样式、表单结构、明细表格结构
- 现有排序、筛选按钮、快捷日期按钮、周期按钮

只替换数据来源与加载时机。

### 6. 错误处理
#### 列表/汇总加载失败
- 保持现有 `MessagePlugin.error(...)` 风格
- 列表失败时表格保持空态或保留安全默认值
- 汇总失败时卡片显示默认 0 值或最近一次稳定值，但不抛出额外 UI 结构变化

为避免状态混乱，推荐默认值方案：
- summary 加载失败时回退到全 0 汇总
- page 加载失败时回退到空列表 + 正确关闭 loading

#### 编辑详情加载失败
- 点击编辑但详情请求失败时，不进入错误数据态
- 给出错误提示
- 编辑器不展示伪造明细

推荐行为：
- 请求成功后再填充草稿并打开编辑器；若希望保持现有交互节奏，也可先打开再显示 loading，但不额外扩展界面结构。
- 为保持改动聚焦，优先采用“请求成功后再进入编辑器”。

### 7. 兼容性与边界
- 现有保存入参结构不变。
- 现有详情接口返回结构不变。
- 现有卡片文案和表格列文案不变。
- 现有筛选条件字段名不变，继续使用 `startDate`、`endDate`。
- 不新增本地缓存，不引入 store，不做跨页预取。

## 职责边界
### 后端
- `/page`：表格分页
- `/summary`：顶部汇总
- `/{id}`：编辑详情

### 前端页面
- 卡片区只消费 summary
- 列表区只消费当前页 page records
- 编辑器只消费 detail

这样每一块数据的来源都单一明确，后续改动不会互相牵连。

## 测试与验证
### 后端
- 补充汇总接口后，按项目 JDK 规则执行最小必要编译验证。

### 前端
按当前协作边界：
- 不主动跑前端 dev/build/type-check/lint，由用户自行验证前端。

建议用户手动验证：
1. 页面初始化时，顶部卡片与表格都正常加载。
2. 切换日期范围后，卡片与表格同时更新。
3. 切分页时，只有表格变化，卡片口径不抖动。
4. 点击编辑时，能正确拉取该条记录完整明细。
5. 保存后，当前页列表与顶部卡片一起刷新。
6. 删除后，当前页列表与顶部卡片一起刷新。
7. 分页为空页时，页码能正确回退。

## 实现顺序
1. 后端新增 `/unbox/record/summary` DTO、Service、Controller 逻辑。
2. 前端补 `page` / `summary` API 与类型。
3. 页面拆分列表状态、汇总状态、编辑详情状态。
4. 改造筛选、分页、编辑、保存、删除的刷新链路。
5. 做最小必要验证并交付。
