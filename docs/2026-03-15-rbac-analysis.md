# Niro 权限系统现状分析

日期：2026-03-15

## 1. 结论

当前项目的权限系统已经有了 `用户 -> 角色 -> 菜单/权限` 的基础表和基础代码，但还停留在“半成品”状态，更准确地说是：

- 已完成登录态校验，基于 Sa-Token 能拦截未登录请求。
- 已完成动态菜单路由的基础链路，前端会根据后端返回的菜单树生成页面路由。
- 已有角色、菜单、用户角色、角色菜单 5 张核心表。
- 但还没有形成可用的、闭环的 RBAC 系统。

目前最关键的问题不是“功能不够多”，而是“核心链路不一致”：

- 数据库表结构和 Java 实体不同步。
- 普通用户角色获取逻辑实际上失效。
- 后端没有真正做接口级权限校验。
- 前端只有菜单级控制，按钮级权限几乎没接入。
- 初始化 SQL 已经和当前真实表结构脱节。

如果目标只是“小项目可用的基础权限管理”，建议把目标收敛为：

1. 登录后能正确拿到用户角色和权限码。
2. 菜单按角色正常展示。
3. 关键后端接口按权限码拦截。
4. 提供最小管理能力：用户分配角色、角色分配菜单。

这个范围足够支撑小项目，不需要上复杂的数据权限、部门树、按钮树、租户、多级审批。

## 2. 当前权限系统的真实状态

### 2.1 数据库层

PostgreSQL 当前存在 5 张权限相关表：

- `sys_user`
- `sys_role`
- `sys_menu`
- `sys_user_role`
- `sys_role_menu`

当前实际数据量：

- `sys_user`: 3 条
- `sys_role`: 2 条
- `sys_menu`: 13 条
- `sys_user_role`: 2 条
- `sys_role_menu`: 15 条

当前角色与用户关系：

- `admin(id=1)` 绑定角色 `超级管理员(role_id=1)`
- `liyl(id=2)` 没有任何角色
- `senlan(id=3)` 绑定角色 `普通用户(role_id=2)`

### 2.2 数据完整性问题

`sys_role_menu` 存在明显脏数据：

- `role_id=1` 关联了 `menu_id=15 ~ 25`
- 这些 `menu_id` 在 `sys_menu` 里已经不存在
- 实际可联表出来的有效菜单只剩很少一部分

这说明当前库里已经出现了“历史菜单 ID 残留”，而且数据库层没有外键约束兜底。

当前这 5 张表的约束情况也说明了问题：

- 有主键
- `sys_user.username` 有唯一约束
- 没有看到 `sys_user_role -> sys_user/sys_role` 的外键
- 没有看到 `sys_role_menu -> sys_role/sys_menu` 的外键

这会直接导致：

- 角色菜单孤儿数据可以长期存在
- 删菜单、重建菜单后，旧关联不会自动失效
- 代码层必须自己做数据修复，否则权限结果会漂移

## 3. 表结构与代码映射对照

### 3.1 `sys_role` 不同步最严重

数据库实际存在字段：

- `role_id`
- `role_name`
- `role_key`
- `role_sort`
- `data_scope`
- `status`
- `del_flag`
- `create_by`
- `create_time`
- `update_by`
- `update_time`
- `remark`

但当前 Java 实体 `SysRole` 已经删除了关键字段：

- 缺少 `roleKey`
- 缺少 `menuCheckStrictly`
- 缺少 `deptCheckStrictly`

其中 `menuCheckStrictly`、`deptCheckStrictly` 是否保留可以讨论，但 `roleKey` 不能删。

原因很直接：

- 角色标识最终要返回给前端
- 超级管理员之外的普通角色，也需要靠 `roleKey` 作为稳定标识
- 现在 `UserController.getInfo()` 里的 `roles` 字段，本质上应该返回 `admin`、`user` 这种角色编码

而当前实体把 `roleKey` 删除后，角色集合已经无法正确计算。

### 3.2 `sys_menu` 与实体基本一致，但存在数据缺口

`sys_menu` 当前实体字段和数据库大体一致，菜单树和路由生成链路也基本能跑通。

但实际数据里仍有问题：

- `id=12` 的菜单 `利润统计`，`name` 为空
- `id=1` 的 `首页` 没有权限码
- `id=11` 的 `订单统计` 没有权限码

这里的含义是：

- `name` 为空会影响前端路由命名、缓存、激活菜单和定位能力
- 没有权限码的页面只能做“菜单可见性控制”，做不了接口或按钮的统一授权

### 3.3 初始化 SQL 已经过期

仓库里的 `niro-server/init-menu.sql` 已经不匹配当前真实表结构。

脚本里使用的是旧字段名：

- `menu_id`
- `menu_name`
- `order_num`
- `component_path`
- `menu_type`
- `perms`
- `is_cache`

但数据库真实字段已经变成：

- `id`
- `title`
- `sort_order`
- `component`
- `type`
- `permission`
- `keep_alive`

这说明当前脚本不能作为可信初始化来源，继续使用只会制造更多脏数据。

## 4. 后端权限链分析

### 4.1 已经实现的部分

当前后端权限链大致是这样：

```text
登录
  -> Sa-Token 记录登录态
  -> WebConfig 拦截未登录请求
  -> /user/getInfo 返回用户基础信息 + roles + permissions
  -> /api/user/menus 返回当前用户菜单树
```

这条链路对应的关键代码位置：

- `UserServiceImpl`
- `UserController`
- `SysRoleServiceImpl`
- `SysMenuServiceImpl`
- `WebConfig`

### 4.2 登录态校验是有的，但只有“是否登录”

`WebConfig` 里注册了 `SaInterceptor`，全局调用的是：

- `StpUtil.checkLogin()`

这意味着当前后端只做了一件事：

- 已登录才能访问大多数接口

但没有做这些事情：

- 按角色拦截接口
- 按权限码拦截接口
- 按资源维度限制操作

代码检索结果里也没有发现这些实现：

- `@SaCheckPermission`
- `@SaCheckRole`
- `StpUtil.checkPermission(...)`
- `StpUtil.checkRole(...)`
- `StpInterface` 自定义权限加载

所以当前系统不能算真正的“后端 RBAC”，只能算“登录校验 + 菜单查询”。

### 4.3 非管理员角色获取逻辑当前基本失效

`SysRoleServiceImpl.selectRolePermissionByUserId()` 现在有三个连续问题：

1. 超级管理员使用硬编码 `userId == 1L`，直接返回 `admin`
2. 非管理员查询角色时，条件写成了 `status = 0`
3. 即使查到角色，方法最后也没有把角色编码放进 `roles` 集合，直接空集合返回

而数据库里当前两条角色数据的 `status` 都是 `1`。

也就是说：

- `admin` 因为硬编码还能拿到 `roles = ["admin"]`
- 普通用户理论上有角色，但代码实际返回的 `roles` 基本为空

这会直接影响前端：

- 用户身份展示不准
- 基于角色的前端逻辑不可用
- 后续如果你想接 `hasRole('user')` 这种逻辑，会直接失效

### 4.4 用户注册后不会自动分配默认角色

`UserServiceImpl.register()` 现在只做了：

- 校验用户名
- 保存 `sys_user`

但没有插入 `sys_user_role`。

这会导致新注册用户天然没有角色，进而出现两种结果：

- `getInfo()` 拿不到角色
- `/api/user/menus` 拿不到可用菜单，或者只拿到空树

这也是当前数据库里 `liyl(id=2)` 没有角色的直接成因之一。

### 4.5 菜单查询链路能跑，但非常依赖数据正确

`SysMenuServiceImpl` 的思路本身是合理的：

- 先查用户角色
- 再查角色菜单
- 最后查菜单表，构造成树

但它有两个现实问题：

1. 它只适合“菜单数据干净、角色菜单关联正确”的前提
2. 它没有处理孤儿关联和历史脏数据

当前库里已经存在 `sys_role_menu` 指向不存在菜单的记录，所以这个链路会天然不稳定。

### 4.6 当前没有“权限管理”后端接口

目前仓库里只有：

- `UserController`
- `SysMenuController`

没有看到这些最小管理接口：

- 用户列表 / 用户分配角色
- 角色列表 / 角色更新
- 菜单列表 / 角色分配菜单

因此当前后端虽然有 RBAC 基础表，但还不能称为“可管理的权限系统”。

## 5. 前端权限链分析

### 5.1 已经实现的部分

前端当前已经具备这些基础能力：

- 登录成功后保存 token
- 访问页面时先请求 `/user/getInfo`
- 再请求 `/api/user/menus`
- 根据后端菜单树动态生成路由
- 左侧菜单从动态路由转换而来

这意味着：

- 菜单级权限控制已经具备雏形
- 只要后端菜单返回正确，页面导航基本能工作

### 5.2 前端权限控制目前主要停留在“菜单可见”

前端有两个权限工具：

- `directive/permission.ts`
- `hooks/usePermission.ts`

但代码检索结果显示：

- `v-permission` 没有真正接到业务页面里
- `usePermission()` 也基本没有业务使用点

所以当前前端的权限控制主要还是：

- 后端不返回菜单，就看不到页面

而不是：

- 页面里某个按钮、操作区、批量操作按权限显隐

这意味着按钮级权限目前基本没落地。

### 5.3 普通用户当前菜单配置不完整

数据库里 `普通用户(role_id=2)` 只关联了 3 个菜单：

- `首页`
- `扫货管理`
- `系统管理`

但这 3 个里：

- `首页` 是叶子菜单
- `扫货管理` 是目录
- `系统管理` 是目录

普通用户没有拿到这两个目录下的具体子页面，所以登录后很可能出现：

- 顶层菜单能看到
- 点进去没有可用子项
- 或者被前端“单子节点提升”逻辑绕成空壳

这不是前端 bug，本质上是角色菜单分配不完整。

### 5.4 部分菜单页面并不受后端权限保护

当前菜单里有一些页面，例如：

- `profit`
- `unboxrecord`

前端本身是本地存储逻辑，不依赖后端业务接口。

例如 `niro-client/src/api/profit.ts` 直接使用：

- `localStorage`

这意味着即便它们被挂进了菜单体系里，实际保护边界也只是：

- 菜单能不能点进去

而不是：

- 后端能不能拒绝非法访问

对于小项目这不是不能接受，但要认清边界：这类页面的“权限”更像 UI 访问控制，不是完整的服务端授权。

### 5.5 当前前端没有权限管理后台

虽然菜单里有“账号管理”，但现在看到的是业务账号管理，不是系统用户/角色/菜单管理。

当前前端没有这些最小权限管理页面：

- 用户管理
- 角色管理
- 菜单授权

所以即便后端修好，你现在也缺一个操作入口。

## 6. 目前最关键的问题清单

按优先级排序，当前最影响系统可用性的点如下。

### P0：`SysRole` 实体缺少 `roleKey`

影响：

- 非管理员角色编码无法返回
- 前端 `roles` 数据不可用
- 后续所有角色判断都不稳定

### P0：`SysRoleServiceImpl` 逻辑本身有 bug

影响：

- 非管理员用户拿不到角色集合
- 角色体系实际上只对 `admin(id=1)` 特判生效

### P0：注册用户不会自动分配角色

影响：

- 新用户注册后几乎无法正常进入权限体系
- 容易出现“能登录、但没有菜单”的状态

### P0：后端没有接口级权限校验

影响：

- 只要登录成功，就能调用大部分业务接口
- 菜单隐藏不等于接口安全

### P1：`sys_role_menu` 存在孤儿数据

影响：

- 角色菜单结果不可信
- 后续改菜单时容易继续积累历史垃圾数据

### P1：`init-menu.sql` 已经过时

影响：

- 新环境初始化不可靠
- 容易把旧结构数据再次写进现有系统

### P1：普通用户角色菜单分配不完整

影响：

- 正常用户体验不完整
- 看起来像是权限系统坏了，实际上是数据没配完

### P2：按钮级权限没有实际接入

影响：

- 前端细粒度控制没落地
- 只能控制页面入口，不能控制页面内操作

### P2：菜单数据质量一般

表现：

- 部分菜单 `name` 为空
- 部分菜单没有权限码

影响：

- 路由命名、缓存、定位能力下降
- 权限粒度难以统一

## 7. 面向“小项目”的最小可行 RBAC 方案

如果你的目标是“小项目可用，不追求复杂”，我建议只做下面这套 MVP。

### 7.1 数据模型收敛

保留 5 张核心表：

- `sys_user`
- `sys_role`
- `sys_menu`
- `sys_user_role`
- `sys_role_menu`

先不要做：

- 部门表
- 数据权限表
- 岗位表
- 多租户
- 复杂按钮树

### 7.2 后端只做三层能力

第一层：登录校验

- 保持现在的 Sa-Token 登录拦截

第二层：角色和权限加载

- 修复 `SysRole.roleKey`
- 修复 `selectRolePermissionByUserId()`
- 修复默认角色分配
- 清理 `sys_role_menu` 孤儿数据

第三层：关键接口授权

优先对高价值接口加 `@SaCheckPermission`：

- 任务管理相关写操作
- 账号管理相关写操作
- 系统日志查看
- 商品/印花管理写操作

对于这个项目，不需要每个接口都精细化，先覆盖“写操作”和“敏感读操作”即可。

### 7.3 前端只做两层能力

第一层：菜单级权限

- 继续沿用动态菜单路由
- 但把角色菜单数据配完整

第二层：按钮级权限

- 在核心页面接入 `v-permission`
- 先只管新增、编辑、删除、启动、停止这类按钮

不建议一上来做过度复杂的：

- 前端角色中心
- 页面级 AB 权限策略
- 大量自定义权限组合器

### 7.4 管理能力建议控制在最小范围

如果只做“小项目可用”，后台管理只需要这 3 个能力：

1. 用户列表
2. 给用户分配角色
3. 给角色分配菜单

角色本身可以先内置两类：

- `admin`
- `user`

后续再按需要扩展：

- `operator`
- `viewer`

这样能大幅降低前后端复杂度。

## 8. 推荐改造顺序

建议严格按下面顺序做，不要一开始就先做页面。

### 第一阶段：把底座修正

- 恢复 `SysRole.roleKey`
- 修复 `SysRoleServiceImpl`
- 注册时分配默认角色
- 清理 `sys_role_menu` 孤儿数据
- 修正普通用户的角色菜单配置
- 废弃旧版 `init-menu.sql`，重写与现表结构一致的新初始化脚本

完成标志：

- `admin` 和普通用户都能正确拿到 `roles`
- 普通用户登录后能看到完整、正确的菜单

### 第二阶段：补后端授权

- 给关键接口加权限校验
- 把权限码与 `sys_menu.permission` 对齐

完成标志：

- 没权限时，即便手工调用接口也会被拒绝

### 第三阶段：补前端细粒度控制

- 在关键页面接入 `v-permission`
- 让新增/编辑/删除/启动/停止按钮按权限显示

完成标志：

- 同一页面内，不同角色看到的操作按钮不同

### 第四阶段：再决定是否做权限管理页面

如果你只想快速可用，其实可以先不做完整权限后台，只做：

- 一个简单用户列表页
- 一个“分配角色”弹窗
- 一个“角色授权菜单”弹窗

这已经足够支撑小项目。

## 9. 建议你下一步优先做什么

如果马上要进入实现，最值得先做的不是页面，而是下面 5 件事：

1. 修复 `SysRole` 和 `SysRoleServiceImpl`，让普通用户角色先能正确返回。
2. 给注册用户分配默认角色，避免出现无角色用户。
3. 清理 `sys_role_menu` 脏数据，并补齐普通用户的菜单授权。
4. 选 3 到 5 个关键接口加后端权限注解，建立真正的授权边界。
5. 在前端关键页面接入 `v-permission`，只先控核心按钮。

## 10. 一句话总结

这个项目现在已经有了 RBAC 的骨架，但还没有形成闭环。

最短路径不是“做复杂权限中心”，而是先把这 4 件事做实：

- 角色字段修正
- 用户角色分配
- 角色菜单数据修正
- 后端接口权限拦截

只要这四步完成，这个小项目就能拥有一套真正可用、而且不复杂的基础权限系统。
