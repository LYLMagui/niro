# Niro 权限系统重构计划表

日期：2026-03-15

## 1. 文档定位

本文档用于指导 Niro 项目的权限系统重构执行，并作为后续重构进度审查基线。

关联分析文档：

- `docs/2026-03-15-rbac-analysis.md`

使用方式：

- 先以本计划作为执行主表推进重构
- 每完成一个阶段，更新本文档的状态、完成日期、审查结论
- 若范围发生变化，先更新分析文档，再回写本文档

范围更新（2026-03-21）：

- 由于产品方向已明确，**后续会移除 Buff 相关功能**。
- 因此，Buff 扫货任务、BUFF 账号、商品、印花等模块的权限工作从“继续完善”调整为“冻结规划、保留现有保护、待功能删除时统一清理”。
- 本计划后续主线转为：通用 RBAC 骨架、登录/菜单链路、C5、日志、通知、订单记录/库存，以及最小权限管理能力。

## 2. 重构目标

本次重构目标不是做一个复杂权限平台，而是基于 Sa-Token 建成一套“小项目可用”的基础 RBAC。

目标范围：

1. 修正数据库、实体、服务层之间的权限模型不一致问题
2. 修复登录后角色、权限、菜单的完整获取链路
3. 建立后端关键接口的权限校验能力
4. 建立前端菜单级与按钮级的基础权限控制
5. 提供最小管理能力，满足用户分配角色、角色分配菜单

明确不做：

- 部门树
- 数据权限范围控制
- 多租户
- 复杂审批流
- 细粒度按钮树后台配置器

## 3. 执行原则

### 3.1 核心原则

- 先修底座，再补页面
- 先保证后端授权真实生效，再完善前端显隐体验
- 先保证数据库和代码一致，再谈扩展能力
- 全程保留可审查痕迹，避免“改完但说不清”
- 重构的过程中必须遵循本计划进行执行，不可私自添加逻辑和修改

### 3.2 技术约束

- 认证与授权仍基于 `Sa-Token`
- 核心 RBAC 模型仍使用现有 5 张表
- 尽量避免一次性大改，采用分阶段、可回归的重构方式
- 每个阶段都必须有独立完成标准（验收执行由你本人负责）
- 本轮允许的数据库调整只限于补约束、修正字段语义、补齐必要字段映射与初始化数据，不引入复杂新表
- 数据库字段禁止使用外键约束，统一通过各表 `id` 字段进行逻辑关联

### 3.3 数据表改造边界

基于 2026-03-15 对 PostgreSQL 真实库的复核，当前权限模型继续保留以下 5 张表，不做推倒重建：

- `sys_user`
- `sys_role`
- `sys_menu`
- `sys_user_role`
- `sys_role_menu`

本轮明确不做的数据库扩展：

- 不新增 `sys_permission`、`sys_role_permission`、`sys_dept`、`sys_tenant` 等复杂权限表
- 不新增 `tenant_id`、`dept_id`、`is_default`、`menu_check_strictly`、`dept_check_strictly` 等当前阶段无直接收益的字段
- 不为了按钮级权限单独拆表，按钮权限仍预留在 `sys_menu.type=2` 的扩展位上，本轮按最小范围接入

本轮建议执行的数据库调整：

1. `sys_role` 保留现有字段，不新增复杂控制字段；补充 `role_key` 唯一约束，并统一 `status` 语义为 `1=正常，0=停用`，与当前库数据和用户状态语义保持一致。
2. `sys_user_role` 保持双列关联表设计，不增加审计字段；继续使用 `user_id -> sys_user.id`、`role_id -> sys_role.role_id` 的逻辑关联，不增加数据库外键。
3. `sys_role_menu` 保持双列关联表设计，不增加审计字段；先清理孤儿数据，再通过脚本校验和代码防护维持 `role_id -> sys_role.role_id`、`menu_id -> sys_menu.id` 的逻辑关联，不增加数据库外键。
4. `sys_menu` 不拆分页面权限表；目录类型可无 `permission`，但受控页面必须补齐 `name` 和 `permission`，后续若需要按钮级权限，再按 `type=2` 增量扩展。
5. 默认角色本轮不通过新增字段实现，先固定使用稳定的 `role_key` 方案处理，例如默认注册角色使用 `role_key=user`。

## 5. 总体方案选择

本次采用“渐进式重构”方案，而不是一次性重写。

理由：

- 当前项目已经有可运行的登录和动态菜单链路
- 一次性重写风险高，容易把业务功能一起带崩
- 渐进式方案更适合小项目，也更方便审查阶段性结果

数据库复核结论：

- 当前库中权限相关表仍然适合沿用，不需要增加表数量
- 当前主要问题不是“少很多表”，而是“现有表缺少最小约束、语义不统一、脏数据未清理”
- 真实库里 `sys_role_menu` 有 11 条孤儿菜单关联，必须在补数据校验方案前先清理
- `sys_role.role_key` 当前无重复，但缺少唯一约束，后续一旦增加角色会留下隐患
- `sys_menu` 当前只有目录和页面两类数据，本轮不强制补齐按钮表数据

总体路径：

```text
阶段1：模型与数据修正
    ->
阶段2：后端授权闭环
    ->
阶段3：前端权限落地（非 Buff 面收口）
    ->
阶段4：最小管理能力补齐（后续主线）
    ->
阶段5：收尾清理与文档（验收由你本人执行）
```

## 9. 风险与应对

| 风险编号 | 风险描述 | 影响 | 应对策略 |
| --- | --- | --- | --- |
| RISK-01 | 旧数据过脏，迁移脚本一次修不干净 | 菜单与权限结果继续异常 | 先做只读核查 SQL，再做修复 SQL |
| RISK-01A | 缺少数据库外键兜底后，后续变更可能再次写入孤儿关联 | 权限链路再次漂移，历史脏数据回流 | 通过初始化脚本、数据巡检 SQL、保存前校验和发布回归共同兜底 |
| RISK-02 | 一次性改动过多，影响现有业务 | 登录、菜单、路由可能失效 | 分阶段提交，每阶段可单独回归 |
| RISK-03 | 前后端权限码命名不一致 | 菜单与按钮控制失真 | 先输出权限码映射表，再编码 |
| RISK-04 | 只做前端显隐，后端仍可越权 | 安全边界失效 | 关键写接口必须优先加后端校验 |
| RISK-05 | 权限管理页范围失控 | 项目复杂度上升 | 严格限制为“用户分配角色 + 角色授权菜单” |
| RISK-06 | Buff 功能进入删除期后，计划与现网保护边界混淆 | 可能出现“以为要删就先拆保护”的回退问题 | 明确采用“冻结规划、不回退保护、删除时统一清理”的策略 |
